# Foliage weather phase: implementation audit (2026-10-22)

**Scope:** source-only/read-only visual audit. No code, build, game run, GPU capture, parity measurement, or commit. This report refines `WATERFALL_NEXT_EFFECT_SOURCE_AUDIT_2026-10-22.md`; the exclusive UV/GPU lane's files and display were not touched.

## Source contract and smallest seams

- Windows `FoliageSway.fx:44-50` displaces the world-space X vertex by `sin(worldY*.1 + Time*TimeMultiplier*GlobalTimeMultiplier)*normalX`, then displaces Y using the **already displaced X**. The global value changes **phase/frequency**, not authored intensity. `Game/src/Game.cpp:369-377` samples `Timing::GetTotalTimeSeconds()` and the current `WeatherManager` multiplier for draw setup. `Game/src/GameObjects/WeatherManager.cpp:45-59,234-236,270-272` gives a new manager **1.0**, rain **2.625** (`2.5*1.05`), and post-rain **2.5**. The snow constant 3.5 is declared but is not selected by the shown update path.
- Waterfall-top permits weather (`Game/XmlFiles/levels/waterfall_top.xml:2-7`). The affected authored sprites include rope ends 36–39 (e.g. ID36 bottom X 10/5 and `time_multiplier=6`, `:667-680`), tree tops 60–65 (e.g. ID60 bottom X 20 and multiplier 1, `:1058-1071`), and leaf shadows 66–67. `port/game/LevelScene.cpp:490-502` already parses the four corner intensities and local multiplier; `:1007-1013` copies them to `render::Sprite` and supplies `visualTime_`. `port/render/Renderer.h:28-33,40-52` is the SDL-free foliage draw contract. `port/linux/SDLRenderer.cpp:383-420` computes the transformed vertices and currently passes literal `2.5f` to `FoliageSwayWorldVertex`; `port/linux/FoliageSway.h:14-23` already accepts a global factor and preserves X-before-Y evaluation.
- Minimal integration: expose a **per-draw foliage global-time multiplier** in the renderer-neutral `FoliageSway` data (default 1.0 for new/fresh state); obtain it from the existing `WeatherLightning` state in `port/linux/main.cpp` after `weather.Update(dt)` and before `scene.Draw(...)`; thread it through the `LevelScene::Draw` argument (`LevelScene.h:79-80`, `.cpp:920`) to `draw.foliageSway` at `.cpp:1008-1009`; pass that field at the existing `SDLRenderer.cpp:409-410` helper call instead of `2.5f`. This path changes neither painter order nor other sprite effects. An explicit narrow renderer state setter is an alternative but risks stale state on preview/menu draws; a per-sprite parameter makes the dependency visible. Coordinate `LevelScene.cpp` editing with its current owner.
- The weather state can expose `FoliageSwayMultiplier()` in `port/game/WeatherLightning.h` backed by a field initialized to 1.0f, set to 2.625f at its rain-start branch (`:54-60`) and 2.5f at its stop branch (`:35-43`). A query derived from `raining_`/`hadWeather_` alone happens to describe the current automatic Linux cycle, but an explicit field matches the Windows assignment contract and remains correct if forced rain is later ported (`WeatherManager.cpp:410-417` starts rain without setting `mHasHadWeather`). Do not key it to particle visibility or lightning alpha. `port/linux/main.cpp:1064-1069` updates weather only while playing and outside paper/upgrade modals; rain particles are independently updated. Painter items at `:1133-1153` must remain unchanged. `WeatherLightning.h:33-63` already encodes first-rain and stop timing, so no second weather timer is needed.

## Timing and clock caveats

- First rain is **not at exactly 180 s**: `WeatherManager::UpdateNoWeather` tests pre-increment `mElapsedTime > 180` and `Update` increments afterward (`Game/src/GameObjects/WeatherManager.cpp:191-231,372-387`). Linux mirrors this order (`WeatherLightning.h:33-63`). At an update that merely advances elapsed past 180 the factor remains 1.0; on the next allowed update it becomes 2.625. The original comment saying “20 seconds” is stale. The weather clock pauses when disallowed (`WeatherManager.cpp:199-204`; Linux `WeatherLightning.h:34`) and Linux also skips weather updates during paper/upgrade modals (`main.cpp:1065-1069`). Do not derive the factor from `visualTime_ > 180` or a level timer.
- Rain factor starts with `StartRaining`, before rain particles need be visible. It remains 2.625 through the 3 s rain outro; `StopRaining` changes it to 2.5 when `mElapsedTime > rainStart + randomized duration + 3` (`WeatherManager.cpp:270-272,314-327`). Linux sets `raining_ = false` at its corresponding strict-`>` stop (`WeatherLightning.h:35-43`); rain particles may still drain afterward (`WeatherRain.h:16-35`). Thus post-rain 2.5 must not be keyed to `VisibleParticles()`, alpha, flash, or a fade envelope. Both boundaries are step changes in phase, not smoothed crossfades.
- Windows' singleton weather manager survives ordinary level changes unless explicitly destroyed; `LevelProperties.cpp:56-58` only toggles allowance. Linux's `weather` is outside scene loads (`main.cpp:292-300`), and door/restart loads replace `scene` without resetting weather (`:603-620,959-975`); only story/menu return resets weather at `:1053-1055`. Therefore 1.0 is a **fresh-manager** value, not every waterfall entry. Do not reset the multiplier on `LevelScene::Load`.
- The Windows shader uses process-total `Timing` time (`Game.cpp:371-377`); the port uses `visualTime_`, reset to zero on each `LevelScene::Load` and advanced at `UpdateVisuals` (`LevelScene.cpp:125,732-733,1008-1009`). This existing clock-origin mismatch can shift the displayed pose even if factor transitions are correct. Keep the phase clock continuous across **weather transitions**; do not reset or substitute the weather elapsed clock. Cross-level Windows pixel matching requires a separately controlled shader clock/origin and equivalent pause/update timing. Linux currently updates visual time even when weather updates are skipped by modal gating (`main.cpp:1064-1072`), another controlled-comparison caveat.
