# Forest player-arm update/render timing source-delta audit — 2026-10-23

## Verdict

**Open mismatch, not runtime closure.** Original Windows advances the forest player's finite back-arm with `Timing::GetLastUpdateDelta()`, the **preceding rendered modified update delta**. Current Linux advances it with the **current** `dt` twice on a successful projectile shot. The source difference can select a different visible arm PNG on the very first shot draw. This is a source-backed command/texture-timing finding, not a matched-frame pixel measurement or a claim about visual severity.

## Source chain and exact divergence

- Forest ID2 is an animated `Player` using `player_anim_default.xml` (`Game/XmlFiles/levels/forest_exploration_1.xml:33-46`). Its arm `Still` and `Running` sequences each contain ten frames at 30 fps (`Game/XmlFiles/animation/player_anim_default.xml:1483-1508`). The XML also defines `Strafing` at `:1510-1521`; this audit's discriminator is deliberately grounded `Still`.
- On a successful projectile, Windows `Player::FireWeapon` calls arm `Restart()` then `Animate()` (`Game/src/GameObjects/Player.cpp:465-474`). `Character::UpdateAnimations` calls `Animate()` again if unfinished, then switches and finishes the arm if its sequence differs from the body (`Game/src/GameObjects/Character.cpp:1098-1112`). `Restart` clears frame and elapsed; `Finish` sets frame to frame count (`Game/src/Animation/AnimationPart.h:58-65`). `AnimationPart::Animate` adds `GetLastUpdateDelta()`, subtracts one `1/frameRate` period and advances **at most one frame per call** (`Game/src/Animation/AnimationPart.cpp:201-237`). Thus both shot-tick advances read the same preceding-render slot, not two distinct frame deltas.
- The timing slot starts at zero (`Game/src/Core/Timing.cpp:6-15`). The Windows loop uses the modified delta for `Update` (`Game/src/program.cpp:168-171`), calls `Render` (`:173`), and only then stores `delta * GetTimeModifier()` as LastUpdateDelta (`:175`). This is the prior **rendered**, modified value. The source draw selects the unfinished arm frame before drawing the body (`Game/src/GameObjects/Character.cpp:1888-1906`).
- Linux's `UpdatePlayerVisual` has only current `dt` as a timing input (`port/game/LevelScene.h:163-167`); its arm lambda adds that `dt` (`port/game/LevelScene.cpp:1163-1170`) and is called once for `projectileFired` and again in the regular update (`:1172-1177`). Its arm command is emitted before the body if frame is in range (`:1306-1314`). `port/linux/main.cpp:1103-1109` supplies current `dt` to the scene before draw and skips visual update on simulate-only iterations. No distinct preceding-rendered animation delta reaches the arm. The scene's existing prior-rendered slot (`LevelScene.h:229-232`, `LevelScene.cpp:1325`) currently feeds waterfall autoscroll (`LevelScene.cpp:1295-1302`), **not** arm animation; its existence does not close this mismatch.

For a controlled shot update with preceding rendered modified delta `.001f` and current `dt=.02f`, source-equivalent `Restart; Animate; Animate` leaves elapsed `.002f`, frame **000**. Current Linux adds `.02f` twice: the first call crosses `1/30` and selects frame **001**; the second does not cross again (`.04f - 1/30 < 1/30`). These are exact expected command paths `Game/Media/characters/player/back_arm_attack/back_arm_attack_000.png` versus `.../back_arm_attack_001.png`, assuming grounded Still throughout. This controlled schedule is a discriminator, not an assertion that original Windows normally produces a `.02f` update (its loop caps against TargetDelta at `program.cpp:162-166`).

On the next grounded Still successful-shot update, pass **current** `.02f` and a **separate animation delta** `.001f`, with `projectileFired=true`; draw and assert exactly one arm command, exact `_000.png` path, immediately before the ID2 body command. The present source should fail by emitting `_001.png`. The fixture must call the real public scene update/draw, not a copied arm arithmetic helper. A shot tick is sufficient; no 20-tick body/orb cadence fixture is needed. `eligibleFireAttempt` alone is not a successful shot and must not be used as the trigger.

This discriminator requires the integration owner to expose/pass the process-owned preceding **rendered modified** delta as a distinct `animationDt` (initially zero), and change the arm accumulator to use it, preserving the two `advanceArm()` calls and finite/sequence behavior. With today's one-delta `UpdatePlayerVisual` API, passing `.001f` as `dt` would merely test a different current update and could falsely pass; the integrated red/green test is not executable against the current API without that seam. No executable test was added or run in this read-only lane.
