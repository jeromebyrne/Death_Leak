## Exact known source/port contract still open

- XML `Game/XmlFiles/levels/forest_exploration_1.xml:4,7-29,612-635,666-689` authors all three as `ParallaxLayer` with `followcamx=true`, `followcamy=false`; ID37/40 are 2048-world-unit, alpha-.95 shrubbery/top-tree layers with X UV multiplier .000690, while ID1 is the distant background. Their current-camera UV movement is intentional.
- In normal, unpaused Windows update→draw, `Game/src/GameObjects/ParallaxLayer.cpp:26-35` invokes `Sprite::Update` **before** assigning camera X to the layer position. Through `DrawableObject::Update` and `GameObject::Update` (`Game/src/GameObjects/DrawableObject.cpp:41-43`; `Game/src/GameObjects/GameObject.cpp:160-212`), this caches the entering X in the World matrix. `ParallaxLayer::Draw` (`:37-83`) independently computes U from the **current** camera X; `Sprite.cpp:626-637` submits the cached World. Thus a moving frame can draw prior-follow-X geometry with current-camera UV. The draw must also pass the original manager's culling; first-load and skipped-update behavior have separate history.
- Current dirty `port/game/LevelScene.cpp:1231-1277` still computes followed `worldX=cameraX` and `draw.uvShiftX=cameraX*object.cameraParallaxX*(flip?-1:+1)` in one draw. No prior-follow-X state appears in `LevelScene.h` or in the inspected dirty `LevelScene.cpp` diff (the latter changes right-stick aim-line parameters/rotation). The SDL UV sign is the previously established D3D-to-SDL convention, not a new reversal bug. At a settled X=1000 then a +8-world-unit step, the source-contract destination center is 634.6667 versus Linux 640 at 2/3 scale, while both use the current equivalent UV phase; a second update held at X=1008 converges. This arithmetic was already audited; it is not a fresh runtime measurement. It changes X registration only, not Y extent, layer opacity, painter order or texture content.

## Narrow acceptance / decision discriminator

1. **First obtain a same-history original-Windows trace** for forest-1 ID37 or ID40: after a held camera, record camera X, the layer's position entering `ParallaxLayer::Update`, World translation used at draw, current left/right U, viewport/backbuffer scale and whether the manager actually draws it. Use a moving step and then a held step. Without this runtime gate, code-path prediction is not a pixel-parity mandate.
2. If the trace confirms a visible source-exact discrepancy worth retaining, CPU-spy the *actual forest XML* IDs 1/37/40 on the current port. For a settled 1000→1008→1008 camera sequence at 2/3 scale, a scoped implementation should emit center X 640→634.6667→640, while `uvShiftX` follows current camera on both moving and held frames. Check fresh-load initialization, culling and skipped-update behavior separately. Keep destination Y/size, alpha, texture, UV convention, weather, depth and draw order unchanged. Do not change ordinary sprites.
3. Only then compare same-history lossless Linux and Windows crops around ID37/40 image features and layer edges. A Linux-only A/B or unmatched Steam JPEG establishes neither improvement nor release parity. If source runtime instead rebuilds World after follow, or the matched moving delta is immaterial, close this candidate without a patch.

**Uncertainty/priority:** the source-path difference is concrete, but its perceptual effect on the present active-play route is unmeasured; previous Linux-only controlled comparisons found a small moving-frame effect and zero held-frame effect. It cannot explain the broad lower darkness. No distinct higher-impact, source-proven *new* omission was found in the authored forest effect/class inventory: foliage IDs41–46, leaf spray ID47, fog ScrollingSprites119/122, and the ordinary large layers are already admitted by `LevelScene`; their exact Windows pixel parity remains open. This is an inspection bound, not a claim that every visual path is perfect.
