# Waterfall-top ID59 Windows followed-X timing source gate — 2026-10-23

## Verdict

**The checked-in original Windows source predicts a preceding-update followed-X *world matrix* at each normal render, while using the current camera X for the view and ID59 UV phase.** This is stronger than an inference from the Linux A/B: it follows directly from matrix construction before `ParallaxLayer::Update` assigns the latest followed position, and from the single update→render→present loop. It is **not** a measured contract of a shipped Windows executable. No original `.exe`/`.pdb`, synchronized Windows draw trace, or matched lossless frame is available in this repository; the `Game/x64/{Debug,Release}` contents are project-output metadata only. Accordingly, this source gate establishes the behavior of the checked-in code under normal active play, but not binary provenance or matched Windows pixels. No port change is made here.

## Source chain (exact references)

1. `Game/XmlFiles/levels/waterfall_top.xml:1034-1056` authors ID59 as a `ParallaxLayer` with `always_update=true`, `followcamx=true`, `followcamy=false`, `effectlighttexture`, `shrubbery.png`, alpha .95, and nonzero X UV multiplier. Its authored initial X is 2778.985352; that value can be used for the first update's matrix until another update rebuilds it.
2. `Game/src/program.cpp:148-176` gates on a target delta, performs exactly one `Update(...)`, then `Render()`, then `Present()` per loop iteration; it does not run a catch-up series of updates before one render. `program.cpp:287-317` connects those calls to `Game::Update` and `Game::Draw` (with optional postprocess). This is the normal non-exiting runtime path.
3. `Game/src/Game.cpp:154-163` advances the camera with `FollowTargetObjectWithLag()` **before** object updates. `Game.cpp:176-180` calls `GameObjectManager::Update` unless the damage-pause gate suppresses it. `Game/src/GameObjects/GameObjectManager.cpp:221-247` updates `always_update` ID59; it then draws each visible drawable in `:302-330`. `Game.cpp:354-408` calls that draw path.
4. In `Game/src/GameObjects/ParallaxLayer.cpp:26-35`, `Sprite::Update(delta)` runs **before** `m_position.X = m_camera->X()`. `Game/src/GameObjects/Sprite.cpp:358-366` delegates through `DrawableObject::Update`; `Game/src/GameObjects/DrawableObject.cpp:41-43` delegates to `GameObject::Update`. `Game/src/GameObjects/GameObject.cpp:160-210` builds `m_world` with a translation from the *then-existing* `m_position.X`. The parallax constructor disables base object parallax (`ParallaxLayer.cpp:4-20`), so its translation does not receive a camera-offset correction in that base path. Assignment at line 33 changes position only; no later matrix rebuild occurs in `ParallaxLayer::Update`.
5. ID59's `effectlighttexture` draw binds `m_world` directly in `Game/src/GameObjects/Sprite.cpp:626-637`; its GPU draw follows at `:650-669`. `ParallaxLayer::Draw` reads the **current** camera X at `Game/src/GameObjects/ParallaxLayer.cpp:37-40`, computes X texture shift at `:43-83`, and delegates to `Sprite::Draw` at `:158-159`. Thus current UV does not imply current world translation. `GameObjectManager::Draw`'s camera/view culling also uses current camera state, which is separate from the bound world matrix.

Let `C_n` be camera X after the camera-follow call in normal update `n`, `P_n` the ID59 X stored after its update, and `W_n` the X translation built in its world matrix during that update. For `followcamx=true`, the call order gives `W_n=P_(n-1)` then `P_n=C_n`; therefore after the first update, normal render `n` binds `W_n=C_(n-1)` while the view and X UV are based on `C_n`. The first update instead uses the authored/initialized position. A held camera makes the values coincide, and damage-pause/paused modes can leave an older unchanged matrix; those are not evidence of current-X matrix rebuilding. This is a **one-update** lag, which equals one preceding rendered frame only in the ordinary one-update/one-render active loop, not as a general data structure or across exceptional suppressed updates.
