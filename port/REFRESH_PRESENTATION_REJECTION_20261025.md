# Fixed-step / high-refresh presentation slice — rejected (2026-10-25)

## Decision

No runtime change is accepted. The existing live loop already advances simulation in fixed 1/60-s quanta and coalesces catch-up updates, but **application presentation is still tied to an update**: with no due update, `main.cpp` sleeps and retries without drawing or swapping. This slice cannot honestly claim device-supported >60-Hz application presentation or interpolation. Its acceptance gates (a parity-safe presentation implementation, synchronized control/candidate/control full-frame pixels, physical NVE7 serial A/B/A latency and gameplay endpoints, and a selected high-Hz display) were not all satisfiable; a report-only disposition preserves the running game.

## Source contract and blockers

- `port/linux/FixedStepPacer.h`: 60-Hz fixed step, elapsed-time accumulator, catch-up debt capped at 120 updates. `main.cpp` lines ~739–752 consumes a simulation quantum before doing any work; no-due iteration only sleeps. It skips intermediate catch-up draws at ~1606 and commits shader phase per simulation update. Simulation and presentation are not separate loop phases.
- The draw path begins around `main.cpp:1620` and is embedded in the large update loop. It consumes update-scoped camera shake random signs, `precedingRenderedModifiedDelta`, `ShaderClock::Draw()/RenderCompleted()`, update-frame capture/script ordinals, and game/UI state. Re-entering this block for a held frame would change state or RNG order unless it is refactored into a side-effect-free presentation snapshot. Repeating `SDL_RenderPresent` alone is not a valid full-frame replay: SDL does not guarantee post-swap backbuffer contents, and the finished frame has post-sepia HUD, film, modal, debug and loading layers not retained in the scene target.
- Gameplay and final HUD film use monotonic wall clock at 11 FPS; the FPS HUD counts *presented* frames using wall time. These must remain presentation-clock concerns. Shader, camera/animation, audio/event updates must remain simulation-clock concerns. Advancing film only on 60-Hz updates or incrementing FPS per simulation update would give incorrect high-refresh behavior.
- `SDLRenderer::Initialize` opens a resizable window and requests vsync, but has no `SDL_GetDisplayMode`/`SDL_GetCurrentDisplayMode` selection, refresh negotiation or actual-mode report. SDL's physical Xorg query during this slice reported **current 1440×900@60**. It also listed 120-Hz modes at *other* resolutions (1440×810 and smaller); these are advertised alternatives, not a selected/validated 120-Hz gameplay mode. No 8K or >60-Hz physical acceptance is claimed.

## Bounded next implementation contract

1. Introduce a distinct render/present slot after a `while (pacer.Due())` fixed-update phase; count script/update ordinals only there. Build an immutable render snapshot (camera/shake, previous/current transforms, shader phase, UI state) and a side-effect-free draw function; first support held state, then interpolate only fields with validated prior/current semantics. Keep fixed-dt scripted routes' one-update/one-render behavior unchanged.
2. Retain the *entire* completed post-HUD frame for held presentation via an explicit target or redraw from the immutable snapshot. Do not rely on undefined post-swap backbuffer contents or replay update-side RNG. Measure the target/copy cost and require exact synchronized full-frame pixels at 60 Hz before accepting a presentation-path change.
3. Enumerate/select/report display refresh on the real window, then test selected 30/60/75/120/144/240-Hz modes only where supported. The physical monitor's current 1440×900@60 mode does not prove any higher mode. For each supported mode, require serial physical NVE7 control/candidate/control gameplay endpoints, film/HUD clocks, full-frame synchronized pixels and p50/p95/p99/transition latency. If 120-Hz mode selection is attempted at 1440×810, treat it as a different-resolution experiment, not 1440×900 high-Hz acceptance.

No production implementation, 60-FPS claim, >60-Hz/8K acceptance or release claim follows from this rejection.
