# Autoscroll cross-scene render-clock design — read-only source follow-up (2026-10-24 03:32Z)

## Finding and limits

**Yes: this is a general, source-proven *conditional command-clock divergence* for every enabled authored autoscroll layer, not a special ID25 speed or phase rule.** Windows `Timing::mLastUpdateDelta` is process-owned, initialized once to zero and set *after* each `Render` to that frame's modified update delta (`Game/src/Core/Timing.cpp:6-16`, `Game/src/program.cpp:115-117,149-177`). `ParallaxLayer::Draw` reads that same slot for both X and Y UV increments before `Sprite::Draw` (`Game/src/GameObjects/ParallaxLayer.cpp:39-161`). Level creation does not reset it; `GameObjectManager::LoadObjectsFromFile` constructs, initializes, scales and zero-updates new objects without touching Timing (`Game/src/GameObjects/GameObjectManager.cpp:377-483`). `GameObjectManager::Draw` calls a visible, positive-alpha object's `Draw`, which owns the UV mutation (`:302-330`). Thus a newly drawn layer uses the preceding **process render**, including during a paused/load interval, rather than the preceding render of that scene.

All enabled authored autoscroll in `Game/XmlFiles/levels/*.xml` is positive Y, with X false: waterfall-top IDs **6, 7, 10, 13, 14, 15, 16, 31** and waterfall-bottom IDs **10, 13, 14, 15, 16, 17, 18, 25, 26, 27, 28**. X would share the Windows clock rule if ever enabled, but the port currently parses/advances only Y (`port/game/LevelScene.cpp:411-412,1444-1451`), so X parity is **not** claimed. Positive speeds scale by backbuffer Y/1080 on Windows (`ParallaxLayer.cpp:223-231`; `GameObjectManager.cpp:451-463`); this clock issue is independent of speed/texture/effect.

Linux owns `precedingRenderedModifiedDelta` in `port/linux/main.cpp:694`, advances it after a completed draw at `:1948`, and already supplies it to other preceding-render visual consumers at `:1535,1548`. However, autoscroll in `LevelScene::Draw` reads `previousRenderedModifiedDelta_`, initialized to zero on each fresh `LevelScene` (`port/game/LevelScene.h:247-248`), then set from scene-local `pendingModifiedDelta_` only at the end of that scene's `Draw` (`LevelScene.cpp:1444-1451,1479`). `Load` resets pending (`:139-141`), and main constructs/move-installs fresh scenes at `:821,866,1017,1396,1427,1466`. The first eligible destination draw after any such replacement therefore advances by zero locally even if the process clock is nonzero. If that draw occurs while gameplay `UpdateVisuals` is skipped (e.g., `loadingPausedThisFrame`, `main.cpp:1530-1536`), its end-of-draw assignment copies pending zero; the next scene draw may also use zero although Windows' process slot has continued to update. This makes a one-time seed at scene installation insufficient for the paused path.

There is a **separate visibility/culling caveat**: Windows gates `ParallaxLayer::Draw` on alpha and camera view *before* UV mutation (`GameObjectManager.cpp:302-330`); Linux currently mutates Y phase before `SpriteMayIntersectViewport` (`LevelScene.cpp:1444-1455`). Do not silently conflate this with the cross-scene clock fix. The command-clock conclusion applies to layers that Windows actually draws, and any test must use known-visible layers or account for this separate eligibility difference. The saved ID25 packet/phase arithmetic was assessed in `PRIVATE_WATCHDOG_BOTTOM_ID25_PHASE_CADENCE_GATE_20261024T0330Z.md`; it is not re-audited here. There is no original matched-state packet, so this report does **not** assert same-state pixel parity or a measured Windows-vs-Linux pixel offset.

## Minimal correction design (for implementation owner)

Make the process previous-render delta the sole production input to autoscroll `LevelScene::Draw`, rather than trying to carry scene-local clock state across loads. Ownership scope: `port/linux/main.cpp` (both scene-draw calls at current lines 1601 and 1656), `port/game/LevelScene.h` (draw API), and `port/game/LevelScene.cpp` (Y increment at 1448-1450 and removal of redundant `pendingModifiedDelta_`/`previousRenderedModifiedDelta_` bookkeeping at 139-141, 847, 1479 and declarations at `LevelScene.h:247-248`). Thread the existing `precedingRenderedModifiedDelta` into each `scene.Draw`; use it in `autoScrollYSpeed * (720/1080) * .001 * (priorDelta / targetDelta)` immediately before submission, retaining each *sprite's* V phase and the existing draw-time cadence. The current fixed-target port uses `priorDelta * 60`; do not substitute current `dt` or update ordinal. Keep the delta process-scoped through fresh scene swaps, opaque loading, pause, and time-modifier changes; no per-swap seeding/reset. A required parameter (or equivalent explicit render-clock context) is preferable to a silent zero default. Updating non-production `Draw` call sites in tests/perf harnesses is a mechanical follow-up for their owners; do not modify those active lanes here. This design does **not** address X-autoscroll support or the separate pre-cull mutation.

The decisive external fidelity gate remains an original Windows same-state *command* capture across a scene handoff (and original packet for any pixel claim).
