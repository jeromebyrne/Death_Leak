# Strafe aim-line source contract — read-only audit, 2026-10-22

Scope: static Windows `Player`/`InputManager` against current Linux `LevelScene`/`main` and `CURRENT_RENDERER_DIFF_VISUAL_QA_2026-10-22.md`. No source changes, build, capture, GPU use, or parity claim. The concurrent `port/linux/main.cpp` edit was left untouched.

## Source behavior and mismatch

- `Game/src/GameObjects/Player.cpp:97-98` fixes the unscaled projectile attachment at `(5,25)`; `:634-658` creates a 400×400 aim-line sprite attached at that offset, initially alpha 0. `:345-365` sets line Y to player Y+25, refreshes a **0.05 s** hold every update while `mIsStrafing`, holds alpha 1 while the timer is positive, then fades by `10*delta` per update. This is independent of whether a projectile was created.
- `Game/src/GameObjects/Player.cpp:388-416` refreshes the same hold on a weapon attempt **after** early collision/rolling/water exits but **before** cooldown/burst rejection. `Game/src/InputManager.cpp:400-420` automatically attempts a primary shot while the right stick exceeds its deadzone and the listed fall/melee gates permit it; therefore a real Windows opposed-stick strafe ordinarily also attempts firing. “No-fire strafe” is a deliberate discriminator for the independent strafe-hold path (e.g. suppress the shot/attempt in a fixture), not a claim that Windows normally treats active right-stick aim as a separate no-fire button mode. Linux `port/linux/main.cpp:707-714` instead obtains `fire` from a script command or `KeyDown(Down)`; a real right-stick strafe with no Down can have no fire attempt.
- `Game/src/InputManager.cpp:374-395` starts from the strafe/facing horizontal direction, but when **either** right-stick component exceeds the deadzone it normalizes `(RX,RY)`, changes camera target Y by `300*RY/32767`, and calls `Player::SetAimLineDirection`. `Game/src/GameObjects/Player.cpp:661-697` maps that vector's quadrant to a rotation angle, vertical-flip state, and **X attachment sign** (`+5` for X>0, `-5` for X<=0). Axis/diagonal orientation is therefore determined by right-stick aim, not player movement or just the body-facing sign. `InputManager.cpp:449-503` sets `mIsStrafing` for opposed sticks (subject to roll/fall/melee gates), adjusts target X by `450*RX/32767`, and resets target offset on neutral right stick. `InputManager.cpp:574-585` calls aim processing before primary fire and strafe processing; this sequencing matters to any frame-exact comparison.
- Port `port/game/LevelScene.cpp:591-602` loads the matching texture/size/depth, but `:1075-1085` refreshes hold **only** from `eligibleFireAttempt` and sets `playerAimLineFacing_ = facing`. `:1099-1106` separately points the strafe body at `strafe.aimFacing`. `:1213,1217-1221,1260,1272-1275` hides the zero-alpha line and otherwise uses movement-facing for attachment/vertical flip; there is no right-stick-angle input to the line and no aim-line rotation state. In opposed LX<0/RX>0, no-Down frames, the line stays absent; with a fire attempt, the body faces right while the line can remain left-attached. `port/tests/strafe_body_cpu_test.cpp:181-201` currently requires a fire attempt and asserts the old movement-facing line, so it encodes the discrepancy rather than detecting it.
- The renderer-diff QA report `port/CURRENT_RENDERER_DIFF_VISUAL_QA_2026-10-22.md:7-15` independently flags this line/attachment issue and the missing right-stick camera offset. This audit confirms both from source. It does **not** establish a new SDL rotation/UV bug or pixel parity.
