# Small-orb `orb_shatter` trail — draw/alpha/lifetime contract (2026-10-22)

Read-only source comparison. This isolates the **rendered quad's frame phase and opacity**; creation, ownership, forest coverage, attachment, painter merge, and broad CPU gates are already covered by `ORB_TRAIL_IMPLEMENTATION_SEAMS`, `ORB_TRAIL_PATCH_PLAN`, and `FOREST_ORB_TRAIL_CPU_GATE`. No source/build/test/GPU work was performed.

## Windows source: what reaches the framebuffer

- On small-orb tracking, `CurrencyOrb::AddTrailParticles` requests a 15-particle radial spray with `Media\orb_shatter.png` supplied by the `flame_orb` material, at the orb's depth, 3200×1200 bounds, 0.1–0.35 s lifetime, 40–80 size, 0.8–1 brightness, lifetime scale target 0.1, fade-in 0.15 and fade-out 0.8, then attaches at zero offset (`Game/src/GameObjects/CurrencyOrb.cpp:326-389`; `Game/XmlFiles/materials.xml:657-660`). The 15 lifetimes are **deterministically staggered**, `0.35 - (0.25/15)*i`, so the shortest is ~0.1167 s, not 0.1 s (`Game/src/Particles/ParticleEmitterManager.cpp:250-275`). At 1920×1080, `gameScale=1` (`Game/src/Game.cpp:142-143`); source particle size/speed are multiplied by that scale when sampled (`ParticleEmitterManager.cpp:313-335`).
- Each source `Update` writes six vertices per *live-at-entry* particle using **the position and size at update entry**, then advances position, age, alpha, and size (`Game/src/Particles/ParticleSpray.cpp:172-220,222-282`). Thus the next draw's center and dimensions are a previous-step snapshot. It does not draw an updated-size quad centered on a previous-step position. Texture UVs `tex1..4` map a full image rectangle (`ParticleSpray.cpp:8-11,192-220`). `Draw` uploads those vertices and issues `particleCount*6` triangles (`ParticleSpray.cpp:128-157`); the shader samples the texture and multiplies **all RGBA by per-particle brightness** (`Game/ShaderFiles/Particle.fx:52-59`). The `alpha` effect variable is declared/set but **not used in this pixel shader** (`Particle.fx:7,52-60`; `ParticleSpray.cpp:133-137`). Standard source blend is source-alpha over destination (`Game/src/Core/Graphics.cpp:392-405`). Orb sprite alpha therefore must not be applied a second time to the trail.
- Fade is evaluated **after** age advances: start each update with vertex alpha 1, then use `remainingFraction / 0.2` only when remaining fraction `<0.2`; otherwise use `elapsedFraction / 0.15` only while elapsed fraction `<0.15`; otherwise 1 (`ParticleSpray.cpp:191-195,233-258`). Effective sampled alpha is `textureAlpha × brightness × fade`; RGB is `textureRGB × brightness` (`Particle.fx:52-59`). In source the fade and size values for a frame are derived from the newly advanced age while vertex XY/size came from the prior state. Fade-out 0.8 means the **last 20% of life** fades, not 80% of life.
- At expiry the same update has already built vertices and computed fade, then either resets position/speed/size/age to the attached orb or marks the particle dead (`ParticleSpray.cpp:285-315`). Attached recycle places it at the *exact current parent XY*, without the original ±3 spawn offset (`ParticleSpray.cpp:479-514`); this is an initial-spread vs recycle visual distinction. The parent is detached and looping disabled on collection (`CurrencyOrb.cpp:112-120`), so remaining particles expire naturally. Source `Warm(true)` is explicitly called for XML-created sprays (`GameObjectManager.cpp:921`), while the runtime radial factory shown here only adds the spray (`ParticleEmitterManager.cpp:350-370`); do **not** assume deferred warm-up is part of the runtime orb trail contract merely because the general `ParticleSpray::Update` supports it (`ParticleSpray.cpp:337-363`).

## Linux state, visual-fidelity gap

- The current `port/game/ParticleSpray.h:40-68` preserves the post-step age/fade/size formulas and previous-step `drawX/Y`, but `Draw` computes the rectangle from **current `p.size`** (`:81-89`). Source uses pre-update size for that frame (`Game/src/Particles/ParticleSpray.cpp:177-180,192-220,269-282`). With lifetime shrinking from 1.0 to 0.1, Linux therefore shows each quad one update *too small* relative to its held previous-step center. This is clearest in the first tick after creation and around a recycle; no GPU is needed to distinguish it.
- The Linux tint maps brightness to RGB and `brightness × fade` to alpha (`port/game/ParticleSpray.h:92-96`), matching the shader's multiplication; SDL applies color/alpha modulation with ordinary blending (`port/linux/SDLRenderer.cpp:167,179-194`). Do not multiply in orb sprite alpha (~0.75) or alter the existing fade thresholds. The current generic port unconditionally warms after its first positive update (`ParticleSpray.h:69-79`), whereas the runtime Windows radial construction does not request `Warm(true)` in the cited path. A runtime orb trail that reuses this behavior would visibly jump particles to randomized ages/positions after its first update and diverge in onset density/phase. Keep XML leaf/splash warm-up unchanged; make warm-up opt-in/off for runtime trail if source parity is the target.
- The current generic Linux `Draw` skips `dead` particles (`ParticleSpray.h:83-84`); source's vertex-buffer draw count is fixed to the full particle list even after death (`ParticleSpray.cpp:128-157,172-176,316`). Those source slots may contain stale/uninitialized vertices, so this is **not** a fidelity target to recreate. Preserve Linux dead-particle suppression.

## Minimal implementation recommendations

1. For runtime trail particles, store `drawSize` alongside `drawX/Y` at update entry and use it for destination XY **and** width/height; initialize it to `startSize` on creation. A generic change is safe only if checked against existing authored spray captures. Keep age-derived fade as-is, including its one-step phase relative to geometry.
2. Add a narrow runtime-trail `warmOnFirstUpdate=false` option (or instantiate it already `warmed=true`) rather than disabling XML spray warming globally. Do not add the orb's own sprite opacity to spray tint.
3. On attached recycle use exact current orb XY; retain initial ±3 spread only for initial particle positions. Do not emulate undefined source dead slots.

## Focused non-GPU discriminant

In a `CaptureRenderer`/direct `ParticleSpray` check, create one trail particle with `startSize=size=80`, `lifetime=0.35`, `scaleTo=0.1`, `fadeIn=0.15`, `fadeOut=0.8`, `brightness=0.8`, `directionX=1`, `speed=2`, `gravity=0`, and a known texture ID. After one `Update(1/60)`, capture its draw: **destination side must still be `80×2/3` pixels and center must be initial XY**, while tint alpha is `round(255×0.8×((1/60)/0.35)/0.15)` (allow ±1 byte for float rounding) and tint RGB `round(255×0.8)`. Current Linux code yields a smaller side (~`76.57×2/3`) because it draws updated size. After first update, runtime trail `elapsed` must remain `1/60` and position must reflect only one simulation step—not a randomized warm age. Repeat at a fixed age in the final 20% to verify alpha `brightness × remainingFraction/0.2`, then detach/expire to confirm no visible dead quads. This is a render-contract discriminant, not a duplicate broad orb lifecycle test; no GPU, Windows RNG matching, or pixel image comparison is required.
