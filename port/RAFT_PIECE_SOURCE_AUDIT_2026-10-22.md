`Game/XmlFiles/levels/forest_exploration_1.xml:191-205,928-957` supplies all three from the same `Media/objects/raft.png`, at the same `kGround` depth (4500), each 458.298584 × 125.316017 world units, opaque alpha 1, with `fade_when_player_occluded=false`, no repeat, sway, or animation. ID11 is centered `(267.985,3115)`, rotation 0, horizontal flip **true**. ID57 is `(640.085,3066)`, rotation **+0.219974 rad = +12.604°**, flip **true**. ID58 is `(-132.215,3070.198)`, same rotation, flip **false**. Source XML order is 11 then 57 then 58. Their differing flip flags are authored, not an art discrepancy. The shipped ContentBuilder level copy is byte-identical to `Game/XmlFiles/levels/forest_exploration_1.xml` (`cmp -s`); no asset/XML change is warranted here.

At unit zoom, the Linux projection in `port/game/LevelScene.cpp:708-785` maps these unrotated destination rectangles to a 1280×720 logical screen with `scale=2/3`, centered on `(cameraX,cameraY)`. At a camera X near 700 (only a reference-search seed), approximate horizontal spans are ID58 **[-67,238]**, ID11 **[199,505]**, ID57 **[452,757]** pixels. Thus ID58/11 overlap around x199–238 and ID11/57 around x452–505 before rotation. Camera changes translate this entire group together; they do not change relative raft seams. The capture's seam near x≈200 is consistent with the first overlap at a camera in this neighborhood, but the exact camera was not logged. The 0.219974-rad rotations move corner positions; these unrotated spans are illustrative, not measured pixel boundaries.

## Windows versus Linux render paths

- Windows reads rotation from XML (`Game/src/GameObjects/GameObject.cpp:348-350`), applies `D3DXMatrixRotationZ` with the scale/translation world matrix (`:202-210`), and its raft shader multiplies local vertices by World, View and Projection (`Game/ShaderFiles/BasicLightTexture.fx:37-48`). The quad is centered on the object's dimensions (`Game/src/GameObjects/Sprite.cpp:215-222`). Horizontal flip is implemented as a negative X matrix scale (`Sprite.cpp:86-94`), so the flipped and rotated raft pieces require transform-order parity, not merely matching texture names.
- The Linux loader retains XML position, dimensions, radians, depth, flip flags, and alpha (`port/game/LevelScene.cpp:409-479`). It projects centered destinations, sets flips, converts radians to degrees, and invokes `SDL_RenderCopyExF` for rotated copies (`LevelScene.cpp:748-785`, `port/linux/SDLRenderer.cpp:169-232`). The prior `port/FOREST14_COMPOSITION_ROTATION_AUDIT.md` documented and verified the radians-to-degrees/sign correction already present in this code. This audit found no reversion of that fix.
- Windows `GameObjectManager::OrderDrawablesByDepth` uses `std::list::sort` on descending depth (`Game/src/GameObjects/GameObjectManager.cpp:65-70,1022-1025`), which preserves equal-depth XML order; Windows draws in that list order (`:302-330`). Linux uses `std::stable_sort` descending depth (`port/game/LevelScene.cpp:486`) and draws the resulting sequence (`:729-785`). Therefore same-depth overpainting is **ID58 above ID57 above ID11** in both paths, assuming the original manager retained XML insertion order. No source-backed raft-specific draw-order inversion appears.
- All three raft objects explicitly disable occlusion fading in XML. Linux honors that flag (`LevelScene.cpp:474,635-665`). A player-occlusion fade cannot explain their seam. Linux's pre-draw cull tests the unrotated destination (`:783-784`), unlike Windows camera's rotated-bound logic (`Game/src/Core/Camera2D.cpp:48-95`), but the approximate spans above intersect the screen, so that general culling difference does not explain the observed seam in this composition.

## Finding and bounded next step

The Linux capture note reports a steeper/disjoint left section while the Steam still reads as a smoother shallow arch. **No concrete raft-only renderer mismatch is proven from these sources and unmatched frames.** The current XML poses, flips, size, same-depth painter order, alpha/occlusion flags, and radians-to-degrees conversion are represented in Linux. The remaining narrow technical uncertainty is whether the combination of horizontal reflection and rotation in `SDL_RenderCopyExF` exactly matches Windows' negative-X scale followed by its world rotation for ID57 (ID58 is rotated but unflipped). It would be premature to flip an angle, rearrange XML IDs, or edit `raft.png` based on the Steam JPEG.

Recommended next fix gate: first obtain a lossless Windows forest-1 frame with actual camera X/Y, viewport/zoom and player/state (as `FOREST_REFERENCE_AUDIT.md` requests). At identical camera and logical viewport, compare the **individual silhouettes** of IDs 58, 11, 57 and their intersections in that order. The existing Linux `DEATHLEAK_RENDER_ONLY_XML_IDS`/`DEATHLEAK_RENDER_HIDE_XML_IDS` filter (`port/game/LevelScene.cpp:61-83`) can isolate these without source or XML edits; the Windows side needs equivalent per-ID evidence or coordinate instrumentation. If matched individual geometry differs, fix only the Linux projection/flip-rotation implementation and verify all three IDs; if geometry matches but seams differ, inspect equal-depth overdraw and texture alpha sampling. Do not change authored art/XML absent that evidence.
