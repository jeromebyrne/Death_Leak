# Small-orb trail: implementation seams (2026-10-22)

Read-only seam audit for the next implementation worker. Source behavior and effect constants are in `NEXT_FOREST_EFFECT_CONTRACT_2026-10-22.md`; this file identifies where the port must connect them. No source, tests, builds, or display state were changed for this audit.

## Minimal ownership and call path

1. **Load/cache texture once per scene:** `port/game/LevelScene.cpp::Load` already uses its local `textures` map and `renderer.LoadTexture` for XML sprays (`:271-335`). Runtime trails are created later in `UpdateAuthoredOrbs`, which has no renderer argument. Cache `Game/Media/orb_shatter.png` during `Load` in a `LevelScene` texture member (or equivalent preloaded asset lookup); fail/diagnose deliberately if absent rather than opening a texture in a tick. Keep the XML spray admission filter unchanged. The asset exists via the source material `flame_orb`; do not add XML entries.
2. **Own trail per authored orb, without unstable pointers:** `SceneSprite` already has `authoredSmallOrb`, `orbTracking`, `collected`, and `persistentId` (`LevelScene.h`; `LevelScene.cpp:454-488`). Create one scene-owned runtime spray at the `!orb.orbTracking` → tracking transition in `UpdateAuthoredOrbs` (`:683-732`), after the hover calculation and strict radius check. Give the trail a stable orb key (prefer `persistentId`/a stable sprite index); do not store a raw pointer into `sprites_` or `particleSprays_`. The existing `continue` correctly defers movement until next tracking update. Do not attach to `UpdateSpawnedOrbs`: those smashable orbs are a separate path.
3. **Particle factory/update:** `ParticleSpray` is header-only (`port/game/ParticleSpray.h`). Its fields already represent texture, 15 particles, dimensions, depth, loop, age, fade, life-scale, speed, gravity, brightness and seeded private RNG. A focused radial factory in `LevelScene.cpp` (or a small helper adjacent to `ParticleSpray`) can initialize these without changing the authored XML parser. Unlike authored leaf/splash sprays, radial particles require independently signed X/Y direction samples; the existing XML parser's fixed `direction` cannot be reused as-is. Use the existing per-spray RNG for reproducibility, not a claimed Windows rand sequence. Preserve staggered lifetimes and spawn spread when constructing particles. Set `drawX/Y` at creation so a zero-delta diagnostic draw is defined.
4. **Attachment on recycle:** `ParticleSpray::Update` currently loops expired particles to immutable `startX/Y`. For a runtime trail only, have recycle take the *current* parent orb XY while leaving live particle positions alone. The source attach offset is zero, so parent orientation tracking does not rotate the emission point; no global sprite transform is needed. A per-spray attached-orb key plus current XY supplied before `Update`, or a narrow `Update(dt, optional parent position)` seam, avoids coupling the generic renderer to `SceneSprite`. Do not mutate every particle's start position each frame. Keep the authored spray update path identical.
5. **Scene update and painter merge:** `LevelScene::UpdateVisuals` (`:733+`) is the existing spray clock; `port/linux/main.cpp:690-694,1077` calls orb tracking, collection, then visual update. Tick attached trails there using the orb's post-motion XY; tick detached trails without a parent. Existing `LevelScene::Draw` (`:914-945,1023-1026`) interleaves `particleSprays_` with descending-depth sprites and dynamic items. Its `nextSpray` cursor **assumes a depth/order-sorted spray stream**. Blindly appending a runtime kOrb spray to `particleSprays_` after XML loading could put it behind lower-depth sprays and cause it to be drawn at the wrong painter position. Keep runtime sprays separately and merge sorted streams, or insert with the correct depth/order. Place trail at `Depth("kOrb")` (3250), with an explicit same-depth tie policy relative to its orb. The existing `ParticleSpray::Draw` world-to-screen/tint renderer is reusable; no new GPU primitive is required. Its current `drawX/Y` previous-step and one-time `warmed` behavior should be checked for runtime-spawn timing, not silently changed for existing authored sprays.
6. **Collection and scene replacement:** `CollectCurrencyOrbs` (`:581-593`) is the single live collection edge. On first collection, detach its trail, set `looping=false`, and leave active particles in scene state until natural expiry. Avoid clearing/drawing them immediately with the orb. `ApplyCollected` (`:595-597`) marks save-restored orbs; a fresh scene has no runtime trail, so it must not create one for a pre-collected orb. If applied to a live scene, it should also detach any extant trail for that orb. Prune a detached spray only when all particles are dead. `Load` clears scene-owned vectors (`:131`) and `main.cpp` replaces the scene on level transitions (`:612,966,996,1028`): those are hard scene boundaries, so old residuals should not cross levels. `SceneSprite` collection/draw filtering must not hide detached residual particles.

## Renderer reuse: exact limit

The existing CPU particle simulation and `ParticleSpray::Draw` cover the effect's simple textured quads, 2/3 world-to-backbuffer scale, brightness/alpha and painter depth. Reuse is therefore feasible with a radial initializer and attached-recycle seam. It is **not** plug-and-play: authored sprays are XML-filtered, fixed-direction, loaded before gameplay, and never attached. The current `Update` has no parent input and its loop restart uses original start XY. `Draw` has no spray-specific culling beyond per-quad viewport culling; the 3200×1200 bounds currently gate **update** in `UpdateVisuals`, while `Draw` renders every admitted spray. For a moving runtime emitter, update-zone checks must follow the current orb/emitter position, and a detached spray must continue ticking until expiry even if the orb is collected or no longer in update zone. Do not regress leaf/splash behavior to accommodate this.

## Focused deterministic tests, no GPU required

- Extend `port/tests/waterfall_orb_hover_tracking_test.cpp` or add a neighboring `orb_trail_test.cpp` with its `CaptureRenderer` pattern. Inspect loaded texture paths/IDs and captured sprite draws under `DEATHLEAK_RENDER_ONLY_XML_IDS` as appropriate; give runtime spray a diagnostic ID or targeted test accessor so the test can distinguish 15 particles from orb art. Test strict `130` equality, crossing just inside after hover, exactly one 15-particle trail, kOrb depth relative to adjacent drawn objects, asset ID, and no duplicate on repeated tracking ticks.
- With a fixed seed, assert per-particle directions have both signs, values lie in the source ranges, lifetimes are staggered, and initial spread/scale/fades/loop time match the contract. Compare two freshly loaded scenes with identical update sequences for deterministic particle state or captured draws; do not compare to Windows RNG samples.
- Advance more than `.35 s` while moving the orb: a recycled particle should originate near the *new* orb XY, while an unexpired particle retains its trajectory. Collect once, assert no further recycling, residual draw count monotonically reaches zero after the maximum remaining lifetime, and no trail on saved/reloaded collected orb. Also exercise `ApplyCollected` on a live tracking scene and `Load`/scene replacement to catch orphaned emitters.
- For a narrow unit test, direct `ParticleSpray` state inspection is better than asserting fragile pixel coordinates; keep one capture-render assertion for actual texture/tint/painter integration. The existing `port/Makefile` test-target pattern can register a new test when the exclusive build worker owns implementation.

## Blockers / decisions for implementation worker

- No preloaded orb-shatter texture handle or runtime spray container currently exists; both are required before spawning from `UpdateAuthoredOrbs`.
- Attachment recycling and draw ordering are behavioral gaps in the current reusable `ParticleSpray` path, not asset problems.
- Source-equivalent same-depth ordering and runtime warm-up timing require a deliberate choice verified by an isolated capture; the present port data structures do not encode a runtime GameObject insertion order for this trail. This does not block the CPU implementation or tests above.
