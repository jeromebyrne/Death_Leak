# Right-stick camera-offset implementation gate — static source audit, 2026-10-22

Scope: read-only Windows-to-Linux plumbing audit following `STRAFE_AIM_LINE_SOURCE_CONTRACT_2026-10-22.md`. This report adds the frame-order and vertical-axis constraints for a future patch. No source edit, build, GPU/display use, or parity result.

## Exact source path and timing

- Windows `Game/src/Core/GamePad.cpp:15-23,26-41` polls XInput and zeroes a failed state; `Game/src/InputManager.cpp:127-143` runs gamepad processing only for a connected, controllable living player. `:556-589` orders left/right movement, aim/Y-offset, primary fire, then strafe/X-offset. The original target offset is loaded from XML and copied at `Game/src/LevelProperties.cpp:24-36`; loading applies it to `Camera2D` at `:43-53`.
- Aim is active if **either** raw right axis has absolute value strictly greater than XInput right-thumb deadzone (8689), not by radial magnitude. `Game/src/InputManager.cpp:374-395` normalizes aim for line/fire, but computes camera Y from the **raw** RY divided by signed-short max 32767 (`:751-754`): `originalY + 300 * RY/32767` (`:14-15`). Neutral aim resets Y; subsequent `ProcessStrafing_gamepad` resets **both** offsets on neutral (`:449-459`). On active aim, `:462-472` returns early for rolling, fall, or melee, leaving X at its prior target while aim/Y can still update; otherwise `:474-503` sets X to `originalX + 450 * RX/32767`, even if no opposed-stick strafe is recognized. Thus camera offset is an aim effect, **not** conditional on `mIsStrafing` or visible StrafeBack/Forward animation. A Y-only stick re-establishes original X; an X-only stick re-establishes original Y.
- Source follow happens before gameplay input in the same `Game::Update`: `Game/src/Game.cpp:154-163` calls `FollowTargetObjectWithLag`; gameplay input runs after object/collision/post-update at `:175-215`. `Game/src/Core/Camera2D.cpp:173-229` consumes its stored target offset, applies zoom and per-axis lag, then `Game.cpp:162` clamps. Consequently right-stick target offsets written by input in update N influence camera follow in update **N+1** (barring a pause/skip), while draw after update N can already see the updated aim-line orientation. A current-stick-before-follow patch would introduce a one-update camera lead. The existing port `port/linux/main.cpp:670-684` follows before `motion.Update` and input/combat, consistent with the source's preceding camera follow, but currently consumes fixed `scene.CameraOffsetX/Y()` (`:678,682`).
- Windows disconnected/keyboard path does **not** call `ProcessStrafing_gamepad` (`InputManager.cpp:134-143`), so neutral reset is not automatically invoked on disconnect; a previous target offset may persist until gamepad input or level load. That is source behavior, not a desirable new sticky default. A port policy that resets on disconnect for usability must be named as an intentional divergence; test it separately from neutral-stick source parity.

## Current Linux seam and safe patch shape

- SDL opens/handles gamepad hot-plug in `port/linux/SDLRenderer.cpp:147,530-542`; its `ControllerAxes()` returns raw leftX, rightX, **rightY** or disconnected zeros at `:563-568`, through the backend-neutral `ControllerSticks`/virtual in `port/render/Renderer.h:24-27,77`. `port/linux/main.cpp:452-455` snapshots once after polling. Current uncommitted `main.cpp` changes pass that snapshot only to `ResolvePlayerStrafeVisual` at `:688-693`, whose strict 8689 test and body-facing output are at `port/game/LevelScene.h:77-92`; the per-frame `UpdatePlayerVisual` call is `main.cpp:1092-1094`. Keep that in-flight body patch and add camera target handling beside it; do not reinterpret `strafeVisual.active` as camera eligibility.
- Convert SDL's screen-down-positive rightY to Windows/XInput world-up-positive RY **once**, at the input normalization seam, before both camera-Y and future aim-line-angle consumers. The current raw `ControllerAxes()` returns SDL `RIGHTY` without inversion (`SDLRenderer.cpp:565-567`). X can pass through unchanged. Preserve the -32768 asymmetry of division by 32767 (a fully negative axis can be slightly below -1); clamp only if a documented source/platform conversion requires it. Do not normalize the `(RX,RY)` vector for camera offsets: source normalization belongs to aim direction, not target-offset magnitude.
- Minimal state is two **mutable effective target offsets** initialized from `scene.CameraOffsetX/Y()` on load/restart/level transition, distinct from the immutable authored offsets held by `LevelScene` (`port/game/LevelScene.cpp:143-149`; getters `LevelScene.h:114-120`). Follow at `main.cpp:676-683` consumes the effective stored offsets; after the current frame's eligible gamepad input, update that state with the strict per-axis/neutral/gate rules above for next frame. Reset from the new scene's authored values at every `scene = ...` replacement, not just initial launch (restart example `main.cpp:616-632`). Do not mutate `LevelScene`'s authored fields or change follow lag/clamp, scripted-camera override (`main.cpp:685-687`), camera zoom, or renderer placement. If headless scripted input remains controller-free, retain its fixed-offset behavior deliberately.
- Gate input processing on gameplay-active/controllable conditions, rather than applying offsets from a top-of-loop snapshot during modal/menu/death/restart; source checks controllability (`InputManager.cpp:127-143`) and skips gameplay input when paused (`Game.cpp:204-215`). Use existing scene-transition and pause decisions in `main`, and make the update-order explicit in code. Distinguish zero-valued connected axes (neutral reset) from disconnected state (source no gamepad camera update). If intentional disconnect reset is chosen, document and test it as divergence.

## Renderer and fractional-UV interaction

- Camera X/Y are used to derive player/aim destinations and parallax placement/phase in `port/game/LevelScene.cpp:1215-1251`; `draw.uvShiftX = cameraX * multiplier * flip sign` and `uvShiftY = -cameraY * multiplier` at `:1245-1251`. A right-stick camera move therefore changes both sprite destination and float UV phase. Do **not** compensate by moving the line/body or reversing UV signs. The aim line uses world player anchor at `:1217-1222`, so camera movement already shifts it in screen space via `:1242-1244`.
- Current `port/linux/SDLRenderer.cpp:246-261` uses integer UV-wrap segments, quantizing subtexel camera phase; `port/linux/ParallaxUV.h:11-20` and `:25-63` define the separate float-corner/dispatch gate for a future direct GL route. The existing `FRACTIONAL_PARALLAX_UV_IMPLEMENTATION_PLAN_2026-10-22.md` owns that renderer change. A camera-offset test should inspect the **emitted float** `render::Sprite::uvShiftX/Y` (`port/render/Renderer.h:46-59`), not infer success from unchanged pixels within one integer cut. Recheck worktree ownership before touching `SDLRenderer.cpp` or integration tests; the current uncommitted renderer/main/header and integration-test changes are shared work (`git status --short`), and this audit changes none of them.

## Minimal CPU/test gate for implementer

1. Extract or expose a pure input-to-target-offset step with authored original `(ox,oy)`, previous effective `(tx,ty)`, converted raw RX/RY, connected/eligible and rolling/fall/melee flags. Test exactly 8689 vs 8690, X-only ±9000, Y-only ±9000, diagonals, neutral reset of both, and active gated X-hold/Y-update. Assert formulas with `/32767`, not normalized-aim components. Include the SDL down→world-up conversion test. Declare disconnected-state policy explicitly.
2. Test two frame updates at fixed player XY, with target state initially authored. Frame N follows with old offset and then accepts stick; frame N+1 follows with new offset, preserving zoom, per-axis lag, follow flags and clamp order. On neutral, the first neutral-frame follow still uses prior offset; the next uses authored offset. Use a non-clamped fixture to assert numerical interpolation, plus one bound fixture to assert clamp. A one-frame immediate 450-pixel jump is **not** expected.
3. In a scene render-spy, drive the resulting camera XY into `LevelScene::Draw`, assert one parallax ID's emitted destination and float `uvShiftX/Y` change with the camera, and separately assert aim-line screen destination moves only through the common camera transform. `port/tests/strafe_body_cpu_test.cpp:1-66,181-201` currently bypasses SDL/main and preserves the wrong aim-line attachment; extending it alone cannot prove SDL axis sign or frame timing. Add a thin injectable controller/follow integration seam or a narrowly scoped main-loop harness for that plumbing. Leave GPU pixel validation and the fractional UV renderer implementation to their owner.

Verdict: the missing code is stateful raw right-stick target-offset update **after** each source-equivalent follow, then consumption on the next follow, with SDL rightY sign conversion. It must be independent of strafe animation and fractional-UV rendering. Static audit only; no runtime parity claim.
