# Waterfall-top ID59 prior-update followed-X implementation gate — 2026-10-23

## Verdict and scope

**A narrowly scoped Linux change is justified for fidelity to the checked-in Windows source:** after each eligible ID59 update, its bound world X is the followed X stored *before* that update; the view and X UV use the current camera X. The current Linux draw instead uses current X for both world and UV. This is a source-level implementation gate, **not** proof of the shipped Windows binary or a matched-pixel visual-acceptance gate. The companion `WATERFALL_ID59_WINDOWS_TIMING_SOURCE_GATE_2026-10-23.md` establishes the update→matrix→follow assignment order and normal one-update/one-render loop. The previous `WATERFALL_ID59_CURRENT_GPU_GATE_2026-10-23.md` demonstrates visible, low-contrast effect but used preceding *rendered-frame* X only as a proxy. No code, build, GPU capture, shared checkpoint, or worker-owned renderer file is changed by this report.

## State lifetime and exceptional schedules

Let `P` be the source-style stored position and `W` the cached matrix X. On an eligible update with current camera `C`, execute `W ← P; P ← C`; draw uses `W - C` for placement and `C` for UV. Thus update 1 uses authored `P0`, update 2 uses `C1`, update 3 uses `C2`. With two updates before one draw, the world uses the immediately prior **update's** X, not a prior rendered-frame X. With repeated draws and no update, `W` is unchanged while current view/UV may change. A draw must never consume or rotate this cache.

In the Linux modal path `main.cpp:1108-1113`, `UpdateVisuals(..., objectsPaused)` is called but returns at `LevelScene.cpp:835`; the patch must live after that return. Both `P` and `W` freeze through paper/upgrade modal frames, including repeated draws. On resume, the first eligible update binds the last stored `P`, then stores the resumed camera X. This mirrors the source manager's `if (!paused)` gate (`GameObjectManager.cpp:205-221`); the source damage-pause gate can likewise suppress object updates (`Game.cpp:167-180`). Do not substitute current camera X merely because rendering continues. `main.cpp:662-673` normally advances camera before scene-object updates; `:1109` invokes them before `:1191` draw. If a camera is externally changed while object updates are suppressed, the frozen matrix and current view/UV can diverge; that is consistent with the source order, not a cache reset trigger.

`LevelScene::Load` clears/recreates `sprites_` (`LevelScene.cpp:125-137,393-405,486-487`), and main replaces the scene with `std::move(nextScene)` on transitions/restarts (`main.cpp:632-640,991-1007,1055-1069`). The cache must be per new sprite, initialized to that destination level's authored X, with no cross-scene inheritance. The door path `main.cpp:1009` may skip that frame's draw; the later first update should still use the fresh authored X. A failed load should leave the current scene/cache untouched because replacement occurs only on success. Do not tie this cache to `pendingModifiedDelta_`/`previousRenderedModifiedDelta_` (`LevelScene.h:229-232`): those serve Y autoscroll timing and have different lifetime.

Resume with active update at 1650: destination world X **1620** (the position stored at last active update), UV **1650**. This distinguishes source-style update history from preceding-draw history.

## Risks and decision boundary

- The source proves checked-in code's normal active schedule; there is no original executable, synchronized Windows trace, or matched frame in this repository. It warrants a scoped source-parity patch, not a claim of shipped-binary/pixel parity. If release policy requires binary proof, hold *release acceptance*, not this implementation design.
- A previous-render-frame cache can accidentally agree with normal one-update/one-render play but fails skipped-update, multi-update, pause, first-frame, and transition cases. A draw-time mutation can also produce order-dependent repeated draws.
- Broadening to all follow-camera layers without checking eligibility could alter weather/other layers; changing `object.x`-based culling or UV to use W would introduce unrelated differences. Keep the correction restricted to ID59 world placement initially.
- This candidate is visually subtle at the measured moving frame and can be masked by overdraw; acceptance must inspect isolated and full frames and command-state logs, not rely on visual impression alone.

**Handoff:** source supports the ID59 prior-**update** world-X patch at the `SceneSprite`/`UpdateVisuals`/`Draw` seam, with current camera UV/view. Implement only when the exclusive ID46 lane is free; no implementation or verification was performed in this read-only lane.
