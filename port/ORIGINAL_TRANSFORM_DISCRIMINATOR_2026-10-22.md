# Original Windows transform discriminator (2026-10-22)

## Bounded finding

There is a **temporal transform-order discriminator** for the foreground `ParallaxLayer` sprites, separate from the already-audited ordinary-sprite `T*S*R` versus SDL centered-transform question. In Windows, `ParallaxLayer::Update` first calls `Sprite::Update`, **then** assigns its followed camera X/Y to `m_position` (`Game/src/GameObjects/ParallaxLayer.cpp:26-35`). `Sprite::Update` calls `DrawableObject::Update` (`Game/src/GameObjects/Sprite.cpp:358-366`), which calls `GameObject::Update` (`Game/src/GameObjects/DrawableObject.cpp:41-44`); that method constructs the world matrix from the **pre-follow** position (`Game/src/GameObjects/GameObject.cpp:202-210`). `ParallaxLayer::Draw` independently reads the current camera and writes UV phase from it (`Game/src/GameObjects/ParallaxLayer.cpp:37-83`); `Sprite::Draw_effectLightTexture` uploads the already-computed `m_world` (`Game/src/GameObjects/Sprite.cpp:626-637`). The manager performs a single object-update pass and a separate draw pass (`Game/src/GameObjects/GameObjectManager.cpp:221-247,302-330`); its `PostUpdate` does not rebuild matrices (`:260-280`). Thus the source path can render a followed quad using the prior update's camera-follow position while sampling texture UVs at the current camera coordinate. This is a source-code implication, **not a measured Windows-frame claim**; global camera update timing must be logged to confirm which camera values occur at each call.

The port instead chooses the current camera X directly as the followed layer's world X during the draw and projects it in the same call (`port/game/LevelScene.cpp:805-810,830-839`). It has no comparable cached-world-versus-current-UV separation. This matters for a moving-camera frame, especially a camera jump or acceleration, and can make a foreground texture landmark appear to travel at a different instantaneous speed even when the now-corrected UV phase coefficient is identical. It does **not** establish a persistent parallax rate error: at constant velocity the old-position term is only a one-update offset; after the camera stops it should disappear on the next update. The existing `RAFT_EXIT_PARALLAX_SOURCE_AUDIT_2026-10-22.md` and commits `dcf395e`, `00612aa` already address XML flip identities, ordinary transform composition, and UV-phase direction; this report does not reopen those findings or propose XML/art edits.

The relevant forest-1 IDs are foreground `ParallaxLayer` 37/40 (`Game/XmlFiles/levels/forest_exploration_1.xml:612-635,666-689`), which follow camera X and use U coefficient 0.000690. Raft 11/57/58 and shaft 15 are ordinary sprites, so the follow-position lag does **not** explain their orientation; their direct discriminator remains the original Windows final world matrix/actual transformed corners versus the port's centered SDL copy, as set out in the prior audit. The static Steam forest screenshot is only a composition reference (`port/FOREST_REFERENCE_AUDIT.md`); it carries no camera time series and cannot discriminate the transient.

## Feasible matched capture

On an instrumented original Windows build, freeze gameplay/animations and log, per update/draw, frame index, camera XY, IDs 37/40 `m_position` **before and after** `ParallaxLayer::Update`, `m_world` translation at draw, and left/right U coordinates. Also log final `m_world` and transformed quad center/corners for ordinary IDs 11, 57, 58, 15. Capture lossless PNGs at (A) a camera held steady for at least two updates, (B) the **first** draw after a known +100-world-X camera step, and (C) one more draw held at the new coordinate, with fixed viewport/zoom. Repeat those exact camera states and frame cadence in Linux with the same IDs isolated, recording port destination centers/UV phase; compare ID37/40 quad edges separately from a recognizable texture landmark. If the Windows log has one-update follow lag, expect a transient quad displacement at B that clears at C, while UV phase changes already at B. If Windows logs show same-frame world translation, reject this temporal explanation and use the logged ordinary-sprite matrices/corners to settle the raft/shaft transform question. A screenshot/trailer alone is insufficient for either verdict.
