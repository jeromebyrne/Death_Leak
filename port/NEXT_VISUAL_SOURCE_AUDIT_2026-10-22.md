# Next source-proven visual gap after firing arm — player ground shadow (2026-10-22)

## Verdict and priority

At HEAD `e676e30`, the Linux port omits the Windows player's runtime-created **ground shadow**. This is the next bounded, source-proven unimplemented forest-1 visual after the separately assigned firing-arm overlay: it is attached to the focal character and present whenever the Windows player is on solid ground, rather than only during a short attack. Its actual per-pixel effect is subtle (source texture alpha peaks at 63/255) and local; it cannot explain the broad ID37 dark band, ID15 pale shaft, or overall unmatched Steam color. This is a source semantic finding, not a measured Windows-versus-Linux screenshot difference.

## Exact evidence

- Forest-1 authors Player ID2 at `kPlayer` with a 181.393768 × 215.352036 body (`Game/XmlFiles/levels/forest_exploration_1.xml:35-47`). The shadow is **not** an XML object: after loading/initializing objects, Windows `GameObjectManager::LoadLevel` unconditionally calls `m_player->AddShadowSprite()` when a player exists (`Game/src/GameObjects/GameObjectManager.cpp:438-446`), before depth ordering (`:448`).
- `Character::AddShadowSprite` constructs a non-native 200 × 128 Sprite using `Media\\characters\\player\\shadow.png`, attaches it to the player with `(0,-150)` world-unit offset without tracking parent orientation, places it at `kGround`, and adds it to the object manager (`Game/src/GameObjects/Character.cpp:1856-1886`). Windows `Character::Update` sets its alpha to 1 on solid surface and 0 otherwise (`:195-226`); manager drawing skips alpha-zero objects and draws the rest in its ordered list (`GameObjectManager.cpp:302-330`). Thus this is a ground-conditional, separate-depth sprite, **not** an always-visible overlay or part of the body texture.
- The shipped `Game/Media/characters/player/shadow.png` is 128 × 128 RGBA. Read-only pixel inspection found an alpha bounding box `(0,71)-(128,128)`, 6,523 nonzero-alpha texels, maximum alpha 63; center `(64,100)` is black at alpha 42. At the port's 2/3 world-to-screen scale, its full destination is approximately 133 × 85 px, but opaque/visible footprint is much smaller. No GPU/image capture was made.
- The Linux loader only creates `SceneSprite`s for XML objects with a texture and a positive rectangle, then sorts those by depth (`port/game/LevelScene.cpp:334-486`). It loads player body animation frames but no runtime shadow (`:359-390`), and `LevelScene::Draw` issues the player body as a single draw from that list (`:729-785`). A targeted search of `port/game` and `port/linux` found no `shadow.png` reference or equivalent player-shadow draw. The existing `PlayerMotion::Grounded()` state is available (`port/game/PlayerMotion.h:24`), and `main.cpp:1053-1056` already passes it to the visual update; it is not currently used for a shadow.
- Existing audits address ID46 `leaves_shadow.png` (a different, XML-authored forest layer), ID37, ID15, particles, fog, foliage, UV, and the firing arm. None implements or reports this runtime player shadow. The latest active-gameplay route (`port/POST_FOLIAGE_GAMEPLAY_REVIEW_2026-10-22.md`) contains player traversal, but without matched Windows state it does not measure the shadow's image contribution.

## Bounded implementation suggestion

Load the existing player shadow texture once when a level with Player ID2 loads. Represent it as a separate ground-depth draw at `(playerX, playerY-150)`, dimensions 200 × 128 world units, using the existing 2/3 projection, source-alpha blending and sepia pipeline. Drive its visibility from the current grounded/on-solid-surface state, matching Windows alpha 1 versus 0; do not fade continuously or tie it to firing. Place it in the `kGround` painter order, not immediately atop the `kPlayer` body, preserving other XML ground objects' stable order as closely as the original dynamic insertion/sort permits. Do not modify `leaves_shadow.png`, XML IDs, ID37/ID15, or global blend settings. A deterministic grounded-versus-airborne same-camera crop can verify the local effect after implementation; exact Windows parity requires a matched original frame and grounded state.

## Uncertainty / exclusion

The source proves creation, depth, offset, visibility condition and missing port representation; it does **not** prove a particular visible delta in the existing Linux captures, which are unmatched with Windows and may occlude the small dark mark under other foreground layers. The alternative missing runtime aim line is a narrower event-driven graphic: Windows creates it at 400 × 400 but initializes alpha to zero (`Player.cpp:634-658`), whereas the ground shadow accompanies grounded traversal. This priority is therefore based on expected screen-time around the focal player, not measured pixel impact. No build, GPU use, capture, source edit, status-file edit, or commit was performed.
