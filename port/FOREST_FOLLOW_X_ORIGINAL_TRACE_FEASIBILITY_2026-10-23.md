# Forest-1 follow-X original trace feasibility — 2026-10-23

## Decision

**The same-history original-Windows moving→held trace is feasible as an instrumented Windows source-build experiment, but cannot be executed from this checkout/shell now.** The first hard gate is a runnable Windows/D3D10 host with VS v143, Windows SDK 10.0.19041.0 and legacy June 2010 DirectX/D3DX dependencies (or a separately acquired runnable shipped binary plus a validated debugger/hook). No local original `.exe`/`.pdb`, Windows runner/toolchain, or saved same-frame Windows transform trace was found. The checked-in `.sln`/`.vcxproj`, XML, textures, DLLs and Steamworks libraries are build/runtime *inputs*, not evidence of a successful Windows run. This leaves the `FOREST1_NEXT_RENDER_CONTRACT_2026-10-23.md` gate open; do not patch follow-X or claim pixel parity from the source prediction alone.

This is a narrow trace gate, not another visual/source inventory. Earlier `FOREST_FOLLOW_X_WINDOWS_TRACE_GATE_2026-10-22.md` and `WINDOWS_FOREST_RUNTIME_TRACE_ACTION_2026-10-22.md` establish the source hypothesis and acquisition route. My read-only recheck found no new local execution path: `find /srv/openclaw/workspace/death_leak_analysis` for `.exe`/`.pdb` and Windows-trace JSON/CSV names returned none; `command -v` found no Wine/wineserver, MSBuild, dotnet, clang-cl, MinGW C++ or PowerShell. `Game/steam_api64.dll/.lib`, irrKlang DLLs, `D3DX10d_43.dll`, `Game/XmlFiles/levels/forest_exploration_1.xml`, and both ID37/40 PNGs are present. The project still hard-codes a developer-specific Steam SDK include/lib location in its x64 configuration, so even a Windows build requires dependency/path validation. I did not attempt one.

## Exact next executable experiment, once that gate is met

1. On an authorized Windows/D3D10 host, first verify a **Debug x64 source build launches forest-1** (quick-play `a. Forest Exploration 1`) with this checkout's XML/assets. Use `DeathLeak.sln`/`Game/Game.vcxproj`, VS v143, SDK 10.0.19041.0, June 2010 D3DX, irrKlang and bundled Steamworks x64 import library; correct the stale Steam paths in an isolated copy/build configuration. Record source revision and SHA-256 of EXE, XML, `shrubbery.png`, `trees_top.png`. This is an *original renderer source build*, not the shipped Steam executable. If a shipped EXE is chosen instead, first prove it launches and that a debugger/hook can obtain the same internal fields; a backbuffer-only frame capture is insufficient.
2. In that isolated Windows build, assign one monotonically increasing render ordinal at the `Update`→`Render`→`Present` loop (`Game/src/program.cpp:168-177`) and record whether an eligible object update occurred (pause/damage pause can skip it). For IDs **37 and 40**, log at `ParallaxLayer::Update` entry and immediately after `Sprite::Update`: entering position X and cached World translation (`m_world._41/_42`); then log post-follow position X. At `GameObjectManager::Draw` log drawable/alpha/in-view gate and actual call to `Draw`, because culling tests the **post-follow object position**, while the World may still be stale. At `ParallaxLayer::Draw`, after UV assignment and before `Sprite::Draw`, log camera X, effective `Camera2D::View()`/projection, World translation, U0/U1 (and effect path), tying all rows to the render ordinal. The actual light-texture submission calls `SetWorld((float*)&m_world)` in `Sprite.cpp:626-637`; verify that value, not a reconstructed position. Optionally capture a lossless native-size backbuffer *after* `Render()` and *before* `Present()` (`program.cpp:295-322`), with identical ordinal/hash/dimensions/stage, if image-parity judgment is intended.
3. Drive **one uninterrupted forest-1 history**: hold the camera through at least two eligible updates/draws, move it so recorded camera X changes while each ID actually draws, then stop and hold through at least one more eligible update/draw. Record the actual camera X and full view per row; `1000→1008→1008` is only a diagnostic example, not an asserted reachable sequence. Keep level/session, viewport, asset hashes, player state and pause/shake status constant or record them. Do not splice independently loaded stills. Camera shake can separate position from the view matrix (`Camera2D.cpp:120-160`), and fresh-load first draw may retain authored X `1316.985352`, so neither is an ordinary moving sample.
4. Accept only rows that pair update ordinal, draw ordinal, camera X, entry/post-follow X, submitted World translation, U0/U1 and draw/cull outcome for both IDs. For normal unflipped IDs 37/40 with multiplier `.000690`, source predicts moving draw World X = **entering** position, post-follow X = current camera X, and `U1 = -0.000690 × current camera X`, `U0 = U1 + 1`; next held eligible update should make World X converge to camera X. If measured submitted World instead follows current X, reject this lag candidate. A trace proves the runtime transform contract; only same-history, lossless Windows/Linux image crops can establish perceptual benefit or pixel parity.
