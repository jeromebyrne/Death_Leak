## Exact insertion map

1. **State and every reset.** Construct `deathleak::game::RightStickCameraTarget` from `scene.CameraOffsetX(), scene.CameraOffsetY()` after the initial `scene.Load`/scene setup (`port/linux/main.cpp:307-323`), before the frame loop. Reinitialize it immediately after each successful scene replacement: menu New Game `scene = std::move(fresh)` (:537); death restart `scene = std::move(nextScene)` (:626); door transition (:984); boat transition (:1014); trigger transition (:1046). Also reset when story completion assigns `scene = LevelScene{}` (:1070), so a later menu New Game cannot inherit a prior target. Do **not** reset on failed loads or ordinary per-frame updates. The initial `--play`/`--load-save`/`--level-preview` paths all pass through the initial load; `--start-encounter`/`--start-hazard` reposition the player/camera but do not replace the scene or its authored offsets (:336-345). Preserve immutable authored `LevelScene` offsets.
2. **Follow site.** Replace only the manual clamp/follow/clamp block at :655-684 with `FollowCameraWithTarget({cameraX, cameraY, worldX, worldY, scene.CameraZoom(), scene.CameraLagX(), scene.CameraLagY(), scene.CameraFollowX(), scene.CameraFollowY(), combat.EnemyCount()!=0, scene.HasCameraBounds(), scene.CameraBoundLeft(), scene.CameraBoundRight(), scene.CameraBoundTop(), scene.CameraBoundBottom()}, target, cameraX, cameraY)` (use the actual aggregate field order in `LevelScene.h:107-114`). This helper preserves the existing unzoomed 960/540 boundary checks, Y-before-X clamp, flags, zoom, enemy X lag, and before/after clamping. Keep scripted-camera override **after** it (:685-687). Follow must consume the target stored from a prior eligible input update, not the current sampled stick. Windows `Game.cpp:154-163,175-215` likewise follows before object/collision/input processing.
3. **Input/update site.** `controllerSticks` is sampled after `PollQuit` at :454 via raw SDL axes (`SDLRenderer.cpp:563-568`). Call `target.Update(controllerSticks, eligible, motion.Rolling(), falling, combat.MeleeActive())` only inside the live, living gameplay branch beginning :633, **after** the follow and preferably after `motion.Update` (:689) and `combat.Update` (:713), before later door/boat/trigger replacements; any subsequent successful scene replacement must reset it again. This keeps the current update's camera fixed and writes next update's target. Do not call from the menu branch (:470), empty-play branch (:558), final-scene frozen branch (:565-579), modal branches (:580-605), or dead/restart branch (:609-633). `eligible` must represent an active, controllable, living player and connected gamepad; for `--script`/simulation paths retain controller-free fixed-offset behavior by skipping the update. Do not gate on `strafeVisual.active`: Windows aim/Y then strafe/X writes offsets even without opposed-stick strafe (`InputManager.cpp:556-589,449-503`). The helper itself handles disconnected/neutral distinction and SDL RIGHTY inversion; do not invert Y again. Aim-line/body visual processing at :691-693 stays independent.
4. **Fall gate is not yet available.** Windows X-hold gate is `JustFellFromLargeDistance() || JustFellFromShortDistance()` (`InputManager.cpp:467-472`), not generic `!motion.Grounded()`, `!wasGrounded && motion.Grounded()`, jump, or downward dash. Windows sets those flags on impact after >300/<700 or >=700 world-unit drops and clears them after impact animations; roll can avoid the delay (`Character.cpp:25-26,340-376,750-785`). The current `PlayerMotion.h:17-42` exposes no equivalent impact-recovery flag/duration; `main.cpp` only computes a landing edge for `ResolvePlayerStrafeVisual` (:688-693). A source-faithful fall argument therefore needs a separate motion/animation contract from its owner. Passing `false` would be a documented temporary gap (X would move during impact recovery); using the landing edge would incorrectly gate only one tick and also gate ordinary landings. Do not claim full fall parity until resolved.
