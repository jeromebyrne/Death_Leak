# Forest-1 follow-X draw-state gate (ID37/40) — 2026-10-22

## Decision

**The source predicts a transient destination-X difference, but the available evidence does not justify a visual correction now.** In an ordinary visible draw after one object update, original Windows uses each layer's X *entering* that update for its cached world matrix and the current draw camera X for texture U. Linux currently uses current camera X for both destination and U. At a +8-world-unit camera step, that is a −5.333333-pixel original-minus-Linux destination shift at 1280×720/2⁄3 scale; after another update with camera held, it is zero. This is source-path arithmetic, not a measured original-Windows frame. The current-head active clip and Steam screenshot 14 do not match camera/history, HUD, effects or compression, so neither proves that changing ID37/40 would improve the visible bridge/foreground. Keep current Linux rendering pending the original-runtime gate below.

Let P be the X followed into the previous *object update* and C the camera X for the present ordinary update/draw; assume source and Linux share the same view transform, visibility and one update per draw. ## Qualification and implementation seam, if promoted

The matrix is the X entering the most recent **eligible object update**, not necessarily the preceding video frame's camera. First draw after load can inherit authored x=1316.985352; a skipped update can keep the matrix stale for longer; a draw without an update must not mutate it. Original draw culling can use post-follow position (`GameObjectManager.cpp:302-330`), and camera shake/view-matrix timing can complicate a captured pixel offset. A trace therefore needs actual view matrix, update and draw indices, culling result and matrix X. On fresh scene load, do not inherit prior-level history. These are boundaries to test, not reasons to add a generalized camera-lag effect.

The smallest port seam is per-`SceneSprite` follow-X state, initialized on `LevelScene::Load` (which clears/rebuilds `sprites_` at `LevelScene.cpp:132,569`) and advanced once on each eligible, unpaused `LevelScene::UpdateVisuals` at `LevelScene.cpp:825` (called from `port/linux/main.cpp:1100`). For IDs 37/40—or the exact predicate `parallaxLayer && followCameraX` if audited for other levels—cache the entering followed X as the draw destination X, then assign current camera X as the next followed X. `LevelScene::Draw` is `const` and should only read that cached destination at its `worldX` selection (`LevelScene.cpp:1220-1222`); leave `draw.uvShiftX` bound to its current draw `cameraX` (`:1251`), and leave Y, opacity, depth, repeat span, texture, other sprites and active gameplay edits untouched. This is a conditional implementable patch shape, **not** an authorization to patch yet. Decide explicitly whether first draw emulates authored-X first-update jump or seeds from camera as a Linux normalization; do not accidentally define it by an uninitialized field.
