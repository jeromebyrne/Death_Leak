# Forest→Waterfall loading icon applicability — read-only source audit

**Verdict:** The Windows UI renderer *can* draw a queued interactable icon over `gameloading`, but the authored Forest→Waterfall transition supplies no such icon on ordinary traversal, including the destination fade-out. This is a general composition-order difference, **not a source-supported defect for this route**. No Linux icon-over-loading patch is warranted for this transition.

- Windows `UIManager::Draw()` draws every screen first, then `mInteractableIconsToDraw`, then clears that queue each frame (`Game/src/UI/UIManager.cpp:174-180,192-234`). `program.cpp:287-292,293-317` updates before rendering. Thus only an icon queued by an object update for the current frame can cover the black splash. `GameObject::UpdateInteractable()` queues an icon only if an interactable object overlaps the player and passes `CanInteract()` (`Game/src/GameObjects/GameObject.cpp:234-237,240-266,303-314`); interactability defaults false (`Game/src/GameObjects/GameObject.h:15-29`).
- The Forest exit is `LevelTrigger` id 13 at x=3410.985, width=400, leading to `waterfall_top.xml` (`Game/XmlFiles/levels/forest_exploration_1.xml:214-220`). `LevelTrigger::Update()` merely requests a deferred level switch on player overlap (`Game/src/GameObjects/LevelTrigger.cpp:21-40`); it never sets interactability. The only authored interactable-class object in this Forest XML is `DojoScrollPickup` id 117, centered x=1167.985, width=170.515 (`forest_exploration_1.xml:1614-1630`; `Game/src/GameObjects/DojoScrollPickup.cpp:57-68`). Its right edge is ~1253; the trigger's left edge is ~3211, a ~1958-unit gap. The player's authored sprite width is 181.394 (`forest_exploration_1.xml:33-35`), so it cannot overlap both regions in the same frame. The icon queue is drained on every render, so an earlier pickup prompt cannot persist into the exit fade.
- On the destination side, the authored `waterfall_top.xml` contains no `Door`, `Boat`, `Pickup`, `DojoScrollPickup`, or `HealthDevil` objects (XML element inventory); its Forest entry is `LevelEntry` id 5 (`Game/XmlFiles/levels/waterfall_top.xml`, entry with `level_came_from="XmlFiles\\levels\\forest_exploration_1.xml"`). The Windows fade-out therefore also has no authored interactable icon source. The Linux path draws its loading sprite after HUD and has no later icon pass (`port/linux/main.cpp:1513-1547`), which is acceptable for this route.

**Boundary:** This is static source/XML evidence, not a Windows runtime assertion; injected/dynamically spawned interactables or altered level data are outside the verdict. **Next bounded action:** Let the loading-fade owner finish timing/physical-GPU validation without composition edits. Only if a matched Windows Forest→Waterfall loading frame actually shows an icon should an owner instrument the per-frame queue and consider a route-specific after-splash icon pass.
