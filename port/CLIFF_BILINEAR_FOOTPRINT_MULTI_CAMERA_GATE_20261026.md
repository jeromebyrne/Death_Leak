## Source-coordinate footprint oracle

The source PNG crop is byte-verified at the atlas rectangle, but RGBA reconstruction does not prove sampled pixels. The current SDL virtual path intersects an authored source rect with a trimmed region, rescales the destination quad, shifts its rotation center and sends a new integer page source rect to `SDL_RenderCopyExF`. That changes normalized UV endpoints and GL float interpolation. In a one-dimensional float32 center-sample model, dedicated source coordinate `u=(i+0.5)/originalWidth` and page coordinate `u'=(rectX+(i-offsetX)+0.5)/pageWidth` are mathematically equivalent under exact arithmetic. Quantized endpoint/interpolation arithmetic is not: maximum calculated center displacement in texels (X,Y) is `cave_underlay` (0.000244,0.000122), `mill` (0.000305,0.000305), `windmill_blades` (0.000244,0.000244), and page-1 `cave_overlay` (0.000244,0.000153). A bilinear footprint can assign different weights when these centers shift. This is a *mechanism bound*, not a proof that every differing final pixel is caused by UV rounding; rotated destination geometry, trim boundary and SDL vertex precision remain possible additional causes. No arbitrary UV bias/filter downgrade has been accepted as a fix.

The proposed source-coordinate-preserving method is therefore **not proven pixel-safe**. The earlier two-page candidate's actual warm active cliff frame saved only one `glDrawArrays` and one `glBindTexture` (37/114 to 36/113), with overlapping query-off preview timing and invalid pixels. No fresh B timing, call or live-VRAM acceptance is justified for a failing visual candidate. Prior raw RGBA allocation proxy was -1,797,088 bytes if all six dedicated copies disappeared; it remains hypothetical and cannot offset failed pixels. No runtime atlas family, batch or production mapping was retained.
