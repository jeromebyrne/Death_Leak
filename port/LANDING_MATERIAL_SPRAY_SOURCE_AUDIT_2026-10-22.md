# Landing material spray: bounded source audit (2026-10-22)

## Finding and boundary

The original Windows `Character` emits a **five-particle** material spray after a solid-line landing whose tracked drop is **[300, 700)** world units, or a distinct **ten-particle** spray for a drop **>=700**. The Linux `PlayerMotion` currently resolves ground contact but has no landing-apex/drop-distance state or landing-emitter call. This is the next *conditional* active-play material effect after takeoff, not a replacement for the takeoff slice already scoped in `port/NEXT_FOREST_EFFECT_POST_FOOTSTEP_2026-10-22.md`. Inspection was source-only; no matched Windows/Linux frame, build, or GPU test establishes a pixel delta.

This audit inspected `b1f8265` plus the concurrently edited working tree. The exclusive jump-takeoff worker currently owns `PlayerMotion`/`LevelScene`; its in-flight `EmitJumpTakeoff` path (`port/game/PlayerMotion.cpp:67-77`, `port/game/LevelScene.cpp:945-978`) is **not** landing coverage and must be allowed to finish before a landing patch. No assertion here relies on the worker's final result.

## Exact Windows contract

- Constants are `kSmallDropDistance=300` and `kLargeDropDistance=700` (`Game/src/GameObjects/Character.cpp:25-26`). After base moving-sprite/collision update, `Character::Update` records the greatest `m_position.Y` while marked moving up **or down** (`:172-176,288-329`). On `IsOnSolidSurface()`, if the stored high point differs from current Y, it computes `dropDistance = mHighestPointWhileInAir - m_position.Y`, calls `DoLandOnSolidSurfaceEffects(dropDistance)`, then resets the high point to current Y (`:336-342,381`). This is **tracked apex minus landing center**, not vertical speed, air time, jump height above the ground, or previous-frame displacement. Initial value is set to current Y at `Initialise` (`:535`); `LevelEntry` can reset it to `-99999` (`Game/src/GameObjects/LevelEntry.cpp:37-40`, `Character.cpp:403-407`). Preserve that source caveat when designing entry tests.
- `DoLandOnSolidSurfaceEffects` returns for **<300**; at exactly 300 the small branch is eligible, and at exactly 700 the large branch is eligible (`Character.cpp:409-435,465-490`). It additionally requires `IsOnSolidLine()`, a current strip, a non-null strip material, and a nonempty `GetRandomParticleTexture()` (`:416-432`). A solid-box landing is not a material-spray landing. Material footstep audio occurs before the texture check; vibration occurs only with a texture and the material flag (`:424-429,460-495`). These nonvisual side effects are not requested in a visual-only slice. The landing-effects call precedes roll-window/impact-animation handling (`:342-378`), so pre-landing roll input must not silently suppress the material spray.
- **Small, 300 <= drop < 700:** `CreateDirectedSpray(5, (X+directionX*10, CollisionBottom()+35), GetDepthLayer(), direction=(0,1), spread=.8, culling bounds=(1200,720), material particle texture, speed=1–1.5, lifetime=.8–1.2 s, size=32–32, gravity=.8, loop=false, brightness=.8–1, loopTime=1, scalesByLifetime=true, scaleTo=5, spawnSpread=(5,.2), fadeIn=.15, fadeOut=.9)` (`Character.cpp:433-458`; argument names in `Game/src/Particles/ParticleEmitterManager.h:58-82`).
- **Large, drop >= 700:** `CreateDirectedSpray(10, (X+directionX*10, CollisionBottom()), GetDepthLayer(), direction=(0,1), spread=.4, culling bounds=(1200,720), same material texture, speed=3–5, lifetime=.4–1 s, size=5–10, gravity=.8, loop=false, brightness=.8–1, loopTime=1, scalesByLifetime=true, scaleTo=15, spawnSpread=(5,.2), fadeIn=.15, fadeOut=.9)` (`Character.cpp:465-490`). The missing `+35` Y offset and smaller initial sizes are material differences; do not clone the jump's ten-particle parameters.
- Factory semantics matter to a deterministic check: spread is a **nonnegative random X addition** and corresponding Y subtraction; lifetimes descend by `(max-min)/count` with particle index; X and Y spawn offsets are signed integer draws up to 50 and 2 respectively for `(5,.2)`; speed/brightness are quantized random values, and size is scaled by game scale (`Game/src/Particles/ParticleEmitterManager.cpp:373-397,424-525`). The 1200x720 value is a culling box, not an onscreen textured rectangle (`ParticleEmitterManager.h:63`). Do not demand Windows RNG identity from a separate Linux stream.

## Current Linux seam and missing behavior

- Forest-1 Player ID2 is at `Game/XmlFiles/levels/forest_exploration_1.xml:33-60`; initial SolidLineStrip ID3 has `grassground` (`:61-85`). Its sole active particle texture is `Media\\rock_particle.png` (`Game/XmlFiles/materials.xml:173-179`). The port parses material particle textures and binds them to ground segments (`port/game/LevelScene.cpp:153-163,258-274`, `port/game/LevelScene.h:62,144`), so a landing effect can reuse the material lookup and `kPlayer`-depth spray drawing seam already used by Running footsteps and takeoff (`LevelScene.cpp:979-1012,1233-1237`).
- `PlayerMotion::Update` already has the decisive contact transition: it remembers `wasGrounded`, sweeps lines and boxes, chooses the highest contact, then sets `grounded_` and `groundedSegment_` (`port/game/PlayerMotion.cpp:121-171`). But it tracks no apex/highest-air-Y and emits no landing spray. `SetPlayerFootstepContact` receives only current contact (`:172`, `LevelScene.cpp:941-944`), and the existing Running spray is three particles on an animation-frame transition (`LevelScene.cpp:979-1012,1087`); the takeoff spray is emitted on jump rising edge, before collision resolution (`PlayerMotion.cpp:67-77`). Neither distinguishes a 300/700-unit landing. Search of the targeted `port/game/PlayerMotion.cpp`, `port/game/LevelScene.cpp/.h` paths found no landing emission. A ground-transition-only implementation would also mistakenly spray after short drops unless it carries the apex and applies both thresholds.

## Minimal falsifiable CPU-only next slice, after jump worker completes

In a deterministic `PlayerMotion`/`LevelScene` fixture, seed a known horizontal grassground segment/loaded texture and start airborne above it (or use a real forest ledge). Step fixed `dt` through descent into *new* solid-line contact. Capture prior grounded/contact state, tracked highest airborne Y, landing center Y, selected segment/material, and scene-owned landing sprays. Use controlled trajectories with computed apex-to-center drops **299.9, 300, 699.9, 700**: expect respectively **0, 1x5, 1x5, 1x10** sprays, exactly once on each landing. Assert origins `(landingX+facing*10, collisionBottom+35)` for small and `(landingX+facing*10, collisionBottom)` for large; player depth, `rock_particle.png`, culling box and the two parameter sets above. Continue several grounded frames and assert no duplicates. Negative controls: same drop onto a solid box, line material with no particle texture, and a non-landing airborne frame all emit zero. Include pre-landing roll-buffer control if the fixture exposes it: source calls material effects before roll handling. Hold a fixed Linux random seed only to make range/sequence assertions repeatable.

Implement only apex/drop tracking plus a landing event and two scene-owned spray variants, without changing collision/jump physics, Running footsteps, or the takeoff effect. On the current port, the new landing-spray count is predicted to remain zero even for eligible line impacts. A CPU event/draw spy is the first discriminator; a later exclusive GPU A/B and matched Windows frame are separate gates for visual parity. The exact Windows `mIsMidAirMovingUp/Down` state machine and entry reset can affect when apex tracking begins; test an actual ledge/fall path before claiming all geometric drops trigger. Do not infer a landing spray from every ground contact, box, water, or downward dash merely because a landing animation plays.
