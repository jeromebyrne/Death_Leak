# Gameplay HUD film overlay — read-only original-source QA (2026-10-23)

## Result

**Source contract established; implementation/visual acceptance not established.** The original `game_hud` includes a full-viewport four-frame film widget at authored alpha 0.2. It is updated by wall-clock UI updates, rendered after scene postprocessing, and ordered before the other HUD widgets by their string keys. A concurrent worker owns `port/linux/main.cpp`; its live contents are a provisional integration snapshot, not a completed or tested result. This audit used no build, GPU, display, capture, or source edits.

## Original-source contract

1. **Art and geometry.** `Game/XmlFiles/UI/UI.xml:2-4` declares a 1920×1080 base and `game_hud`. `Game/XmlFiles/UI/game_hud.xml:3-16` specifies `26_scratch_anim` at `(-960,-540)`, size `1920×1080`, `hflip=false`, `vflip=false`, `alpha=0.2`, `use_standard_effect=true`, `fps=11`, with `film_frame.png`, `_2`, `_3`, `_4` in that attribute order. The `image=noise_layer.png` attribute is initially loaded by `UISprite::LoadContent`, but `UIAnimatedSprite::LoadContent` replaces `m_texture` with frame 1 when frame paths exist (`Game/src/UI/UISprite.cpp:124-132`; `Game/src/UI/UIAnimatedSprite.cpp:20-39`). Thus `noise_layer.png` is not the normally submitted film texture. The four frame files are present under `Game/Media/UI/` (576×324 source PNGs; they are stretched by the authored quad).
2. **Frame timing and lifecycle.** The frame list is read from XML attributes in order (`Game/src/UI/UIAnimatedSprite.cpp:41-59`). Initial frame index is 0 at load (`:33-38`), but each active-screen update can advance it. `Update` reads `timeGetTime()` and, when `mLastFrameSwitch + 1000 / mFramesPerSecond < currentTime`, advances **one** frame modulo frame count and stores current time (`:61-78`). For 11 FPS, integer division makes a strict `>90 ms` test; no catch-up loop. `mLastFrameSwitch` begins at zero (`:4-7`), so the first active update can already advance if process wall time exceeds 90 ms. The screen is constructed/loaded once and `PushUI` reuses it without resetting animation state (`Game/src/UI/UIManager.cpp:249-267,294-369`). `UIManager::Update` updates only current screens (`:81-102`); `UIGameHudScreen::Update` first calls `UIScreen::Update` (`Game/src/UI/UIGameHudScreen.cpp:36-49`). Thus a pause/pop can leave the stored frame and last-switch time intact, followed by at most one advance on resumed update. Frame phase must not be inferred solely from elapsed gameplay/fixed delta or from the first visible draw.
3. **Draw order.** `Game/src/program.cpp:293-318` draws scene, postprocess if enabled, and then `UIManager::Draw`; `Game/src/UI/UIManager.cpp:174-180` draws current screens in list order. `UIScreen::XmlRead` inserts widgets into `m_widgetMap` keyed by name, and `UIScreen::Draw` iterates that `std::map`, not XML sequence (`Game/src/UI/UIScreen.cpp:51-77,161-171`; `Game/src/UI/UIScreen.h:34`). Within `game_hud`, `26_scratch_anim` therefore precedes `29_frame_top`, `30_frame_bottom`, `40_orb_count`, `9_health_meter`, `91_xp_meter` (`Game/XmlFiles/UI/game_hud.xml:3-16,49-98`). `UIGameHudScreen::Draw` adds orb-count text only after base-screen widgets (`Game/src/UI/UIGameHudScreen.cpp:226-241`). A port may composite film before later HUD elements, but it must preserve existing top/bottom frame treatment when comparing exact HUD order; drawing it after all meters would contradict source order.
4. **Alpha/effect.** `UISprite::Draw` selects the standard effect when requested, binds `m_texture`, and sets `m_alpha` (`Game/src/UI/UISprite.cpp:254-268`). The standard shader multiplies sampled texture alpha by that value while leaving RGB as sampled times light color (`Game/ShaderFiles/BasicLightTexture.fx:53-59`). Windows blending uses source alpha and inverse source alpha (`Game/src/Core/Graphics.cpp:392-405`), enabled before the scene/UI draw (`Game/src/program.cpp:293-317`). Therefore 0.2 is a **modulator of each texel's alpha**, not a command to force every film pixel opaque-at-20%. A byte tint of 51 is a reasonable representation only if the Linux renderer multiplies it by sampled texture alpha once and uses equivalent source-over blending. The `final_scene_hud` has a separate 0.25 authoring (`Game/XmlFiles/UI/final_scene_hud.xml:3-16`); its 64-byte tint is not the gameplay-HUD contract.
5. **Reachability.** The main-menu play action pushes `game_hud` after level load (`Game/XmlFiles/UI/mainmenu.xml:68-77`); `UIManager::PushUI` keeps it in current screens until popped (`Game/src/UI/UIManager.cpp:237-291`). This is ordinary active gameplay, not merely menu or final-scene film.

## Linux integration acceptance criteria (for the owning worker/coordinator)

- In an ordinary active gameplay level, submit exactly one of the four `Game/Media/UI/film_frame*.png` frames over the logical viewport after scene postprocess and before later HUD frame/orb/meter/text draws. Preserve the separate menu and `sea_2` paths; do not apply gameplay alpha 0.2 to `final_scene_hud`'s alpha 0.25.
- Preserve 11-FPS **wall-clock** frame switching with strict threshold, one-step advance, wrap, and clearly documented first-visible-frame/reentry semantics. A monotonic clock is a practical Linux analogue, but starting it on the first gameplay draw differs from the Windows `mLastFrameSwitch=0` initial update and should be labeled as such, not asserted exact phase parity.
- Ensure no double alpha multiplication or replacement of per-pixel texture alpha. If the renderer's tint/texture/blend path is not already evidenced, inspect that path before claiming the authored 0.2 is visually reproduced.
- In a focused, non-GPU command-spy/clock test owned by the implementation worker, check load success for all four paths, selected texture/viewport/alpha, postprocess-before-film and film-before-HUD order, strict threshold and wrap, and menu/final-scene nonregression. A shared renderer change or physical-GPU gate should be assigned separately by the coordinator; this QA owns neither.
- For visual acceptance later, obtain a state-matched original Windows **post-HUD** active-play frame/clip with observed frame index/phase and compare equivalent Linux output, including translucent regions and top/bottom HUD overlap. Current source analysis cannot prove matched-Windows pixels or Jerome's visual approval.
