# Right-stick fall/impact X-hold gate — bounded source audit (2026-10-22)

Scope: read-only comparison of the Windows impact-recovery flags with the existing Linux right-stick target and motion layer. No source edit, build, GPU run, or parity claim. This report is the sole artifact of this audit.

## Existing gate and live wiring (inspected first)

- `port/game/LevelScene.h:81-107` already implements `RightStickCameraTarget`: skip disconnected/ineligible input, strict per-axis 8689 deadzone, neutral resets both authored offsets, active stick always writes Y from raw converted RY, and rolling/falling/melee holds **previous X**. Thus the missing definition is specifically the `falling` argument, not another camera formula. `port/tests/right_stick_camera_cpu_test.cpp:30-52` checks a supplied `fall=true`, but cannot establish when real motion should supply it.
- `port/linux/main.cpp:452-455` snapshots controller axes. Camera follow at `:653-687` still reads fixed `scene.CameraOffsetX/Y()` before `motion.Update` at `:688-690`, and `:691-693` sends sticks only to strafe visuals. `main.cpp:1089-1094` updates visuals later. The target component is **not** wired to the live loop; any impact contract below is a handoff for its owner, not a functioning camera gate. Initialize/reset its target on initial load (`:305-328`) and all `scene =` paths (`:537,626,984,1014,1046,1070`) when wiring it, as the earlier right-stick handoff describes.

## Windows meaning: landing-recovery flags, not airborne state

- The thresholds are `kSmallDropDistance=300` and `kLargeDropDistance=700` world units (`Game/src/GameObjects/Character.cpp:24-26`). `mHighestPointWhileInAir` tracks maximum center Y while moving up/down (`:319-329`); when on a solid surface and apex differs from current Y, drop is `apex - currentY` (`:336-342`). For a controllable player, with no successful pre-landing roll, outside water, and not already rolling, **300 < drop < 700** sets short impact, clears large, and stops X acceleration (`:344-377`). **drop >= 700** invokes `DoLargeImpactLanding`, clearing short, setting large, stopping X acceleration and shaking player camera (`:124-135,374-377`). Exactly 300 produces neither; exactly 700 is large. `DoLandOnSolidSurfaceEffects` at `:409-414` has its own `drop < 300` particle/sound threshold; it does not define the recovery gate.
- A successful buffered/pre-landing roll clears **both** recovery flags even for a large drop; it may still shake for `drop >= 700` (`Character.cpp:344-363`). Water or an already-active roll bypasses the normal classification (`:364-378`). A separate **hard-impact** cause is landing after a downward dash: on solid, `mWasDownwardDashing` calls `DoLargeImpactLanding()` at `:198-212`; this is not conditional on a 700-unit drop. The dash-history flag is then updated/cleared there. The large flag can also be cleared by side collision (`:331-334`), so it is not purely an elapsed landing timer.
- These flags survive the landing frame until the corresponding animation finishes. `Character::UpdateAnimations` forces `ImpactLandHard`, animates it and clears large only on `IsFinished()` (`Character.cpp:735-767`); `ImpactLandSoft` similarly clears short on finish (`:769-790`). `AnimationPart::IsFinished` tests frame index against frame count (`Game/src/Animation/AnimationPart.cpp:47-54`); `SetSequence` restarts it (`:142-157`), and `Animate` advances from update delta and sequence frame rate (`:201-235`). Authored player sequences are soft 30 fps and hard 15 fps (`Game/XmlFiles/animation/player_anim_default.xml:767,814`). A fixed 0.5-second roll timer, a single landing pulse, or a generic grounded flag is not an equivalent recovery lifetime. `Player::UpdateAnimations` delegates to Character after intro (`Game/src/GameObjects/Player.cpp:927-983`). Animation is called by `Sprite::Update` through `MovingSprite::Update`/`SolidMovingSprite::Update`, *before* Character's landing classification in its update (`Sprite.cpp:358-366`; `MovingSprite.cpp:53-65`; `SolidMovingSprite.cpp:44-59`; `Character.cpp:172-176,336-379`); collision and input then run after object updates (`Game/src/Game.cpp:176-215`). Match the state visible to input after post-update/collision, not a later render-only pose.
- The camera X-hold condition is explicit `JustFellFromLargeDistance() || JustFellFromShortDistance()` in `Game/src/InputManager.cpp:462-472`, following neutral reset at `:449-459`. The Y offset is updated earlier in `ProcessAimDirection_gamepad` (`:374-395`), and aim precedes strafe in the input order (`:556-589`). Therefore an **active** stick during either recovery holds prior X while updating Y; a **neutral** stick during recovery resets both offsets. It is neither an airborne gate nor a freeze of both axes. Dead/uncontrollable players bypass gamepad input (`:127-143`).

## Minimal Linux `PlayerMotion` contract for camera wiring

`port/game/PlayerMotion.h:9-27` exposes `Grounded()`, `Rolling()`, `DownwardDashing()`, velocity, etc., but **no impact-recovery state**. `PlayerMotion.cpp:90-95,180-187` already maintains an airborne apex and computes `landingApexY_ - y_` for material spray on `!wasGrounded && grounded_`. That value is the natural classification input; the spray itself is not a gate. `Reset` initializes apex, placement and roll/dash fields (`:15-20`). `Update` resolves foot contact and clears dash at `:129-193`; it currently has no impact flag/animation lifetime. `main.cpp:688-700` evaluates `motion.Update`, strafe visual and buffered roll after camera follow; a future target update should use the post-motion recovery state, with any same-frame roll cancellation applied, after follow and before next follow. It must not infer recovery from `!Grounded()`, `VelocityY()<0`, `!wasGrounded && Grounded()` alone, `DownwardDashing()` alone, or render animation name.

Proposed smallest API/state: expose `ImpactRecovering() const` (or `JustFellFromLargeDistance() || JustFellFromShortDistance()` if separate visual states are needed) backed by an internal `None/Soft/Hard` impact state. At a real new landing with valid non-authored apex, classify strict `(300,700)` and `>=700` only when not rolling/in water and no accepted buffered roll; also promote a completed downward-dash landing to Hard irrespective of distance. Clear/reset on successful landing roll, `Reset`, and source-equivalent hard side-collision cancellation. Keep Soft/Hard until their **actual motion/animation recovery completion**; if the Linux visual animation system cannot provide completion, use an explicitly documented approximation whose onset and expiry are tested, not a one-frame landing boolean. Do not erase an existing recovery on ordinary grounded updates without a new landing. Priority of same-frame buffered roll versus classification must be explicit: Windows roll avoidance clears both (`Character.cpp:344-363`), whereas current Linux `TryBufferedRoll` is called after `motion.Update` (`main.cpp:688-700`), so either clear recovery on successful `TryBufferedRoll` or move the decision into the landing transition without changing gameplay roll behavior. A hard dash landing can be triggered by the source's retained `mWasDownwardDashing` even if current dash has been cleared; Linux currently clears `downwardDashing_` on ground (`PlayerMotion.cpp:178`), so preserve pre-contact dash history for classification.

Pass **only** `motion.ImpactRecovering()` as `falling` to `RightStickCameraTarget::Update` (`LevelScene.h:92-105`). Keep `Rolling()` and combat melee as separate gate inputs. A live integration should retain follow-before-input (`main.cpp:670-693`), SDL Y conversion once (`LevelScene.h:86-105`), and gameplay/connected eligibility. The impact feature does not require changing camera lag, clamp, authored offset, strafe body, or renderer.

## Proposed CPU fixture assertions (not executed here)

1. Drive a flat landing with controlled airborne apex: drop **300** ⇒ no recovery; **300+epsilon** and **699.999** ⇒ Soft; **700** ⇒ Hard. Confirm initial authored placement and an ordinary jump/fall in flight never gate. Confirm a later short landing replaces hard and a later hard landing replaces short only when a new source-equivalent landing occurs.
2. With an active right stick and prior non-authored target X, feed Soft then Hard recovery: X remains exactly prior target while Y becomes `authoredY + 300*RY/32767`; on neutral axes both reset even during recovery. With recovery ended, active stick sets X to `authoredX + 450*RX/32767`. Reuse existing target fixture (`port/tests/right_stick_camera_cpu_test.cpp:30-52`) but derive `falling` from driven motion, not a literal Boolean.
3. For qualifying drops, successful pre-landing/buffered roll ⇒ no impact recovery (and preserve roll gate independently); water/already-rolling normal landing ⇒ no distance-classified recovery. Downward-dash landing below 300 ⇒ Hard. Assert no spurious hard impact on dash activation before contact, and reset/level load clears recovery.
4. Advance Soft/Hard through their chosen animation-completion seam: recovery persists across more than one grounded update and clears at completion; no fixed frame count is asserted without verified animation timing. Verify next-update camera target consumption: landing/input frame follows old target, then active gated input holds X; subsequent follow consumes that held X and updated Y. A side-collision fixture should prove hard-state cancellation if modeled.

## Gaps / handoff

The port has apex data but not Windows impact recovery, retained dash history, side-collision recovery cancellation, or an animation-finished signal in `PlayerMotion`; its current 0.5 s roll duration is explicitly a stand-in (`PlayerMotion.cpp:29-34`). Also the existing CPU right-stick fixture supplies `fall` synthetically and the live `main.cpp` target is unwired. The implementer should add the minimal motion state/expiry seam and focused CPU fixtures under the shared-source owner, then wire `ImpactRecovering()` to the existing target only after that state is trustworthy. This audit does not claim precise animation-duration parity or live-input/GPU parity.

**Handoff:** Windows `JustFellFromLarge/ShortDistance` means *post-impact animation recovery*, plus a hard dash-landing cause; for active stick it blocks camera X writes while allowing Y writes, and neutral still resets both. The correct Linux gate is an explicit post-landing recovery state, not generic falling/grounded/one-frame landing.
