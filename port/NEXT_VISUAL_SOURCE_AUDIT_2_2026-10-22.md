# Next source-proven forest-1 visual gap after firing arm and ground shadow — player aim line (2026-10-22)

## Verdict and priority

The next distinct, bounded runtime visual omitted by the Linux port is the Windows player's **aim-line sprite**. It is created for every loaded player, becomes visible briefly when `Player::FireWeapon` is attempted, and stays visible while strafing. The current port's repeated right+fire forest route exercises its firing path, but the port has no aim-line texture, state or draw. This is a **local, thin, intermittent** player visual, not an explanation for scene-wide darkness, ID37 or ID15. Priority is based on a proven omission in the focal active-gameplay path, not on a measured Windows/Linux pixel delta. It follows the separately assigned firing arm and the reserved ground-shadow task; do not conflate their draw layers or triggers.

## Source and port evidence

- Forest-1 has Player ID2 at `kPlayer` (`Game/XmlFiles/levels/forest_exploration_1.xml:33-47`). After object initialization and before depth sorting, Windows `GameObjectManager::LoadLevel` calls both `m_player->AddAimLineSprite()` and `AddShadowSprite()` (`Game/src/GameObjects/GameObjectManager.cpp:438-450`). The aim line is **not** an XML sprite.
- `Player::AddAimLineSprite` creates a non-native 400 × 400 sprite from `Media\\aim_line.png`, attaches it at projectile offset `(5,25)` to the player, assigns `kPlayer` depth, and initializes alpha to zero (`Game/src/GameObjects/Player.cpp:97-98,634-658`). The existing asset `Game/Media/aim_line.png` is 200 × 200 RGBA. Read-only pixel inspection found only 350 nonzero-alpha texels, alpha maximum 121/255, and alpha bounding box `(145,89)-(199,110)` in PIL's exclusive-coordinate convention. At the port's 2/3 screen projection and 2× source-to-world scaling, the visible source-alpha footprint is roughly 72 × 28 px before rotation/occlusion; the full destination would be about 267 × 267 px. Thus the texture is not a broad square overlay.
- `Player::FireWeapon` refreshes the line's visible timer to 0.05 s after its initial movement/water/collision guards and **before** the burst/reload cooldown return (`Game/src/GameObjects/Player.cpp:388-415`; timer constants at :22-23). During update, strafing continually refreshes that timer; positive timer sets alpha to 1, otherwise alpha falls by `10*delta` until zero (`:345-365`). Windows draw manager skips alpha-zero objects (`Game/src/GameObjects/GameObjectManager.cpp:302-330`). This is not simply a permanently visible line or an animation started only on a successful projectile.
- Right-stick aiming supplies the direction and calls `SetAimLineDirection` (`Game/src/InputManager.cpp:374-395`). That method sets rotation, vertical flip and offset sign by aim quadrant (`Game/src/GameObjects/Player.cpp:661-697`); straight-right default leaves the initialized transform. The line is a separate `kPlayer` object inserted after the player, then depth-sorted, not part of the player's arm/body frames. The source `Sprite`/scene transform should be followed for any eventual angle support; this audit does not infer a new aim-angle convention from an unmatched screenshot.
- Linux currently creates scene sprites only from textured XML objects, plus special authored particles (`port/game/LevelScene.cpp:267-486`); no `aim_line.png` reference or aim-line state/draw exists in `port/game` or `port/linux`. `UpdatePlayerVisual` receives a successful-projectile event for the separate firing arm (`port/game/LevelScene.cpp:698-759`; `port/linux/main.cpp:682-687,1053-1057`), and `LevelScene::Draw` draws that arm then body in the XML player slot (`port/game/LevelScene.cpp:803-845`). No standalone player-depth line is emitted. The existing post-foliage forest route documents sustained firing (`port/POST_FOLIAGE_GAMEPLAY_REVIEW_2026-10-22.md`), but no matched Windows state/frame was captured in this audit.

## Bounded implementation suggestion

Load the shipped aim-line PNG once for levels with a player, retain a **separate** player-depth sprite and opacity timer, and project its 400 × 400 world-unit quad at the source projectile offset `(±5,+25)` with the same alpha blending/sepia treatment as ordinary sprites. For the port's current horizontal-only firing input, refresh the timer on an eligible fire attempt at the analogous point in the fire path, even if cooldown rejects that attempt; apply source 0.05 s hold and `10/s` fade. If/when analog aim/strafe input is supported, feed the actual aim vector and reproduce the source quadrant rotation/flip/offset logic; do not synthesize a diagonal direction from a horizontal script. Place the separate sprite in the `kPlayer` painter order after the body as the source's insertion/order implies, without folding it into firing-arm or ground-shadow drawing. Verify with deterministic player crops for idle, eligible held-fire, cooldown and fade, then an active route; Windows pixel parity still requires matched camera/input/time. Do not edit XML, PNG art, ID37/ID15, or global blending.

## Limit

This is a source-semantic omission, not proof that the tiny semi-transparent line is conspicuous in any existing unmatched screenshot. In particular, the current Linux `playerProjectileFired` flag tracks successful shots and is insufficient by itself to reproduce the Windows pre-cooldown timer refresh. No game/build/GPU/capture, shared checkpoint/status edit, commit or push was performed for this audit.
