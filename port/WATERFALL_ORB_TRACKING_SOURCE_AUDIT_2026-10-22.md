# Waterfall-top authored CurrencyOrb tracking: bounded source audit (2026-10-22)

Scope: read-only comparison of original Windows source and the current Linux `SceneSprite` path. No build, runtime, GPU capture, or parity claim. This is separate from the splash IDs 50/51 work.

## Authored data and Windows behavior

- `Game/XmlFiles/levels/waterfall_top.xml:1270-1293` gives a representative *small* authored orb, ID 75 at (-1335.014648, 2995), 47.6973 × 72.831207, `native=false`, `updateable=true`, `always_update=false`, Y sine offset 20 / amplitude(speed) 2 / randomized phase, X offset 0, alpha .75, `flame_orb`, vertical flip, `orb_anim.xml`, no gravity, X max velocity 20, Y max 99999, collision box 40.938286 square with Y offset 10. IDs 77, 82, 84, 86, 88, 89, 91, 98 follow at `:1294-1485` with the same type/parameters but different positions. There are 22 `<CurrencyOrb>` entries in this level (source text count); do not hard-code that count as gameplay logic. `native=false` is the Windows small/large discriminator (`Game/src/GameObjects/CurrencyOrb.cpp:65-70`).
- Initial state is `kIdle`; `Initialise` enables and reinitializes the Y sine around the authored XY with randomized initial phase, sets alpha .75, no gravity, X resistance 1, Y resistance 3, X max 20, small material, and `kOrb` layer (`CurrencyOrb.cpp:18-28,38-73`). The base `GameObject::Initialise` initializes the oscillator again from `rand()%999999` (`GameObject.cpp:120-127`); exact seeded cross-platform phase is not established. `SineWave.cpp:14-26` updates phase by `2*delta` and produces Y = initialY + 20*sin(phase), X = initialX. `GameObject.cpp:187-200` writes this into the actual world position; it is not draw-only bobbing. `CurrencyOrb.cpp:149-186,210-213` then checks player distance **from the current orb position**, strict `<130²`, and on first entry sets `kTracking`, attaches a small-orb trail, and plays a rate-limited material damage SFX. Large orbs do not proximity-track.
- Important update ordering: `CurrencyOrb::Update` calls `SolidMovingSprite::Update` before its state switch (`CurrencyOrb.cpp:138-147`); that reaches `MovingSprite::Update` and `Sprite::Update` (`MovingSprite.cpp:53-70`). Thus on the trigger frame the idle sine has already updated and tracking is armed, but `DoTrackPlayer` does not run until a subsequent update. On its first tracking update `DoTrackPlayer` disables sine (`CurrencyOrb.cpp:188-193,215-223`), after the base update has already run one more sine step. Maintain position continuity; do not reset to authored Y when tracking starts.
- Tracking is sticky: no return to idle and no distance-based release in `CurrencyOrb.cpp:147-207`. The target is the **player collision centre**, not player origin (`CurrencyOrb.cpp:225-230`; `SolidMovingSprite.h:62-70`). Each tracking update increments `mTimeTracking`; acceleration is 2.5, tripled once time is strictly `>2.0` s. Only the dominant absolute direction axis is actively set each step, with an additional 4.8 rate (also tripled) if that axis's current velocity opposes the target. The other axis's prior acceleration may remain set: `CurrencyOrb.cpp:232-259` and `MovingSprite.cpp:276-325`. Velocity direction rotates the orb at `CurrencyOrb.cpp:261-271`. Acceleration affects position through the **next** base update, not the current `DoTrackPlayer` call: `MovingSprite.cpp:79-88,147-153,179-205`. X is capped at ±20 source velocity units and position uses `delta/targetDelta`; `MovingSprite.cpp:82-88,152-153,202-206`. Avoid assuming a simple instantaneous steering vector or both-axis acceleration. Authored no-gravity and velocity limits are in XML `:1285-1288`; `MovingSprite.cpp:238-253` reads them.
- Collection is a separate collision callback, not automatic on the `<130` trigger. `CurrencyOrb.cpp:75-135`: reject already-collected and spawn-period instances and non-player contacts; small orbs require strict distance `<100²` from orb position to **player Position()** (not collision centre), then remove, increment currency balance once, set `mCollected`, and play material footstep sound. An authored/load-time orb additionally records its runtime ID (`CurrencyOrb.cpp:274-282`); the trail is detached and stopped (`:112-121`). This callback is reached through collision processing, so the 100-unit check alone is not proof of exact collision dispatch timing/geometry. Runtime-spawned orbs are different: `CurrencyOrb.cpp:394-422` starts them in `kSpawnPeriod`, with randomized launch velocity and 0.01–0.109 s pickup lockout; `:194-205` transitions directly to tracking. Do not conflate this with authored idle orbs.
- Windows persistence uses *runtime game IDs*, not XML `id`: saved IDs are loaded and suppress construction at `GameObjectManager.cpp:411-427,761-774`; a collected load-time orb appends its ID at `:1098-1101`, and save/level transition caches the list at `:515-529`. `SaveManager.cpp:305-312,325-365` stores both total currency and per-level collected IDs. Linux can keep its own key scheme but must continue one-time balance and reload suppression.

## Current Linux gap (snapshot read during audit)

- `port/game/LevelScene.h:13-51` has `SceneSprite` position, animation, `currencyOrb`, `collected`, persistent key, but **no authored-orb idle/tracking state or velocity/time**. `port/game/LevelScene.cpp:431-472,495-519` loads animation and authored XY/alpha plus level-path#XML-ID key. `UpdateVisuals` at `:666-758` advances selected visuals and orb animation; it does not update authored orb sine/track. `CollectCurrencyOrbs` at `:564-580` immediately collects static authored sprite XY within 100 and applies saved suppression. This misses pre-pickup hover, 130-unit acquisition, homing, rotation, trail, and current-position pickup geometry. Existing `SpawnedOrb` logic at `LevelScene.h:67` / `LevelScene.cpp:625-657` is a separate runtime path and is not reusable verbatim for authored state/order.
- `port/linux/main.cpp:675-688,1070-1075` updates player, calls authored collection and spawned-orb update, then later calls `UpdateVisuals` (and skips it for `simulateOnly`). Any authored motion placed only in `UpdateVisuals` changes pickup to previous-tick XY and stops it in simulation-only mode. This ordering is a concrete integration decision, not a visual-only tweak. The existing persistence application is `port/linux/main.cpp:301,607` (and other transitions) and `LevelScene.cpp:577-580`.

## Minimal implementation/test handoff

1. Give only `currencyOrb` authored sprites an idle/tracking state, oscillator phase/initial XY, tracking elapsed, per-axis velocity and acceleration, and current rotation. Initialize from authored data; preserve existing animation/depth/alpha/persistent key. Gate updates by the source 4000×4000 camera zone / `updateable` / `always_update` (`GameObjectManager.cpp:229-247,397-399`). Keep simulation authoritative, including `simulateOnly`, and decide/document source-equivalent ordering relative to player motion and collision.
2. On idle ticks, update world XY with Y = originY + 20*sin(phase) for waterfall-top small orbs. Trigger at strict `<130` from current XY to player position. Model source's base-update-first / one-step transition timing, sticky tracking, collision-centre target, dominant-axis acceleration and opposing-velocity boost, `>2s` multiplier, X cap, no gravity, and rotation. Avoid an origin snap on handoff. Trail/SFX can be staged but must be listed as remaining parity gaps until implemented.
3. Collect once at current world XY and strict `<100` against player position, keep existing Linux persistent key/total-balance behavior, and ensure collected/restored sprites never update or draw. Do not apply spawned-orb lockout to authored orbs.
4. Focused deterministic tests: ID75 authored load/parameters; out-of-range idle hover and animation/update-zone freeze; 130 boundary and trigger timing with no teleport; target motion/axis reversal and `>2s` behavior; 100 boundary and one-time collection at *moved* XY; saved-key reload suppression; simulation-only motion. A source-like numerical comparison needs fixed oscillator phase and explicit timestep/targetDelta. No such tests or parity evidence were run in this audit.
