## Input truth table and priority

Let `D=8689`, the XInput right-thumb deadzone, and compare **raw signed** SDL values strictly. At the start of each tick set `active=false`. If disconnected or neither `abs(RX)>D` nor `abs(RY)>D`, stop. If rolling, melee, or either just-fell recovery state, stop. Otherwise `RX<=0 && LX>D` yields `active=true, aimFacing=-1`; else `RX>0 && LX<-D` yields `active=true, aimFacing=+1`; all other combinations stay inactive. The source divides RX by 32767 only to obtain its sign (`InputManager.cpp:449-501,751-754`); do not require `RX` itself to exceed D when RY is active. In particular RX=0, RY>D, LX>D qualifies left aim; same-sign pairs and exact ±D LX/RX edge values do not qualify as a substitute for these comparisons. Source gamepad movement is processed before strafing (`InputManager.cpp:566-591`), so this current-tick visual pose is not a claim of exact original entry-tick flip timing.

`PlayerMotion` exposes no `JustFellFromLargeDistance`/`JustFellFromShortDistance` state (`port/game/PlayerMotion.h`). For this bounded slice, explicitly document the approximation: use a freshly detected airborne-to-grounded transition as the closest available just-fell gate, if obtainable without changing motion behavior; cover it with a fixture. Do not claim full impact-recovery parity or invent a sticky timer/animation. Input eligibility alone does not override higher-priority body selection: source `Character::UpdateAnimations` handles impact, melee, roll, crouch, air/water and wall-slide before the ordinary side-clear moving branch (`Character.cpp:746-1033`). The port lacks some of those exact states; preserve existing port priorities and label those omissions.

## Frame order, rate, and clock

XML `Game/XmlFiles/animation/player_anim_default.xml:366-522` defines two 20-frame loops, both default 30 FPS, min 4, max 60. `StrafeForward` index 0..19 maps `_000`..`_019` (footstep flags at indices 0,10); `StrafeBack` maps `_019`..`_000` (footstep flags at indices 9,19). Back includes per-frame skeleton data that this body-texture slice does not reproduce. Preserve XML order; do not reverse a loaded forward list at draw time or infer pose from shared texture IDs.

For **Player**, `Player::Initialise` sets `mRunAnimFramerateMultiplier=2.65f` (`Player.cpp:72-82`), overriding Character's 3.0 default. New strafe sequence rate after each ordinary movement animation advance is:

- dry, non-sprint: `clamp(abs((portVx/60.f) * 1.8f * 2.65f), 4.f, 60.f)` FPS;
- sprint or wet-last-frame: `clamp(abs((portVx/60.f) * 2.0f * 2.65f), 4.f, 60.f)` FPS, except source wet-last-frame uses `overrideMinFramerate=true`, so it clamps at max 60 but **not** min 4;
- source slow motion scales the dry computed rate by `mDeltaTimeMultiplierInSloMo` *before* clamp (`Character.cpp:1033-1050`). Expose/use sprint, wet-last-frame, and slow-motion state only if already represented; otherwise implement the available dry non-sprint case and label the others deferred, not silently approximate them. Do not globally alter the existing Running 2.65 rate.

`Character::UpdateAnimations` guards `SetSequence` by name; `SetSequence` itself always restarts (`AnimationPart.cpp:142-162`). Restart frame/clock only when target name changes. `AnimateLooped` advances at most one frame per tick and retains elapsed excess (`:168-197`). Source advances using the sequence's *previously stored* rate, then assigns the new movement rate. Initially XML rate is 30; a first short tick can show frame 0, but a long entry tick may already show frame 1. A faithful port needs mutable per-sequence current rate initialized from XML and updated **after** the advance, including reuse on re-entry; do not assert immediate first-tick dynamic rate or discard excess dt.
