# Strafe body static QA — 2026-10-22

Scope: read-only inspection of the current strafe edits in `LevelScene.{h,cpp}`, `SDLRenderer.cpp`, `main.cpp`, `Renderer.h`, the new `strafe_body_cpu_test.cpp`, and original Windows source. Only this report was written. No build, test execution, Docker, GPU, source edit, commit, or shared status change.

## Findings (ordered by gate impact)

1. **The new CPU fixture's second frame assertion is deterministically wrong.** `port/tests/strafe_body_cpu_test.cpp:63-66` enters `StrafeBack` at `vx=-100`, `dt=.01`, then updates at `dt=.024` and expects `_018`. `LevelScene.cpp:1124-1138` advances the first tick using XML 30 FPS, then stores `clamp((100/60)*1.8*2.65,4,60)=7.95` FPS. Accumulated `.034` seconds is below the new `1/7.95≈.1258` period, so the second tick remains `_019`. The test will fail when run with assertions enabled. Use a velocity/timing pair that crosses the *stored* second-tick period, or explicitly assert the slow-rate hold. This is not a compiler issue.

2. **The fixture is not linked into an existing test gate.** Neither `port/Makefile` nor `port/tests/integration.sh` mentions `strafe_body_cpu_test.cpp`; the integration script invokes only `player_visual_test.py` among these focused visual fixtures. The implementation note calls the fixture “unbuilt,” accurately. The normal standalone CPU linkage pattern for this scene is `port/game/LevelScene.cpp`, `port/game/PlayerMotion.cpp`, and the four `Game/tinyxml` implementation files, with `-Iport/compat` and `-UNDEBUG`; simply compiling the test translation unit will leave `LevelScene` references unresolved. There is no clear new API compile break in the reviewed C++ signatures: `ControllerAxes()` is non-pure, SDL uses existing controller APIs, and the appended `UpdatePlayerVisual` argument has a default, preserving old call sites. Full compilation remains unverified.

3. **The fixture does not establish its claimed frame-order/identity coverage.** `body()` at `strafe_body_cpu_test.cpp:46-54` searches only four texture IDs and falls back to the first drawn sprite; if an unexpected body frame or an arm precedes it, later negative assertions can pass without identifying the body. It checks only `_019/_018` and `_000/_001`, not all 20 XML frames or authored footstep indices. It does not check arm/body draw identity/order/XY, no Running-only spray under strafe, or raw SDL disconnect behavior. The final aim-line comparison verifies offset and flip only. These omissions matter because `LevelScene.cpp:1279-1287` may draw an arm before the body, and the source XML reuses the same PNGs in opposite frame order. Treat this as a focused smoke fixture after fixing item 1, not the full acceptance gate described in `STRAFE_BODY_CPU_TEST_PLAN_2026-10-22.md`.

4. **Source-contract limitations are explicit, but entry timing is not exact Windows behavior.** Windows `InputManager.cpp:566-591` processes movement before `ProcessStrafing_gamepad`, while the port computes `strafeVisual` after `motion.Update` and applies it in that frame's visual update (`main.cpp:685-693,1091-1093`). Windows `Character.cpp:1549-1574` uses the prior `mIsStrafing` state when movement changes horizontal flip. The port's selected strafe body flips to current RX sign immediately (`LevelScene.cpp:1099-1106`). Thus first-entry flip/pose parity is not established even with matching axes. This is a bounded approximation already identified in the corrected patch spec, not a reason to reject the body slice.

5. **The just-fell gate is narrower than Windows.** Windows rejects both `JustFellFromLargeDistance` and `JustFellFromShortDistance` while those recovery states persist (`InputManager.cpp:463-472`); the port only rejects `!wasGrounded && motion.Grounded()` for one update (`main.cpp:685-693`). It can resume strafe pose during subsequent impact-recovery frames. The implementation note acknowledges this; retain the limitation in any parity claim.

## Positive static checks

- Raw axis helper matches the source's strict ±8689 right-stick activation, signed RX branch (including zero when RY opens the gate), and raw LX opposing threshold (`InputManager.cpp:449-487`; `LevelScene.h:77-95`). SDL `KeyDown` movement remains a separate strict ±8000 gate (`SDLRenderer.cpp:546-560`). Controller removal clears the SDL pointer in `PollQuit`, and the new snapshot returns disconnected/zero when absent or detached (`:535-540,563-568`).
- The loader adds only body `StrafeForward`/`StrafeBack`; arm allowlist remains Still/Running (`LevelScene.cpp:404-450`). XML gives forward `_000.._019`, back `_019.._000`, 20 frames each, rate 30/min 4/max 60. `currentRate` starts at XML rate and is assigned after advancing; target-name changes reset cursor/clock. Running-only spray remains guarded by `target == "Running"` (`LevelScene.cpp:1121-1147`).
- The port keeps combat/movement facing separate from selected strafe body flip and preserves aim-line offset/vertical flip through `playerAimLineFacing_` (`LevelScene.cpp:1085-1106,1217,1270-1287`). Existing priority keeps melee, roll, water, dash, air, and wall slide ahead of grounded strafe. Crouch/impact exact states, sprint/wet/slow-motion animation-rate variants, and `StrafeBack` skeleton poses remain outside this slice, as documented.

Add discriminating body identity and a small set of missing source-contract assertions before treating it as a CPU gate; keep the first-entry timing and impact-recovery limitations explicit. No runtime or Windows pixel-parity conclusion follows from this static review.
