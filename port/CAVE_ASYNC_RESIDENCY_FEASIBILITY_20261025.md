## Real scheduling constraints
Physical NVE7 first top scene load/draw is fixed-route frame 411, and top Sprite ID3 `Game/Media/levels/underwater_cave/cave_background.png` (1750×1313) is viewport-admitted on the first draw. Its decoded RGBA buffer is exactly 9,191,000 bytes (8.77 MiB). Deferral beyond that draw would change pixels. The original renderer does PNG decode and `SDL_CreateTextureFromSurface` inside synchronous `LoadTexture` during `LevelScene::Load`; no independent upload queue exists. Prior diagnostic split one explicit SDL static allocation/update interval into 28.267 ms allocation/driver plus 6.416 ms update, and original SDL creation/upload varied 7.586–64.449 ms over serial routes. This is allocation/synchronization plus transfer, not a bandwidth-only operation.

An isolated same-binary worker probe starts at Forest frame 120, decodes the original PNG through libpng on a separate CPU thread, and retains the resulting RGBA vector through top entry. It deliberately does **not** hand that vector to the renderer or issue GPU work. This separates worker readiness/CPU-memory feasibility from the unresolved GPU-residency guarantee; it is not a candidate optimization. The probe uses 9,191,000 payload bytes plus vector/thread/decoder overhead; `ru_maxrss` stayed at about 107,660 KiB in this run because a larger earlier peak obscured incremental residency, so it is **not** a measured total RAM budget. The buffer would coexist with SDL/driver allocations at entry and may entail further copies. No trustworthy live VRAM budget is available: the prior physical NVE7 NVX values were implausible/uncalibrated and debugfs inaccessible.

Any production candidate must use a synchronized deterministic visual clock/transition packet and decoded RGBA comparisons at multiple first-draw and later frames.

## Decision
**Reject a production async/GPU-residency patch in this bounded slice.** CPU decode is schedulable during Forest, but that alone merely duplicates 8.77 MiB and does not remove top decode unless the renderer consumes the result. More importantly, simply precreating the full SDL texture during a Forest frame would move an observed ~28-ms and highly variable allocation/driver stall onto that frame; PBO chunking only addresses transfer after allocation and needs GPU fence/backpressure proof. Neither a per-frame allocation bound nor a defensible VRAM budget was observed. No serial physical A/B/A of a fully resident, pixel-exact candidate exists, so no software gain is accepted. No code commit/push or milestone DM.
