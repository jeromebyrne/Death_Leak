# Controller-strafe body: bounded implementation contract (2026-10-22)

## Decision and boundary

Implement the missing **player body sequence plus visual aim-locked facing** as a small input-to-`LevelScene` slice. This is a source/code-and-art eligibility contract, not a claim of Windows/Linux pixel parity. The existing `B` scripted right+fire input does not supply right-stick aim and cannot exercise it. Do not silently repurpose projectile direction, camera target offset, aim-line timing, right-stick Y aiming, or material spray behavior as part of this body patch. See `FOREST_VISUAL_BEHAVIOR_GAP_2026-10-22.md` for the source-backed omission.

## Exact source rule and priority

- Original `InputManager::ProcessStrafing_gamepad` (`Game/src/InputManager.cpp:449-501`) begins each gamepad tick with `SetIsStrafing(false)`. If **both** right axes are inside `XINPUT_GAMEPAD_RIGHT_THUMB_DEADZONE` it returns; rolling, either just-fell state, or melee also returns. With an active right stick, the *raw* left X must exceed that same right-stick deadzone in the opposite direction. `rightRangeX <= 0 && leftRawX > deadzone` sets strafe direction -1; `rightRangeX > 0 && leftRawX < -deadzone` sets +1. The zero-X/right-Y-active + left-positive case therefore qualifies for -1 by the actual source comparison; do not replace this with a generic “opposed nonzero X” test. A same-side stick pair is not strafing. `GetThumbstickRange` divides by `SHRT_MAX` (`InputManager.cpp:751-754`). `ProcessLeftRightMovement_gamepad` precedes strafing in gamepad dispatch (`:162-185,578-591`). Windows XInput deadzone is 8689 for right thumb; Linux should compare signed SDL raw axes to that threshold (and use the same strict `>`/`<`). The Linux port currently polls left X at 8000 for binary motion; that is a separate existing control policy, not a replacement for the source strafe threshold.
- `Character::UpdateAnimations` (`Game/src/GameObjects/Character.cpp:735-1062`) gives impact recovery, melee, roll, crouch, airborne/water and wall-slide branches priority. In its ordinary moving/no-side-collision branch (`|m_velocity.X| > 0.05` source world units/tick), active strafe selects `StrafeBack` if `mStrafeDirectionX != m_direction.X`, else `StrafeForward`; otherwise `Running`. With port velocity expressed per second, its existing `|vx| > 3` threshold is the matching ordinary-motion gate. Ordinary opposite-stick travel has movement direction opposite the aim/strafe direction, so it selects `StrafeBack`; `StrafeForward` needs an explicitly constructed state with strafe active and stored movement direction equal to aim direction (e.g. eligible input with direction/inertia state lag). Do not invent a same-stick shortcut to force it.
- `Character::AccelerateX` uses `mStrafeDirectionX` for horizontal flip while strafing (`Character.cpp:1553-1575`). It does **not** change the character's movement direction to aim. `AnimationPart::SetSequence` restarts at frame zero only on transition (`Game/src/Animation/AnimationPart.cpp:142-162`); `AnimateLooped` increments at most one frame per update (`:168-197`). Source `Character.cpp:1035-1050` adjusts the active moving sequence rate after the frame advance: dry non-sprint `abs(sourceVx * 1.8 * 3.0)`, sprint/wet `abs(sourceVx * 2.0 * 3.0)`, then sequence min/max clamp (`Game/src/Animation/AnimationSequence.h:15-27`). Strafe XML declares 30 default, 4 min, 60 max (`Game/XmlFiles/animation/player_anim_default.xml:366-522`). The port's current Running-specific 2.65 factor is pre-existing and must not be globally changed under this slice; implementing source rate for *new* strafe sequences should be explicit about the port's `/60` velocity conversion and the first-tick default-rate-before-adjustment nuance.

## Minimal state/API seam

1. `port/render/Renderer.h`: expose a backend-neutral controller-stick snapshot such as `struct ControllerSticks { int leftX, rightX, rightY; bool connected; }; virtual ControllerSticks ControllerAxes() const { return {}; }`. A non-pure default preserves existing render-spy implementers. This is input API only, not drawing logic. `port/linux/SDLRenderer.cpp`: read `SDL_CONTROLLER_AXIS_LEFTX/RIGHTX/RIGHTY` from the existing `gamepad_`, return zero/disconnected on removal/no controller. Keep `KeyDown(Left/Right)` and keyboard behavior unchanged. Sampling left raw X is necessary because binary `KeyDown` loses the source deadzone distinction. Read all axes once per play tick after event polling, not separately after motion/combat.
2. `port/linux/main.cpp`: keep existing `facing` as **movement/combat-facing** because it feeds `combat.Update(..., facing, ...)` (`:706`) and currently tracks `direction` (`:600-608`). Compute a separate transient strafe eligibility/aim sign from controller snapshot and current roll/melee/just-fell state; clear it every play tick, including controller disconnect and neutral axes. Feed motion the pre-existing `direction`. For the body contract pass a small explicit `PlayerStrafeVisual { bool active; int aimFacing; int movementDirection; }` (or equivalent scalar arguments) into `LevelScene::UpdatePlayerVisual` at `main.cpp:1076-1087`. Keep `facing` passed to combat untouched. Do not infer strafe from `fire`, `B`, `vx` sign, or the last facing alone. If port does not expose source just-fell state, document and gate against its closest existing motion state, with a targeted fixture; do not claim full source eligibility parity without it. State that any non-strafe right-stick flip is deferred: original has such an aim-only branch, but this bounded contract covers sustained strafe pose.
3. `port/game/LevelScene.cpp`: append `StrafeForward`, `StrafeBack` to the Player **body** allowlist (`:403-427`), using the existing XML frame loader/texture cache. Do not add them to arm allowlist. In `UpdatePlayerVisual` (`:1056-1133`), apply strafe selection only at the existing ordinary `Running` branch, after higher-priority melee/roll/water/air/wall conditions. Compare `aimFacing` with the **stored movement direction**, not `vx` sign, to mirror `mStrafeDirectionX != m_direction.X`. Set `playerFacing_` to aim sign only while visual strafe is selected, otherwise retain the existing `facing` argument. This also controls the player/arm flip in the existing painter slot (`:1223-1270`); inspect the aim-line flip/offset at `:1206,1261` before accepting any unintended change there. Extend the existing looped-frame set and movement-rate branch to both strafe names; keep transition reset and one-step-per-update clock. Do not touch `SDLRenderer` drawing/blending or XML/PNG art. Running-only material-spray code (`:1127-1131`) should remain Running-only until a separate strafe-footstep contract is taken; report that omission honestly.
