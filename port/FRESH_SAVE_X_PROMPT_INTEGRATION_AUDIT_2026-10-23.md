# Fresh-save X prompt integration audit — 2026-10-23

## Verdict

The private CPU patch implements the source trigger and sprite geometry in the correct world pass, but **visual parity is unproven**. One source-backed painter-order gap remains: the integer depth `2999` schedules the X after **all** depth-3000 objects, whereas Windows invokes the X draw immediately after `Character::Draw` *inside the player's own draw call*. No shared source change is made here; the minimal integration correction is a player-adjacent painter hook, not a global change to depth ordering. A matched prompt-off/on physical pixel gate is still required.

## Source contract checked

- `Game/src/GameObjects/Player.cpp:42,986-1000,1121-1165,1177-1202`: `mTotalTimePullingSword` advances by gameplay delta in `IntroCutscene1` regardless of Interact. Release resets the separate continuous held counter, not the phase total. The phase total resets in `IntroCutscene2`/later. Draw requires **strictly** `>8.0f` and raw Interact up; holding hides the X immediately and releasing after eight seconds shows it immediately. It is not an E-key/world-interactable prompt.
- `Player.cpp:73-74,1186-1199`: Steamworks Deck detection selects `x_deck.png`, 60×60 world units; otherwise `x.png`, 150×90. The quad is centered at player `(-35,+50)` and passed `GetDepthLayer()+0.1f`.
- `Game/src/Utils/DrawUtilities.h:24-66`: full-texture UVs, `EffectLightTexture`, identity world transform, alpha 1.0, no rotation. `Player::Draw` calls `Character::Draw` **before** drawing X. `GameObjectManager.cpp:302-329` calls each object's Draw as a unit; its drawable list is depth-sorted descending (`:62,1024`). `Graphics.cpp:81-83` sets depth comparison ALWAYS, so the X's `+0.1` is not itself a guarantee of occlusion; the actual draw-call sequence matters.

## Linux integration checked

- `port/linux/main.cpp:51-58,426-437,666-696,1280-1300`: the new cumulative clock advances once in active Looped gameplay; it survives release/rehold and resets at Pull/completion/scene replacement. Its visible predicate is strictly `>8`, Looped, raw Interact up. Asset selection is explicitly `--steam-deck` because Steamworks Deck detection is unavailable; mere controller presence does not select Deck art. The private CPU report/test covers these logic cases but is not a rendered-frame proof.
- The sprite uses the complete loaded PNG, default white/opaque tint, no rotation/flip, world dimensions and centered position as authored. The world-space Y inversion in the current formula is consistent with the port's player projection. `SDLRenderer.cpp:184,205-277` uses alpha blending and texture alpha, so "opaque" here means alpha **modulation** 1; transparent PNG pixels remain transparent. The assets are RGBA PNGs: `x.png` 300×180, `x_deck.png` 256×256. The authored quad is minified on screen and uses the renderer's scene sampling policy; Windows/SDL filtering parity has not been pixel-proven.
- The prompt is submitted before `LevelScene::Draw`, through the same `drawCameraX/Y` (including shake) and scene `SetWorldZoom`/`ProjectWorldRect` path as the body, before `ApplyScenePostprocess` and HUD. The 2/3 authored-1920-to-1280 projection plus zoom applies to both. It is not a screen-fixed overlay. This is the right integration seam.
- `LevelScene.cpp:1311-1332,1335-1340`: dynamic items are stable-sorted descending and drawn only when their depth is **greater** than the next static object's depth. Thus `2999` is painted after the player **and every other 3000 item**, not immediately after the player. Source Player::Draw paints the icon immediately after Character::Draw, before a later same-depth object is visited by GameObjectManager. This distinction can affect overlap with a same-depth pickup/effect and is not fixed by interpreting `+0.1` as an SDL depth value. Current bucket is a reasonable ordinary-frame approximation, not exact painter parity.

## Minimal handoff and physical gate

1. Integration owner: retain the current trigger/geometry/camera/zoom implementation. If pursuing exact ordering, add a narrowly scoped post-player draw slot in `LevelScene::Draw` (or equivalent player-adjacent callback) and submit the X there; preserve all other painter ordering. Do not widen the change to fractional depth globally. Verify any same-depth pickup/particle interaction against source object visitation before moving it. This is the one source-backed correction, not a confirmed visible defect in available frames.
2. With the GPU/build lane released, capture a fresh forest-1 unheld Looped state at `<=8.0` and first `>8.0`, then held and released after eight seconds. Use identical scene/frame/camera/zoom/shake state for prompt-off/on A/B if a controlled render toggle is available. Record binary/source hashes, elapsed phase clock, raw Interact, body phase, draw camera, zoom, Deck mode, renderer/GPU identity. Pixel difference should be restricted to the projected player-offset X quad (allowing scene postprocess/texture filtering at its edge); no HUD relocation, body/burst change, or second X draw. Capture both default and explicit Deck asset at least once. A renderer-spy can additionally assert one draw at the player-adjacent slot and zero in Pull/completion/loaded/other-level/menu states.
3. A same-history Windows frame (save state, viewport, input, camera/zoom, Deck identity) is needed before claiming **Windows pixel parity**. Existing physical captures stop before eight seconds and cannot answer this gate. No build, GPU capture, or comparison was performed in this audit.
