# Next waterfall-top visual discriminator — rotated fog edge admission (2026-10-22)

**One finding (read-only source audit):** The port can discard each of waterfall-top's four large, rotated, alpha-faded fog quads while a rotated corner is still on screen. This is a **camera-edge pop / lost atmospheric fringe**, not a claim that the central waterfall composition is currently wrong. It is the highest-priority distinct *remaining* source-backed discriminator I found after the sheet-flow (including IDs 13/14), splash 49–51, orb-hover, foliage/weather phase, shader-clock and ordinary min-filter work: these four 1988×1290 foreground quads span much of the entry/bridge view, and the branch can suppress the whole quad. No matched original frame measures the effect's magnitude.

## Evidence and precise seam

- `Game/XmlFiles/levels/waterfall_top.xml:1798-1861` authors `ScrollingSprite` IDs **117, 118, 119, 121** with `Media/fog.png`, 1988×1290 native size, **0.11 rad** rotation, `kGroundFront`, pixel wobble, and alpha 0.6/0.6/0.6/0.5 before each fade. Their X scroll/fade is already implemented (`port/SCROLLING_FOG_CHECKPOINT.md`); this audit does not propose changing it. The existing active-gameplay evidence is `port/build/current-waterfall-gameplay-video-2026-10-22/{waterfall-top-current-head-10s.mp4,still-1s.png,still-5s.png}` (`port/CURRENT_WATERFALL_GAMEPLAY_VIDEO_2026-10-22.md`). Steam `../store_media/screenshots/16.jpg` is a different camera/state still; these assets establish scene context, **not** an observed matched-edge pop.
- Windows `Game/src/GameObjects/GameObjectManager.cpp:302-329` asks `Camera2D::IsObjectInView` before each draw. For rotated objects, `Game/src/Core/Camera2D.cpp:39-79` uses `GetRight/Left/Top/BottomRotated`; those methods use the conservative square `mLargestPossibleDimensions` (`Game/src/GameObjects/GameObject.h:137-152`), set to `max(width,height)` on each axis (`Game/src/GameObjects/GameObject.cpp:117-118`). Thus a 1988×1290 rotated fog object remains eligible to draw while its center is within **994 world units vertically** of the camera edge, subject to the source's strict overlap check and current parallax offset.
- Linux builds the correct rotated GL quad in `port/linux/SDLRenderer.cpp:317-375`, but `port/game/LevelScene.cpp:1020-1023` first rejects sprites using the **unrotated** projected destination rectangle. For this fog size, its vertical half-extent is only 645 world units. At 0.11 rad the true rotated vertical half-extent is about `994 sin(.11)+645 cos(.11) = 750` world units, roughly **105 world / 70 output pixels** beyond that pre-draw test. The source's conservative 994-unit test is even broader. A camera position with fog center just outside the unrotated top/bottom threshold but within the rotated extent can therefore produce a visible fog fringe on Windows while Linux draws nothing. This is conditional geometry, not evidence that the 10-second video traverses that threshold. The old forest raft audit notes the *general* rotated-cull distinction; this report isolates the four untested waterfall-top fog IDs, their much larger vertical footprint, and a specific edge discriminator.

## Bounded implementation and verification proposal (not executed)

For scene Sprite draws only, replace the final unrotated viewport reject with a conservative rotated-quad screen AABB when `rotationDegrees != 0` (or simply defer this optimization to the renderer). Keep the XML transform, scrolling/fade state, wobble UV/clock, alpha, layer order, and shaders unchanged. Do not alter the manager-style **update-zone** predicate or particle emitter culling. A CPU unit should place one ID117-sized quad at a fixed camera with its center just beyond the unrotated vertical limit but a rotated corner still inside, assert that the draw reaches `Renderer::DrawSprite`, and also assert rejection only after the rotated AABB is wholly outside; include unrotated ID6 as a control. When the exclusive GPU lane is free, render the same ID-only waterfall-top camera boundary at two positions straddling that threshold and check gradual fringe exit rather than all-at-once disappearance. A matched Windows camera/frame and user review remain needed for visual parity.

The Steam JPEG has no matched camera, clock, weather, or fog fade, so no pixel-parity or acceptance claim is made.
