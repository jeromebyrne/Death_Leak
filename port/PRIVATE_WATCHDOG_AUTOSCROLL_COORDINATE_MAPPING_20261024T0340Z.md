## Verdict

**The ID15 object-side Windows cull inputs are reconstructible exactly from the current Linux scene for this static authored layer; an exact active-gameplay WindowsCameraAdmission decision is *not* derivable from the Linux camera pair alone.** The missing input is the original Windows `Camera2D::m_position` at the manager's admission instant (and its backbuffer dimensions). At an actual 1280x720 Windows backbuffer, supply to the Windows predicate:

- current center `(217.922994,878.710856)`, current size `(746.757975,1493.515951)`; ordinary zero-rotation bounds `x≈[-155.456,591.302]`, `y≈[131.953,1625.469]`;
- stored largest-possible width **and** height `2240.273926`, **not** `1493.515951` or the rendered quad's trigonometric AABB; this square is used whenever the current Windows rotation is nonzero;
- current Windows angle `0` for ID15 (XML angle zero, auto-rotation zero), irrespective of Linux's flip-adjusted SDL rotation. `GameObject.cpp:168-170,349-350,565-573` controls a nonzero dynamic angle if generalizing;
- object-parallax offsets `(0,0)`: `ParallaxLayer.cpp:6-24` disables `mObjectParallaxEnabled`; `GameObject.cpp:21-34,173-185` initializes offsets to zero and only updates them when enabled. The level's `camera_properties xOffset/yOffset` are **camera target offsets**, not these object offsets;
- positive current alpha `.2`, subject to runtime changes. ID15 does not follow the camera, so its current cull position remains scaled XML position; other layers with follow flags require current post-`ParallaxLayer::Update` position (`ParallaxLayer.cpp:27-36`), not `followWorldX` used for the world matrix by `port/game/LevelScene.cpp:892-899,1374-1382`.

For ID15 at the stated backbuffer, `Camera2D::IsObjectInView` (`Game/src/Core/Camera2D.cpp:39-81`) can therefore be evaluated with **actual Windows** camera center `(cx,cy)`, width `1280`, height `720`, strict origin/bounds comparisons and zero object offsets. At `cy=2000`, the ID15 top `1625.469` is below camera bottom `1640`: Windows rejects it regardless of X. Holding X overlap, its upper-edge admission begins only when `cy < 1985.469` (strict edge), unless its origin is independently inside. This is a concrete correction to the *authored-coordinate* `cy≈2000` illustrative first-admission example in `PRIVATE_WATCHDOG_AUTOSCROLL_PRECULL_SOURCE_GATE_20261024T0335Z.md`; that example did not scale the Windows object.

## Camera mapping blocker

The Linux scene stores authored coordinates and `LevelScene::Draw` projects with `(worldX-cameraX, cameraY-worldY) × 2/3` into a 1280x720 destination (`port/game/LevelScene.cpp:1324-1325,1374-1405`). Its main loop initializes `cameraX/Y` from XML, then follows the authored player (`port/linux/main.cpp:534-544,1053-1061`), and passes a possibly shaken `drawCameraX/Y` to rendering (`:1549-1559`). This is a rendering transform; it is **not** proof that `Camera2D::m_position=(2/3)×(cameraX,cameraY)` in Windows.

Indeed the original loads XML camera `(0,3000)`, target offset `(0,-100)`, and `followY=false` (`waterfall_top.xml:3`; `Game/src/LevelProperties.cpp:24-53`). During level load, `GameObjectManager::Initialise` calls `FollowObjectsOrigin(m_player)` **before** scaling all objects (`GameObjectManager.cpp:183-201,438-465`); that call overwrites only followed axes (`Camera2D.h:43-53`). Consequently Windows Y initially remains **3000**, not `2000`; Linux also initializes Y from `3000`. Original X initially takes the unscaled player X, then `Camera2D::FollowTargetObjectWithLag` chases the *scaled* player plus target offset, zoom and lag (`Camera2D.cpp:175-233`). Original `m_width/m_height` are the camera's constructed backbuffer dimensions, while zoom changes the projection, not `IsObjectInView`'s cull extents (`Camera2D.cpp:10-32,39-81,262-279`). `Camera2D::Update` may also perturb `m_position` with shake before the manager cull (`:120-167`). Linux's authored camera and original's scaled-player camera thus need not have one fixed linear relationship during play. The target offset `-100` does not shift top-level Y when `followY=false`, but X target offsets/right-stick can change the active X trajectory.

An exact implementation can take an explicitly synchronized **Windows-equivalent camera center** snapshot and actual backbuffer size, then combine it with the object mapping above and the exact strict predicate in `PRIVATE_WATCHDOG_AUTOSCROLL_ELIGIBILITY_DESIGN_20261024T0337Z.md`. Reconstructing that center inside Linux requires separately reproducing Windows camera load/follow/clamp/shake/update order from a matched state; merely scaling `drawCamera`, scaling XML `posy`, using camera target offsets as object offsets, or using the Linux destination is incorrect. At the known initial top-level Y=3000, Windows ID15 is offscreen; that fact alone does not establish later active-gameplay admission or a matching phase history.
