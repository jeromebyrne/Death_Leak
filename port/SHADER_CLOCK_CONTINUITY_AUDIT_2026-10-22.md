# Shader clock continuity audit — 2026-10-22

**Verdict.** Windows has one process-lifetime `Timing::mTotalTimeSeconds`, initialized once and incremented on every rendered main-loop iteration by the *modified* delta (`Game/src/Core/Timing.cpp:9-15`, `Timing.h:21-22`, `Game/src/program.cpp:145-178`). `Game::Draw` supplies that clock to foliage sway, vertex wobble, and noise (`Game/src/Game.cpp:371-375`); `UIManager::Update` gives the same clock to its vertex-wobble default effect (`Game/src/UI/UIManager.cpp:83,145-162`). It does **not** restart on level entry. Linux instead zeros `LevelScene::visualTime_` on every `Load`, increments it in `UpdateVisuals`, and supplies it only to foliage (`port/game/LevelScene.cpp:125,732-733,1008-1011`). Door/boat/restart transitions load a fresh `nextScene` then move it into `scene` (`port/linux/main.cpp:606-620,960-975,990-1022`), so foliage visibly phase-jumps to zero at each transition, independent of the weather-factor issue. Even the first loaded level lacks preceding menu time. This is source-semantic, not a measured pixel mismatch.

## Affected effects and boundaries

- **Foliage sway: directly affected now.** Authored `effectfoliagesway` occurs in live level XML (124 instances across `Game/XmlFiles/levels`); `FoliageSway.fx:44-50` uses `Time` in both world-vertex sine phases. Linux `FoliageSwayWorldVertex` receives `draw.foliageSway.time = visualTime_` (`port/game/LevelScene.cpp:1008-1009`, `port/linux/SDLRenderer.cpp:383-420`). The weather global multiplier is a separate phase factor and is being handled in its own lane; do not reset the base clock on rain onset or change that factor here.
- **Pixel wobble: separate, also discontinuous at scene load.** Windows `Game::Draw` keeps `static` `pixelWobbleShaderTime` and `inReverse` for process lifetime, advances by `Timing::GetLastUpdateDelta()` **per draw**, reverses at strict `>10` and `<5`, and passes the resulting time to the effect (`Game/src/Game.cpp:379-401`). Linux zeros `pixelWobbleTime_` and reverse state on `Load`, increments them in `UpdateVisuals`, and passes the time to every pixel-wobble sprite (`port/game/LevelScene.cpp:125,735-738,1010-1011`; `port/linux/SDLRenderer.cpp:348`). The live XML has 171 `effectpixelwobble` entries. This clock must remain a separate triangular/reversing oscillator; substituting monotonically increasing total time is wrong. Existing `port/tests/scrolling_sprite_test.cpp:88-102` explicitly expects a reload reset, so that assertion would need replacement.
- **Other Windows total-time consumers: not yet equivalent Linux shader paths.** `BasicLightTexture_VertexWobble.fx` uses `Time` for vertex displacement; `Noise.fx` uses `fTimer` for UV distortion (`Game/src/Game.cpp:373-374`). UI's vertex-wobble effect also receives total time, including while paused. Live XML has four `effectnoise` objects (hot springs, cliff, waterfall cave, test); no live `effectvertexwobble` XML tag was found. Linux `LevelScene` currently recognizes only foliage and pixel-wobble effect tags (`port/game/LevelScene.cpp:490-510`), and `render::Sprite` carries only those two effect payloads (`port/render/Renderer.h:28-52`), so a clock-only patch cannot make the absent noise/vertex-wobble visuals appear. Preserve one process clock seam for their later port; do not bundle implementation of those effects into this fix.

## Timing contract and smallest next change

Windows' process clock advances while `Game::mPaused` is true: pause gates gameplay object updates, not `program.cpp`'s total-time increment or subsequent `Render`; UI remains drawn (`Game/src/Game.cpp:154-212,269-304`; `Game/src/program.cpp:169-178,293-318`). It also advances through menu frames. Damage slowdown uses `GetTimeModifier`, so the source clock is **not** unscaled wall time. `GetLastUpdateDelta` is set *after* `Render` (`program.cpp:169-177`), making the pixel-wobble oscillator consume the preceding rendered iteration's modified delta, unlike foliage's current total-time sample. A load can omit a render on a Linux transition due to `continue` (`port/linux/main.cpp:970-976`); that is a frame-routing difference to account for in exact comparison, not reason to reset the clock. Linux currently calls `scene.UpdateVisuals(dt)` even when paper/upgrade modals suppress weather updates (`port/linux/main.cpp:1064-1073`), which is directionally correct for shader animation; do not tie shader time to weather or `levelTime`.

**Bounded implementation:** own persistent shader timing in `port/linux/main.cpp` (or a small renderer-neutral process clock), outside `LevelScene` and outside weather. Advance its total once per frame using the existing frame delta, including menu and modal frames; use modified delta if/when Linux implements the Windows time modifier. Feed total time into the foliage draw payload, with no reset on `LevelScene::Load`, fresh `nextScene`, or weather change. Own the pixel-wobble time/reverse flag in the same persistent scope but update it by its **own** Windows draw-order rule (previous rendered frame's delta and strict 10/5 thresholds); feed it to `LevelScene` separately. Reset both only for a genuinely new process, not a game-over/menu return. Keep per-scene animation/particle elapsed values scene-local. Passing an explicit clock snapshot to `LevelScene::Draw`/its sprite assembly is preferable to static globals or copying clock state between every transition; it also makes menu and transition timing testable. Coordinate the narrow `LevelScene` edit with its current coding owner.

**Exact CPU discriminator (no GPU needed):** drive a fixed-step process sequence with 3 menu frames, load forest, draw a known nonzero-sway foliage sprite (and a pixel-wobble sprite), advance 4 gameplay frames, hold a modal for 2 rendered frames, then load a fresh `nextScene` and draw before and after its first update. Assert foliage's draw-carried time equals the process total at each point (no zero after either load, +2 steps over the modal); assert pixel wobble retains its previous oscillator state across the fresh-scene move rather than restarting at zero. Separately set pixel time to exactly 10, then one positive step to 11 (reverse activates), to exactly 5 while reversing (still reverse), and below 5 (forward activates), checking drawn time and direction. Test the transition through `main`'s clock-to-scene draw seam, not only a helper; replace the current reload-reset expectation in `scrolling_sprite_test.cpp`. A Windows-matched capture additionally needs identical frame index, preceding menu/pause duration, time modifier and weather factor; a single same-level static screenshot cannot discriminate this bug.

**Scope:** read-only source audit; no source/test edits, build, game/GPU/display run, checkpoint touch, or commit. Weather phase implementation is intentionally excluded.
