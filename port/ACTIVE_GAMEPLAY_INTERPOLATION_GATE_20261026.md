## Ownership and smallest candidate

The smallest visible gameplay state with a real prior/current pair is the player body/arm world position: `main.cpp` snapshots `worldX/worldY` from `motion.X/Y()` once per fixed update; `LevelScene::Draw` projects the player body and optional arm using `(playerX-cameraX, cameraY-playerY)` and emits their sprites in the authored player painter position. Camera X/Y is also updated by `FollowCameraWithTarget` in the fixed update, then camera shake is prepared there. Shadow, aim line, child X prompt, footstep/jump/landing sprays, combat, rain, and parallax are separate painter items or effects. Moving only player body/arm would visibly detach these from the player and can change occlusion against same-depth painter items. Moving the whole packet in screen space would shift HUD/postprocess and would not reproduce distinct parallax, UV scroll, camera bounds or shake. This is not an isolated safe transform family.

The opt-in `--refresh-slots` path runs only with no fixed update due. It replays a sealed `PresentationCommandPacket` whose sprite destinations are owned values recorded at the preceding ordinary draw; `Replay()` accepts no transform/alpha argument and targets the underlying renderer without sampling game state. The ordinary draw is made at current update state. Naively changing only replay geometry would make a fresh update present at current, jump backward on the next repeat, then move forward until the next update—cosmetic stutter. A correct one-update-latency interpolation would also need the ordinary draw to use the same previous/current pair and alpha, plus tagged player-adjacent command ownership and a coherent camera/effect policy. The current packet has no such semantic tags. Implementing a float lerp alone therefore cannot produce a safe refresh-independent visible presentation.
