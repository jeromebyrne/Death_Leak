Starting SolidLineStrip ID3 has material `grassground` (`:61-85`), whose sole active particle texture is `Media\\rock_particle.png` (`Game/XmlFiles/materials.xml:173-179`). Thus an eligible grounded strafe on ID3 has a concrete material particle asset; do not infer material from background artwork.
- XML `StrafeForward` has 20 frames in `_000`→`_019` order, with `sfx_type="footstep"` at **indices 0 and 10** (`Game/XmlFiles/animation/player_anim_default.xml:366-387`). `StrafeBack` has 20 frames in reverse `_019`→`_000` order, marked at **indices 9 and 19** (`:389-522`, marks at `:445,515`). A texture-name check alone is insufficient because both sequences reuse the same PNGs in opposite order. The source's ordinary horizontal-moving branch chooses a strafe sequence, calls `AnimateLooped`, invokes `DoAnimationEffectIfApplicable`, then stamps `mLastRunFramePlayed` every tick (`Game/src/GameObjects/Character.cpp:1006-1063`). Therefore the event is gated by a *new current frame index* and that frame's SFX flag, not by elapsed seconds or merely having an active strafe pose. The shared last-frame index also means a sequence switch onto the same numeric index may suppress its marked first-frame event; preserve/test that behavior rather than forcing one burst on each sequence entry.
- `DoAnimationEffectIfApplicable` requires current solid-line contact, its material, non-water material and a nonempty particle texture (`Character.cpp:1119-1146`). It requests **3** directed particles at `(player.X + m_direction.X*12, CollisionBottom()+17)`, character painter depth `kPlayer=3000`, direction `(-.5,.5)` when source movement direction X is positive and `(.5,.5)` otherwise, spread `.1`, culling bounds 1200×720, speed 2–4 source units/tick, life .3–.7 s, size 40–50 world units, gravity .5, nonlooping, brightness .8–1, life-size target 2.5, zero spawn spread X/Y, fade-in .15 and fade-out .7 (`Character.cpp:1147-1179`; depth in `Game/src/GameObjects/GameObject.h:40-49`). Source uses **stored movement direction `m_direction`**, not the visually aim-locked strafe facing; for an opposed-stick StrafeBack pose those signs differ. The port's existing Running emitter has these visual particle parameters (`port/game/LevelScene.cpp:1023-1061`), so duplicating its particle logic is unnecessary.
- Linux scene loading retains per-frame `sfx_type` booleans for both strafe sequences (`port/game/LevelScene.cpp:403-435`). `UpdatePlayerVisual` selects `StrafeForward`/`StrafeBack` in the grounded horizontal branch and advances them as loops (`:1087-1140`); its only call to `EmitRunningFootstep` is under `target == "Running"` (`:1139-1144`). The emitter itself uses `playerFacing_` for origin/direction (`:1032-1041`), but strafe selection sets `playerFacing_ = strafe.aimFacing` (`:1097-1103`). Reusing it unchanged in a strafe branch would emit from the **aim** side, unlike source `m_direction`. `SetPlayerFootstepContact` retains actual line segment/player XY (`:945-948`) and the existing renderer/scene particle path is already available. Thus the missing part is precise event dispatch plus movement-facing selection, not a new shader/asset/physics system.
