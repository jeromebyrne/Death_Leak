## Observed allocation and fence budget

- ID3 dimensions 1750×1313 RGBA = **9,191,000 bytes** (8.77 MiB). At Forest frame 120, `SDL_CreateTexture(RGBA8888, STATIC)` took **26.994 ms**, and its complete frame took **30.183 ms**. Native `glTexImage2D(..., RGBA8, null)` took **31.824 ms**, and that frame took **34.815 ms**. Flanking control frame-120 values were **21.656 / 21.642 / 21.613 ms**. Thus the initial allocation is the dominant extra Forest cost and native GL did not evade it. This is a single sample per allocation method, so it bounds neither worst case nor thermal variance.
- 21 consecutive 64-row-or-less uploads at frames 121–141 transferred the full 9,191,000 bytes, ≤448,000 bytes/frame. SDL update calls summed **11.198 ms** (maximum **1.895 ms**), plus **1.348 ms** total fence-submit overhead. Native GL subimage calls summed **4.848 ms** (maximum **0.281 ms**), plus **0.528 ms** fence-submit overhead. This is API/CPU time, **not** measured GPU execution time or a PBO result. No Forest upload frame exceeded 25 ms in either probe; the allocation frame did.
- Nonblocking `glClientWaitSync(..., timeout=0)` on each latest fence returned timeout through frame 142 and first reported already-signaled at **frame 143** in both probes, far ahead of first top draw at 411. The probe replaces its tracked fence each chunk and does not establish a bound on all earlier GPU work. No blocking fence wait was put on the game thread. Per-poll CPU maxima were **0.0082 ms** SDL and **0.0038 ms** GL. This proves eventual completion in these runs only; it does not prove a general backpressure/driver-fence budget.
- Forest frames 100–410 (291 samples): control A1/A2/A3 median **19.263/19.309/19.356 ms**, p95 **21.385/21.425/21.435**, maxima **21.656/26.265/29.803**. SDL probe median **19.307**, p95 **21.602**, max **30.183**; GL probe median **19.252**, p95 **21.694**, max **34.815**. All medians remain above the 16.667-ms 60-FPS target, and the preallocation introduces a ~30–35-ms Forest hitch.
- Waterfall-top entry frame 411 totals A1/B/A2/C/A3 **145.145/142.141/93.232/112.180/128.519 ms**. Because the diagnostic texture was not consumed, ID3 still decoded and uploaded on entry. These variable values overlap; **no top-tail saving is claimed**. A true reuse candidate would need SDL texture identity/lifetime integration and exact moving-camera first-draw visual parity.

## Live VRAM and output gate

NVE7 exposes GL max texture/renderbuffer dimension 16,384 and advertises `GL_NVX_gpu_memory_info`, but the prior dedicated-memory query returned an implausible **1,074,259,972 KiB** while reported total/available were **414,768/31,635 KiB**. Nouveau debugfs and per-process VRAM counters are inaccessible here; `/sys/class/drm/card1/device/mem_info_vram_{total,used}` is absent. No counter was calibrated against a known allocation and no defensible **live VRAM budget** is available. The only honest minimum increment is the level-0 payload size of 8.77 MiB; driver backing, extra copies, mip levels and evictions remain unknown.

Final frame-415 raw BMP pixel payload SHA-256 differed across **all five** arms, including three controls (A1 `9c5d95f11e30b7f6`, A2 `21f437955494eca4`, A3 `151a22a6a5695feb`, prefixes only). A diagnostic texture never participates in rendering, but the existing wall-clock visual variability prevents claiming strict cross-run RGBA equality; only identical scene transition and fixed-route input are established. No gameplay/visual parity is asserted for a texture-reuse implementation. No PBO/native-GL-to-SDL texture sharing was demonstrated.

## Decision and next distinct task

**Reject pre-resident full-ID3 allocation on the present evidence.** Moving the 27–32-ms allocation from first top draw into Forest yields a new ~30–35-ms Forest frame, one exceeding the 33.333-ms slow-frame gate, while top entry is unchanged without a risky renderer integration. Chunked transfer and nonblocking fence polling are relatively cheap in this particular sequence but cannot cure initial allocation, prove a driver-wide bound, or supply a calibrated live-VRAM budget. Therefore no production patch, commit, push, FPS gain, 8K/high-Hz or release acceptance follows.

Next distinct route: investigate **decode-only handoff** from the already feasible CPU worker into the existing synchronous SDL load path without advance GPU allocation, first measuring whether it removes a repeatable top-entry decode component under serial physical A/B/A and synchronized first-draw/moving-camera RGBA. Alternatively, establish an independently validated real VRAM counter and a low-latency driver allocation primitive before revisiting GPU residency. Do not repeat raw-sidecar/direct-upload substitutions already rejected.
