# Waterfall-top CurrencyOrb idle hover: implementation audit (2026-10-22)

Read-only source audit for `port/NEXT_WATERFALL_COMPOSITION_GAP_2026-10-22.md`. No source, tests, build, capture, GPU, or shared checkpoint was changed. This report is a proposed bounded implementation/verification contract, not an acceptance result.

## Source contract and current gap

- `Game/XmlFiles/levels/waterfall_top.xml:1270-1284` shows representative CurrencyOrb ID75 at `(-1335.014648, 2995)`, `kOrb`, with `sine_wave_props` active, X offset 0, Y offset 20, amplitude 2, randomized initial step, and alpha .75. The brief identifies 23 waterfall-top IDs through 115. `Game/src/GameObjects/CurrencyOrb.cpp:38-55` explicitly initializes the same sine settings for CurrencyOrb, with `rand()%999999` as initial step. The XML amplitude is the phase speed (radians/second), not a second spatial amplitude.
- `Game/src/SineWave.cpp:4-26` advances `step += 2*delta` and computes `(initialX, initialY + 20*sin(step))`; `Game/src/GameObjects/GameObject.cpp:187-205` writes both coordinates before rebuilding the transform. The authored center is the stable origin, not an incrementally displaced Y. The period is π seconds; extrema are ±20 world units, or ±13⅓ output pixels at the port's 2/3 scale for this `kOrb` layer (`port/game/LevelScene.cpp:893-918`).
- `Game/src/GameObjects/GameObjectManager.cpp:205-257,397` updates only updateable objects whose bounds meet its 4000×4000 camera zone unless `always_update`. `CurrencyOrb::Update` (`CurrencyOrb.cpp:138-203`) calls the base update before its idle/tracking state switch. `DoIdleHover` enables sine; `DoTrackPlayer` disables it (`:210-217`). Consequently, the state switch is not a reason to continuously bob an orb once tracking motion is active; a boundary frame may still have the prior sine update because of the call order.
- Port `SceneSprite` (`port/game/LevelScene.h:13-52`) has position, animation and collected flags, but no sine origin/phase/state. Loader (`port/game/LevelScene.cpp:429-452`) loads animation and assigns static XML XY. `UpdateVisuals` (`:664-756`) advances animation in the update zone without moving the orb. `Draw` (`:886-918`) projects `object.y`, so changing the sprite world Y is sufficient for its visual center and existing collection-distance check. No renderer, asset, rectangle, alpha, or depth change is needed.

## Bounded change sites and integration choices

1. **`port/game/LevelScene.h`, `SceneSprite`:** add orb-specific hover origin Y, phase, and (if XML-driven) offset/speed/active fields. Keep existing `x/y`, width/height, depth, animation frame, tint, alpha, `persistentId`, and `collected` semantics unchanged. Store the XML origin separately; never accumulate `sin` onto the previous `y`. A boolean for idle hover is useful only if there is a real tracking transition to drive it.
2. **`port/game/LevelScene.cpp`, CurrencyOrb load block around `:429-452`:** initialize the hover fields after XML XY is known. For this type, Windows `CurrencyOrb::Initialise` hard-codes X offset 0, Y offset 20 and speed 2 even though authored XML agrees; either parse `sine_wave_props` with an explicit fallback to those type constants or use those constants directly for the bounded waterfall-top slice. Seed each orb with a stable phase derived from level path and XML ID (not `std::hash`, whose cross-run stability is not guaranteed); distribute phases across `[0,2π)`. This is diagnostic determinism, **not** a claim to reproduce Windows' global `rand()` history or exact starting phase. Keep animation texture/frame selection, .75 alpha, `kOrb` depth and XML order untouched.
3. **`port/game/LevelScene.cpp`, `UpdateVisuals` around `:687-750`:** for a non-collected, updateable idle CurrencyOrb within the same current-position camera ±2000 zone used by orb animation, advance phase by `speed*dt`, then assign `y = originY + offsetY*sin(phase)`; X remains the authored center. Decide zone membership before moving on that tick, matching GameObjectManager's pre-update bounds test. Freeze phase and Y outside the zone; resume without catch-up. The bobbing `y` is the world position used by draw and collection, so collision distance follows the visible orb. Keep hover update independent of whether an animation has >1 frame. `Draw` remains state-free. Avoid touching `ParticleSpray` or the waterfall sheet auto-scroll path in the same loop.
4. **`port/game/LevelScene.cpp`, collection path `:562-578`:** `CollectCurrencyOrbs` currently checks 100 world units from sprite XY and sets `collected`; `ApplyCollected` suppresses persisted instances. The proposed updated XY naturally changes the check and neither collected nor restored-collected orbs should advance/display thereafter. Do not reset Y to origin on collection, which would create a final-position jump. The gameplay caller runs collection before `UpdateVisuals` in each frame (`port/linux/main.cpp:685,1071`), so collection uses the prior completed hover position; document this one-tick ordering in a focused test rather than silently making a draw-only bob that disconnects collision from visuals.

## Existing state mismatch to preserve/disclose

The source has a distinct small-orb tracking state: idle transitions inside 130 world units and subsequent `DoTrackPlayer` disables sine (`Game/src/GameObjects/CurrencyOrb.cpp:10-13,147-166,189-217`); collection uses 100 units after player collision (`:80-130`). The port's authored `SceneSprite` orbs have **no** tracking state or chase behavior: they stay static until immediate distance-based collection at 100 (`LevelScene.cpp:562-573`); only separately spawned orbs use `SpawnedOrb::trackingTime` (`:623-655`). Thus a hover-only patch can correctly stop on collection, but cannot honestly claim to verify the source's idle→tracking handoff. Do not tie authored hover to `SpawnedOrb` state or add a cosmetic 130-unit switch that freezes an orb without implementing the matching motion. If tracking is later ported, disable hover on the real state transition and hand off the **current** XY, without snapping to XML origin; account for the source base-update/state-switch ordering. Large-type orbs follow a different source path (`CurrencyOrb.cpp:100-130,153`); inspect target type before extending behavior beyond waterfall-top authored small orbs.

## Focused verification design (not run)

- Add a CPU-only `CaptureRenderer` test like `port/tests/orb_animation_zone_test.cpp`, loading waterfall-top with render filter on ID75 (and a second orb ID). Capture destination center and texture ID, with camera fixed at the orb and player far away. For a controlled injected phase 0, π/2, π, 3π/2, expect world-Y offsets 0, +20, 0, −20 (screen-Y signs invert), unchanged X/rectangle size/alpha/depth, and advancing animation texture on its own frame clock. For natural seeded phases, assert repeatability across loads and non-lockstep phases for two IDs; do **not** assert Windows random-phase identity. These phase probes should use independent expected screen coordinates, not re-evaluate the implementation's own formula.
- Advance a fractional phase in zone, move the camera wholly outside the update zone, advance time, then re-enter; assert both phase/position and animation clock freeze off-zone, resume without catch-up, and boundary decisions use the moving world Y. Verify redraws without `UpdateVisuals` do not advance motion.
- Test collection at a point whose distance straddles 100 when the orb is at Y+20 versus Y−20, using the actual current world Y. Check `CollectCurrencyOrbs` returns once, writes the existing persistent key, and `ApplyCollected` hides the same ID after reload. Specify whether collection is called before or after the test update, since the production loop calls it before. A future tracking test must use an actual authored-orb tracking implementation and prove current-position handoff/no teleport; it is **not** verifiable against today's port.
- For visual review only after implementation: fixed camera, known tick count and uncollected/nontracking ID75 plus another ID, then normal unfiltered painter view. Linux-only capture can prove motion and composition; matched Windows pixel parity requires controlled RNG history/phase, camera, timestep and player proximity. No pixel-delta improvement is claimed here.
