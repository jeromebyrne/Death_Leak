# Forest-1 ID21 original-Windows ordering source gate — 2026-10-23

## Verdict

The original Windows source predicts the same **ID19 → ID21 → ID22 painter relationship** as the current Linux experiment: ID19 is drawn before ID21 at the same middle-background depth, and ID22 is subsequently drawn at nearer depth. ID21 is authored as a full-alpha, ordinary light-texture sprite; its source texture is the dark tree strip. The existing Linux hide ladder establishes ID21 as the current-frame x320 occluder and exposes ID19 when it is removed. This audit establishes **source-order/alpha-path equivalence, not original-Windows pixel parity**. No Windows matched frame, D3D execution, or Windows sampled-alpha measurement was produced; no source or art correction follows.

## Original-source evidence

- The forest XML places ID19 at `kMiddleBackground`, alpha 1, `effectlighttexture`, `ground_blur.png`, horizontally flipped and repeat-X (`Game/XmlFiles/levels/forest_exploration_1.xml:307-321`). ID21 occurs later in that XML at the **same** depth, centered `(-678.915161,3736)`, native 1985×1238, alpha 1, `effectlighttexture`, `tree_strip_dark.png`, no flips, repeat-X true and fade-on-occlusion false (`:337-351`). ID22 occurs later at `kNearBackground`, alpha 1, with `tree_strip.png` (`:352-366`). `kMiddleBackground=5500` and `kNearBackground=5000` (`Game/src/GameObjects/GameObject.h:33-39`).
- The original loader walks sibling XML nodes in file order, pushes objects into a `std::list`, then sorts once using **descending depth only** (`Game/src/GameObjects/GameObjectManager.cpp:403-427,448-450,1021-1025`; list declaration `Game/src/GameObjects/GameObjectManager.h:116`; predicate `GameObjectManager.cpp:58-64`). Stable `std::list::sort` leaves ID19 before ID21 on their equal key, while the 5000-depth ID22 follows both. `GameObjectManager::Draw` iterates the resulting list and submits each visible drawable in sequence (`GameObjectManager.cpp:302-330`). This is an order claim, not a claim that every submitted texel covers x320.
- Original D3D10 depth comparison is `ALWAYS`, so ID21 is not rejected by the earlier ID19 depth value (`Game/src/Core/Graphics.cpp:77-107`). The render entry enables standard source-alpha / inverse-source-alpha blending before scene draw (`Game/src/program.cpp:293-317`; `Game/src/Core/Graphics.cpp:380-407`). The light-texture path binds the sprite texture and object alpha, then issues the indexed draw (`Game/src/GameObjects/Sprite.cpp:626-672`); its pixel shader multiplies sampled RGBA by light color and sampled alpha by object alpha (`Game/ShaderFiles/BasicLightTexture.fx:53-59`). Consequently, an opaque ID21 texture sample can replace ID19 in RGB; transparent/edge samples can leave or mix earlier color. The original ordinary sprite quad uses a single UV span for native-dimension repeat-X, since UV repetition is extended only when `!m_drawAtNativeDimensions` (`Sprite.cpp:194-235`). This does not establish exact filtered edge coverage.
- Original parallax factors for the middle and near layers are `(0.5,0.97)` and `(0.75,0.99)` respectively (`Game/src/GameObjects/GameObject.cpp:879-898`). The port's depth mapping and transform implement those same factors (`port/game/LevelScene.cpp:1250-1271`), and the predecessor source gate reports point-sampled ID21 PNG alpha 255 at x320/y440–520 but 0 at x640 for its measured **Linux** camera `(1248.98621,3400)` (`port/FOREST_MIDDLE_BAND_17_19_CURRENT_SOURCE_GATE_2026-10-23.md`). That asset probe is a prediction for corresponding coverage, not a Windows D3D texture-sample result.

## x320 exposure and remaining discriminator

The completed same-binary Linux GPU ladder reports `hide-22 → hide-22,21` changing all 61 x320 pixels in y440–500; then `hide-22,21 → hide-22,21,19` changes 60/61 there, while the earlier `hide-22 → hide-22,19` showed no x320 ID19 delta in y380–559 (`port/FOREST_ID21_OVERDRAW_GPU_DISCRIMINATOR_2026-10-23.md`; `port/FOREST_ID22_OVERDRAW_GPU_DISCRIMINATOR_2026-10-23.md`). Thus ID19 is exposed at x320 **in that Linux frame** only after ID21 is removed. Source ordering supports that result in Windows; it cannot prove the original Windows camera, filtering, postprocess, or displayed RGB would match.

**One next matched-frame discriminator:** when an original Windows D3D10 build/runtime is available, acquire a single state-locked render ordinal at a recorded 1280×720 (or explicitly mapped native) viewport and the equivalent measured camera/effect state, with lossless pre/postprocess identity recorded. On that same frozen ordinal, capture three ID-mask variants: `hide-22`, `hide-22,21`, and `hide-22,21,19`. Test incremental RGB changes at x320/y440–500 and retain x640/y440–500 as the ID19 exposure control, then compare those registered windows with the existing Linux ladder. A Windows x320 ID19 delta restored only after suppressing ID21 would confirm the predicted original painter occlusion; a different result would direct attention to original transform/coverage/effect state before any port edit. Full visual parity still requires a matched unmasked Windows/Linux frame, including postprocess, not merely this ablation. The current checkout lacks an executable Windows matched-state route (`port/FOREST_WINDOWS_MATCHED_FRAME_CURRENT_ROUTE_2026-10-23.md`).
