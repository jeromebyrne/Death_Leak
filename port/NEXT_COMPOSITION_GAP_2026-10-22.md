# Next forest/waterfall composition gap — waterfall splash spray (2026-10-22)

## Finding and priority

The largest remaining *source-proven, discrete* waterfall-top omission after the ordinary SDL scene min-filter slice is the authored **waterfall splash particle layer**. Waterfall-top defines three looping `waterfall_splash.png` sprays (IDs **49–51**, 120 particles total), including a 100-particle, 1000×3000-world-unit culling region at the main falls. The port explicitly loads only forest-1 oak-leaf spray ID47, so none of these waterfall sprays reaches its update/draw stream. This removes a moving, translucent waterfall/foreground element outright; it is more consequential in expected scene coverage than another local edge-sampling adjustment. The 1000×3000 dimensions are the emitter's culling bounds, **not** one giant splash quad; each source particle is a separate, variably sized textured quad. This is an omission proven by source paths, not a measured visible-area ranking or Windows/Linux pixel delta.

## Source-to-port evidence

- `Game/XmlFiles/levels/waterfall_top.xml:836-898` places ID49 at `(320.985,3530.298)`, `kGroundFront`, 100 particles, size 250–450, lifetime 1–1.5 s, downward direction `(0,-1)`, looping, 25% fade-in/out. IDs 50/51 sit at `(92.985,2709)` and `(572.985,2697)` in `kMiddleForeground`, 10 particles each, size 45–90 scaling toward 4×, lifetime 0.5–1.5 s. All use the shipped `Game/Media/waterfall_splash.png` and brightness 1. Their authored depth layers make them composition objects, not weather rain or the eight already-ported V-scrolling water sheets.
- Windows recognizes `particlespray` in `Game/src/GameObjects/GameObjectManager.cpp:693-695`; `ReadParticleSpray` passes XML count, position, depth, bounds, texture, motion, size, loop, brightness and fades to the load-time emitter factory (`:833-902`), then requests deferred warm-up (`:921`). The factory creates individual particles and a `ParticleSpray` (`Game/src/Particles/ParticleEmitterManager.cpp:598-705`). `ParticleSpray::Update` advances position, fade, size and loop (`Game/src/Particles/ParticleSpray.cpp:160-303`); `Draw` emits one quad per particle (`:128-157`), using `Particle.fx:52-59` for brightness and alpha. Windows updates non-always-update objects in its camera update zone and draws visible objects in depth order (`Game/src/GameObjects/GameObjectManager.cpp:221-257,302-330`).
- Port `LevelScene::Load` hard-gates its `ParticleSpray` branch to `forest_exploration_1.xml` ID47 and `continue`s for every waterfall emitter (`port/game/LevelScene.cpp:271-275`). Its existing spray update and depth-merge draw paths would otherwise process `particleSprays_` (`:665-670,868-879`); `port/game/ParticleSpray.h:12-99` already carries much of the needed per-particle model. The current waterfall gameplay report logs 81 ordinary sprites/zero unsupported assets (`port/CURRENT_WATERFALL_GAMEPLAY_VIDEO_2026-10-22.md`), but that count does not prove these omitted sprays rendered; the explicit loader exclusion does.

## Bounded implementation recommendation

First admit **waterfall-top ID49 only** to the existing `ParticleSpray` load/update/painter stream, using its authored texture, `kGroundFront` order, 100 count, spawn spread, speed/lifetime/size/fade, loop and source update-zone behavior. Reuse the current particle alpha/brightness and warm-up semantics; keep the XML bounds only for culling. Preserve the scene's existing sheet autoscroll, shafts, filtering, sepia and XML/art untouched. Then add IDs 50/51 in a second bounded pass *after* checking their unusual `speed min="5" max="-32"`: source factory deliberately takes `maxSpeed` when `maxSpeed <= minSpeed` (`Game/src/Particles/ParticleEmitterManager.cpp:670-674`), so normalizing/sorting that range would change their motion. Compare deterministic splash-only ID49 frames across time, then its unfiltered waterfall painter placement; matched Windows camera, timing, RNG and output size are needed for parity acceptance.
