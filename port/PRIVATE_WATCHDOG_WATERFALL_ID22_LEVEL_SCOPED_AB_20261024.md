# Forest→Waterfall ID22 level-scoped active GPU discriminator — 2026-10-24

## Verdict

The prior ID22 toggle's upper-field residual is **not caused by drawing Waterfall ID22 in the upper field**. An opt-in exact-level diagnostic isolated the two authored ID22s without changing simulation. At active Waterfall ordinal 638, hiding **Waterfall-top ID22 only** changed 114,393 final RGB pixels, all in y≥320 (bbox `[144,320,1280,687)` against a byte-stable visible control). The upper `[0,0,1280,320)` was byte-identical. Hiding **Forest-1 ID22 only**, while leaving Waterfall ID22 visible, changed the upper field (219,954 pixels above y=282) and matched the broad-hide arm's upper-field hash in one matched pair. Forest history/transition/compositing, not direct Waterfall ID22 coverage, is the first localized route divergence established here. This is a diagnostic counterfactual, **not a demonstrated original-versus-port bug** or reason to alter either authored sprite.

## Important repeatability limit and next discriminator

The first unfiltered `visible.bmp` differed from the two later byte-identical visible controls by 583,643 RGB pixels, including 217,311 above y=282. A second broad-hide `broad2.bmp` also differed from the first broad-hide by 582,892 pixels. Terminal gameplay state still matched. Therefore broad upper-field difference **cannot be treated as a fully deterministic quantitative effect in all runs**. The stable scoped pairs and exact upper hash match localize the main upper response to the Forest-hide route, but they do not identify whether the underlying mechanism is transition-history sampling, lingering renderer/GL state, frame-phase timing, or another stochastic presentation state. The source shows `SDLRenderer::BeginFrame` clears the scene each frame and `ApplyScenePostprocess` copies the scene for sepia; it does not prove which intermediate stage first diverges.

Find the earliest upper-field differing stage and resolve the intermittent unfiltered/broad hashes before changing rendering. A matched original D3D10 state/command/pixel packet is still required for a parity fix. No visual correction or original-Windows parity claim is justified by this Linux counterfactual.
