# Next forest-1 active-play effect after Running footstep: takeoff material burst (2026-10-22)

## Verdict and priority boundary

At inspected HEAD `e2c5adf1de43bf694185367b4702acb32c3e32bc`, the highest-priority **still-unported, source-backed forest-1 active-gameplay visual effect** found in this bounded audit is the player's **ten-particle material burst on a successful jump from a solid line**. It is player-centered and available on the starting forest ground during normal traversal. This is a priority judgment from trigger frequency, focal placement, and ten textured particles, **not** a measured Windows/Linux pixel difference or a claim that every jump emits: the source checks retained solid-line contact after moving the player up. The existing three-particle Running footstep spray was implemented at HEAD and GPU A/B-reviewed in `FOOTSTEP_QA_GPU_REVIEW_2026-10-22.md`; ID37/ID40 follow-lag is a separate, already audited temporal background issue. Neither is the proposed next effect.

The nearby **landing** path is also unported, but requires a drop of at least 300 source world units and has small/large variants (five or ten particles); ordinary takeoff has a simpler reproducible trigger and is the first slice. Roll/strafe frame-marked footsteps are likewise outside this takeoff finding. The burst is local and transient; it cannot explain a broad fog/foreground/color mismatch. No matched original-Windows frame or new capture was inspected.

## Exact source → forest XML → Linux chain

- Forest Player ID2 is at `Game/XmlFiles/levels/forest_exploration_1.xml:33-58`, `kPlayer`, with collision height `214.898743`; the starting SolidLineStrip ID3 is `grassground` (`:61-85`). `Game/XmlFiles/materials.xml:173-179` has one **active** `grassground` particle texture, `Media\\rock_particle.png` (the grass/wet alternatives are commented out). The port already loads material textures and retains line material in `port/game/LevelScene.cpp:258-274` / `port/game/LevelScene.h:62,140-141` for Running footsteps. Asset selection therefore need not be invented.
- Original `Character::Jump` checks `CanJump`, rejects water, applies upward velocity, then calls `SetY(m_position.Y + 10)`, increments jump count and calls `DoJumpParticles()` (`Game/src/GameObjects/Character.cpp:1239-1308`). `SetY` only assigns position (`Game/src/GameObjects/GameObject.h:116-119`); it does not itself clear the solid-line pointer. `DoJumpParticles` returns unless `IsOnSolidLine()`, the current strip, its material, and a nonempty particle texture exist (`Character.cpp:1311-1341`). Thus a normal grounded grass-line jump can reach the spray, while a coyote/wall/air jump must **not** be assumed to do so merely because `Jump()` succeeds. Original collision code can clear contact later (`Game/src/GameObjects/SolidLineStrip.cpp:130-138`). The exact input-vs-collision ordering should be retained in any implementation test.
- The source call is `CreateDirectedSpray(10, (X + directionX*10, CollisionBottom()+35), GetDepthLayer(), direction=(0,1), spread=.8, bounds=(1200,720), material texture, speed=1–1.5, lifetime=.8–1.2 s, size=32, gravity=.8, loop=false, brightness=.8–1, loopTime=1, scalesByLifetime=true, scaleTo=5, spawnSpread=(5,.2), fadeIn=.15, fadeOut=.9)` (`Character.cpp:1343-1367`; argument order `Game/src/Particles/ParticleEmitterManager.h:63-89`). The `CollisionBottom()+35` origin is evaluated **after** the +10 Y bump. Bounds are emitter culling bounds, not a 1200×720 rendered sprite. The source also plays a material footstep sound; this report concerns only the missing visual.
- Linux accepts jump in `port/game/PlayerMotion.cpp:75-91`, applies `y_ += 10`, then clears `grounded_` and resets timers; it reports only the **post-update** grounded segment to `LevelScene` at `:168`. `port/linux/main.cpp:633-635,680-681` passes jump input into `motion.Update`. Existing `LevelScene::EmitRunningFootstep` at `port/game/LevelScene.cpp:941-973` is called only from Running animation-frame entry (`:1047-1051`) and creates **three** particles with different direction, lifetime, size and scale. Targeted inspection of `port/game/PlayerMotion.cpp`, `port/game/LevelScene.cpp/.h`, and `port/linux/main.cpp` found no takeoff event or call with the source's ten-particle jump parameters. Consequently the current Running spray does not cover this burst; inferring jump contact from the post-update `grounded_` value would suppress the ordinary takeoff case.
