# Private Forest-1 walking/running body animation next gate — 2026-10-23 21:34 UTC

## Verdict

**One concrete, source-proven Running frame-selection gap remains:** the port advances ID2's Running body using the *new current-velocity-derived rate*, whereas the original advances using the Running sequence's *previous stored rate* and only then updates that rate from current velocity. A speed change during continuous grounded Running can therefore emit a different body PNG on the same rendered update. This is a CPU/source command-path finding, not a measured Windows pixel mismatch. The ordinary Still preceding-rendered-delta and slow-frame cap discrepancies have already been integrated/gated (`FOREST_PRECEDING_DELTA_INTEGRATION_2026-10-23.md`, `PRIVATE_BODY_SLOW_FRAME_COMMAND_GATE_20261023T1948Z.md`); this report does not reopen them. The strafe implementation reports already recognize advance-before-rate assignment for StrafeForward/Back; the **Running** branch is the overlooked exception.

## Exact source and port evidence

- Forest-1 ID2 is the animated Player using `player_anim_default.xml` (`Game/XmlFiles/levels/forest_exploration_1.xml:33-46`). Authored Running starts at 60 fps, clamps to 4–60 fps, and frames 000/001 are distinct PNG paths (`Game/XmlFiles/animation/player_anim_default.xml:188-207`). Player overrides the movement animation multiplier to 2.65 (`Game/src/GameObjects/Player.cpp:72-82`).
- Original `Character::UpdateAnimations` enters/selects Running at `Game/src/GameObjects/Character.cpp:1006-1031`, calls `bodyPart->AnimateLooped()` **before** `SetFrameRate` at `:1033-1050`, then selects `CurrentFrame()` at `:1054-1056`. `AnimationPart::AnimateLooped()` reads the sequence's currently stored rate and preceding rendered modified delta, advancing at most one frame (`Game/src/Animation/AnimationPart.cpp:160-196`). `AnimationSequence::SetFrameRate` mutates and clamps that stored rate (`Game/src/Animation/AnimationSequence.h:15-25`); `SetSequence` restarts the cursor/elapsed but does not reset the sequence's rate (`Game/src/Animation/AnimationPart.cpp:142-157`). Thus a continuing Running tick uses the rate assigned on the *previous* Running tick; on first-ever Running entry it uses XML 60.
- Port `port/game/LevelScene.cpp:1248-1256` resets cursor/elapsed on sequence entry, computes Running `rate=clamp(abs(vx/60)*1.8*2.65,min,max)` immediately, and uses that freshly computed `rate` as `advanceRate` at `:1257-1264`. Only strafe sequences use the stored `sequence.currentRate` and update it after advancing (`:1275-1276`). The port therefore lacks source's one-Running-update rate lag and rate persistence across exit/re-entry. Prior-rendered delta is correctly wired at `:1259`; changing that clock is not this gate.
