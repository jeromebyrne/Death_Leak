# Next executable visual discriminator — waterfall Y-flow cadence (2026-10-23)

**Nomination:** the active waterfall-top sheets' **one-render lead in vertical texture-scroll phase** is the strongest remaining *currently CPU-discriminable* source/port visual contract after excluding the attributed forest ID15 shaft and the raft-mip question blocked on an actual Windows bound-SRV descriptor. This is a narrow temporal discrepancy, not an explanation for forest darkness or a measured Windows/Linux image error. It was noted as a caveat in `WATERFALL_AUTOSCROLL_IMPLEMENTATION_2026-10-22.md`; the current working tree still has the mismatch. Unlike raft mips, its first-frame and variable-delta outcomes are decidable directly from the original source and an isolated CPU draw-spy. Eight large, translucent `waterfall_4.png` curtains make the phase visible in active waterfall-top play, though pixel magnitude is unmeasured.

## Exact chain

- `Game/XmlFiles/levels/waterfall_top.xml:109-355,563-585` authors ParallaxLayer IDs **6/7/10/13/14/15/16/31** with `autoscrolly=true`, speeds 7/9/11, alpha 0.3–0.5, and either ordinary light texture or pixel wobble; ID6 at `:109-137` is a concrete 3303-world-unit-high, alpha-0.5, speed-7 sheet; ID13 at `:261-289` is a speed-11, alpha-0.3 wobble sheet. These are in the active falls, not dormant X-autoscroll.
- Windows `Game/src/GameObjects/ParallaxLayer.cpp:114-150` advances V **in Draw** by `scaledYSpeed * .001 * Timing::GetLastUpdateDelta()/GetTargetDelta()` and carries the prior UV; `:223-231` scales positive speed by backbuffer-height/1080. `Game/src/program.cpp:115-117,149-177` sets target 1/60, runs Update, increments total time, **renders, then** stores this iteration's modified delta as LastUpdateDelta. The first rendered sheet therefore advances by zero; each later render consumes the preceding completed render iteration's delta. A repeated Draw would advance again in Windows, but ordinary gameplay draws once per render.
- Current Linux `port/game/LevelScene.cpp:397-402,829-836,1267-1271` loads the Y flag/speed, advances `autoScrollYPhase` in `UpdateVisuals` using the **current** `dt` before Draw (including modal frames), then submits that phase as `uvShiftY`. At a fresh 1280×720 waterfall scene and fixed 1/60 update, ID6's first displayed phase is `.007*(720/1080)=.0046667` cycle versus Windows zero; ID13's is `.011*(720/1080)=.0073333` versus zero. At the nth steady rendered frame the lead remains one such increment, modulo one. This is a UV-phase prediction, not a predicted RGB delta; shader sampling, texture content, flips and compositing determine visibility. At a dt change, the lead tracks the **current** versus preceding modified delta, so the difference need not stay one constant increment.
