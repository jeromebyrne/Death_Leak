# Forest active-play visual behavior gap — controller strafe pose (2026-10-22)

## Decision and evidence boundary

At HEAD `a6dddb5670ea0a2fd66e9e38ebbf5259567a0f00`, the highest-priority **distinct, non-renderer, source-backed missing visual behavior** found in this bounded forest-1 audit is the player's **controller-strafe body pose and aim-locked facing**. The original switches between authored `StrafeForward` and `StrafeBack` animation while moving with the left stick and aiming against/with that movement using the right stick. Linux has the source art but neither admits those sequences into its player animation state nor samples right-stick aim for a strafe state; it continues showing `Running` and faces travel direction. This is a sustained, focal-player pose difference on a normal combat/traversal input, not a broad scene-composition or renderer defect. Its priority is based on recurrence and full player-body substitution, not measured pixel coverage. The right+fire scripted `B` route is **not** proof of strafe: it supplies no independent right-stick direction.

This is separate from implemented firing arm, aim line, ordinary Running footstep, jump/landing material bursts, forest orb trails, and the reserved fractional parallax UV/fog-mip lanes. Roll/strafe footstep omissions are smaller follow-ons, not this report's primary visual slice. No current matched original-Windows forest strafe frame or Linux strafe capture was found; the statement is a code/asset-path omission, **not** pixel parity or a claim about the visible current right+fire video.

## Exact original → authored art → Linux evidence

- Forest-1 Player ID2 uses `XmlFiles/animation/player_anim_default.xml` (`Game/XmlFiles/levels/forest_exploration_1.xml:33-48`). Its body has `StrafeForward` and `StrafeBack` sequences at `Game/XmlFiles/animation/player_anim_default.xml:366-387` and `:389-522`; the forward sequence uses 20 `Media/characters/player/strafe_default/strafe_default_000.png` through `_019.png` frames, and the reverse begins at `_019.png`. The 20 corresponding PNG assets exist under `Game/Media/characters/player/strafe_default/`. The first/eleventh forward frames are marked `sfx_type="footstep"` (XML `:367,377`); the reverse has its own marks (e.g. `:445,515`). These are a different body texture sequence, not a recolor of Running.
- Original `InputManager::ProcessStrafing_gamepad` (`Game/src/InputManager.cpp:449-501`) clears strafe by default, then requires right-stick activity, no roll/fall/melee restriction, and **opposed X directions** between right and left sticks: right aim + left travel sets `mStrafeDirectionX=+1`, left aim + right travel sets `-1`. It also changes camera target offset X. `ProcessLeftRightMovement_gamepad` uses left-stick movement (`:162-185`). The gamepad action order calls aim/fire then strafing (`:578-591`), so the implementation must not silently assume aim, firing and pose are all sampled in an interchangeable order.
- Original `Character::UpdateAnimations` selects `StrafeBack` when `mStrafeDirectionX != m_direction.X` and `StrafeForward` otherwise, inside the moving, non-side-colliding branch, then loops the authored body sequence at motion-derived rate and invokes per-frame effects (`Game/src/GameObjects/Character.cpp:1005-1062`). `Character` flip/facing follows `mStrafeDirectionX` during strafe, not travel X (`:1553-1575`). Source `AnimationPart::SetSequence` restarts at frame 0 and `AnimateLooped` advances at most one frame/update (`Game/src/Animation/AnimationPart.cpp:142-162,168-197`). On the ordinary opposed-stick moving case, movement direction and aim direction differ, so `StrafeBack` is expected; `StrafeForward` remains an authored source branch whose reachability depends on direction/inertia state and should be tested separately rather than assumed for that ordinary case.
- Linux `SDLRenderer::KeyDown` maps left stick X only into `Left`/`Right`; the switch has no `SDL_CONTROLLER_AXIS_RIGHTX/RIGHTY` case (`port/linux/SDLRenderer.cpp:544-560`). `main.cpp:600-650` reduces play input to movement direction and sets `facing` directly from it, then passes that facing to `LevelScene::UpdatePlayerVisual` (`:1076-1085`). The player loader's explicit body-sequence list excludes both Strafe sequences (`port/game/LevelScene.cpp:403-427`). `UpdatePlayerVisual` therefore selects `Running` for grounded horizontal motion and receives no strafe/independent aim state (`:1078-1118`); draw flips from `playerFacing_` (`:1223-1251`). Targeted source search found no `StrafeForward`, `StrafeBack`, or right-stick axis use in `port/game`/`port/linux` beyond generic left-stick axis polling.

## Bounded fix seam and acceptance

Add an explicit **right-stick X aim/strafe input state** at the SDL input boundary and carry the source-eligible strafe/facing state through `main.cpp` into `LevelScene::UpdatePlayerVisual`. Load only the two authored body sequences alongside the existing player sequences; choose forward/back from the original movement-versus-aim/facing condition, restart on sequence entry, loop at the source movement-derived rate, and draw within the existing player painter slot with the aim-locked horizontal flip. Keep the implemented firing arm, aim-line clock, ordinary Running state, XML/art, material sprays, and renderer blending untouched. Camera aim offset, projectile direction, right-stick Y, and footstep effects need separate coordinated gameplay contracts; do not describe a body-only patch as complete strafing parity. In particular, `main.cpp` currently has one `facing` variable shared with other systems, so avoid changing projectile/motion behavior incidentally until that contract is explicit.

Focused CPU/render-spy acceptance with a forest-1 Player ID2 scene at grounded moving state: (1) neutral right stick selects Running with movement-facing draw; (2) active right aim with left movement and active left aim with right movement enter `StrafeBack` in the ordinary opposed-axis case (and `StrafeForward` only in a separately constructed eligible same-direction state), keep visible facing locked to aim, and advance from authored frame 0 to 1 without texture fallback; (3) stopping aim, rolling, melee, side collision, or loss of horizontal motion exits strafe according to source priority; (4) sequence re-entry restarts and held frames do not over-advance; (5) current Running footstep and firing-arm behavior remain unchanged when not strafing. A Linux same-camera draw-spy/isolated player crop can prove the previously absent pose is rendered; a physical-GPU clip is optional downstream, not needed to establish the source omission. **A matched Windows frame/short clip is required for a visual-parity claim**, with the same controller axes/eligibility, direction state, player XY/velocity and animation frame, effective camera/viewport, fire/arm state and simulation time. Existing Steam screenshot 14 and Linux forest clips lack this input/phase match and cannot adjudicate pose pixels.
