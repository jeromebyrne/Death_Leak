# Next forest visual discriminator after all-flip rotation (2026-10-22)

## Finding and priority

The next bounded **forest-1 active-gameplay** discriminator is a one-update X-position lag of the two broad, camera-following foreground `ParallaxLayer`s, IDs **37** (lower shrubbery) and **40** (top trees). This is a reproducible source/port *geometry-state* gap during camera motion, not a conjectural color/brightness adjustment or a claim that either layer's authored dark artwork is wrong. The current Linux draw uses the current camera for both quad center and UV phase; Windows builds a cached world matrix from the preceding layer position, then changes that position to the current camera, while its draw computes UV phase from the current camera. Both IDs recur across the full forest route, so this is a wider-area active-frame discriminator than the already fixed player knife/arm/leaf-alpha details. Its normal-frame pixel magnitude is **not measured**; do not call it a high-impact visual fix until the trace and a matched frame justify that ranking.

This finding agrees with, and narrows the next action from, `port/NEXT_POST_ROTATION_VISUAL_GAP_2026-10-22.md` and `port/PARALLAX_FOLLOW_TEMPORAL_TRACE_2026-10-22.md`. It does not reopen all-flip rotation, ID15 shaft art, ID37 alpha, or the already interleaved combat painter.

## Reproducible code-path evidence

- Authored `Game/XmlFiles/levels/forest_exploration_1.xml:612-635,666-689`: IDs 37/40 are 2048-wide, alpha .95, `kMiddleForeground`, `always_update=true`, `followcamx=true`, `followcamy=false`, unflipped, with camera-X UV coefficient .000690. They have Y=2800 and Y=4100 respectively. Their X follow is not conditional on visibility.
- Windows `Game/src/GameObjects/ParallaxLayer.cpp:26-35` calls `Sprite::Update` before assigning `m_position.X=camX`. `Game/src/GameObjects/Sprite.cpp:358-366` reaches `DrawableObject::Update`, and `Game/src/GameObjects/GameObject.cpp:202-212` constructs `m_world` using the **pre-follow** `m_position`. `Game/src/GameObjects/ParallaxLayer.cpp:37-83` then computes draw U from the **current** camera. `Game/src/GameObjects/Sprite.cpp:626-637` uploads the cached matrix. `Game/src/GameObjects/GameObjectManager.cpp:221-257,302-330` separates update and draw passes, so there is no intervening matrix rebuild in this path.
- Linux `port/game/LevelScene.cpp:945-958` chooses `worldX=cameraX` in the draw pass for both layers; `:978-985` projects that current X and derives U from that same current camera. Its visual update pass has no prior-follow-position cache (`:732-749`). The in-progress all-flip angle helper at `:1009-1012` does not affect these zero-rotation, unflipped layers.

At 1280×720 and the port's 2/3 world scale, hold the camera at X=1000 for two updates, step it to X=1100 for one update/draw, then hold X=1100 for another. On the step frame, Windows' cached world X is 1000 and its layer screen center is **573.333**; Linux's draw X is 1100 and its center is **640**. Windows left/right U are **0.241 / -0.759** from the new camera (one-span source convention); Linux's equivalent positive SDL phase is **+0.759**. On the next held frame, both centers become 640 while UV phase stays at the new-camera value. The 66.667-pixel displacement is a deliberately large **CPU test-vector contrast**, not an observed gameplay-frame error. On ordinary motion it scales as `-(cameraX[n]-cameraX[n-1])*2/3` in screen X. Since neither ID follows Y, this gap cannot explain a persistent full-width horizontal dark band or a changed vertical extent.
