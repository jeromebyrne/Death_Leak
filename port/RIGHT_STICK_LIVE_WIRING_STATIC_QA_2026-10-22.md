# Right-stick live wiring: bounded static QA (2026-10-22)

Scope: current uncommitted `port/linux/main.cpp`, `SDLRenderer.cpp`, and `PlayerMotion.{h,cpp}`, compared with the original Windows input/impact path. Read-only inspection only; no source/build/GPU/status change. This report does not repeat the separate right-stick × fractional-parallax integration-risk audit.

## Findings

1. **High — live right-stick aim moves the camera, but cannot fire or aim a knife.** `SDLRenderer::ControllerAxes()` exposes RX/RY (`port/linux/SDLRenderer.cpp:563-568`), and `main` feeds that sample to the camera target (`port/linux/main.cpp:699-700`). Yet live `fire` is exclusively the Down key/controller Down button (`main.cpp:687-693`; `SDLRenderer.cpp:551-552`), and `Combat::Update` creates player shots using only `facing` with zero vertical velocity (`port/game/Combat.cpp:389-397`). Windows uses active RX *or* RY to establish a normalized aim direction (`Game/src/InputManager.cpp:374-395`) and, with the same active-stick test, fires `FireWeapon(currentActions.mAimDirection, ...)` (`:398-416`; call order `:582-589`). Repro by source: hold only the right stick up in living gameplay: the port's next camera target pans vertically, but no knife fires; pressing Down fires horizontally, not toward the stick. The right-stick camera feature is therefore visible without its associated authored action. Handoff: route stick-active fire and normalized aim through combat while retaining the existing keyboard fallback; validate diagonal/up/down shots and the camera's one-tick follow order together.

2. **Medium — impact recovery gates the camera X target but not player control, producing a post-landing camera/player mismatch.** New `PlayerMotion` state is set for qualifying landings and held for approximate soft/hard durations (`port/game/PlayerMotion.cpp:192-215`, `:12-15`), then passed as the right-stick X-hold gate (`port/linux/main.cpp:699-700`). But the same gameplay tick still feeds movement/jump directly to `motion.Update` (`main.cpp:611-613,668-670`); `PlayerMotion::Update` applies direction acceleration and accepts jump without checking `impactRecovery_` (`PlayerMotion.cpp:64-90`). Windows blocks left/right movement and jump during both recovery flags (`Game/src/InputManager.cpp:162-170,202-210`), while active-stick camera X is held (`:462-472`). Repro by source: land after a >300-unit drop while holding left stick and right stick; camera X target remains pinned for recovery, but Linux player can move/jump during it. Handoff: either implement recovery control lockout with an explicit input-order contract, or document this as a deliberate gameplay divergence before treating the camera gate as parity.

## Checked, no additional issue identified

The current seam samples axes once after SDL event polling (`main.cpp:453-455`), follows with the stored target before motion (`:656-670`), writes the next target after motion/combat (`:693-700`), and resets it on the successful scene replacements/story clear (`:539,629,969,1000,1033,1058`). SDL right-Y conversion, strict deadzone, neutral reset, disconnected hold, and active-stick Y-before-X/X-hold behavior reside in `port/game/LevelScene.h:81-106` and match the cited Windows input order (`Game/src/InputManager.cpp:374-395,449-503,582-589`). These are source observations, not a live controller or pixel-parity result.
