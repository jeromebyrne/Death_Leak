# Private forest-intro next visual gap — gameplay HUD film initial phase (17:48, 2026-10-23)

## Bounded finding

The next distinct source-backed, unowned **HUD** mismatch is the first active `game_hud` film-frame selection on a fresh Forest-1 intro. The Windows source initializes `26_scratch_anim` at frame 0 but advances it to frame 1 on its first active UI update whenever `timeGetTime()>90 ms`; the Linux ordinary-gameplay HUD deliberately draws frame 0 on its first draw and only starts its 90-ms clock then. `timeGetTime()` is the Windows multimedia system uptime clock, not time since this widget was loaded, so the condition is overwhelmingly expected in a normal booted session; source evidence alone does not establish a particular captured Windows frame or pixel-error magnitude. This is **one frame-phase discrepancy**, not a missing film overlay or an alpha/order change. It spans the viewport at authored alpha 0.2 and can contaminate same-frame forest-intro visual comparisons even when camera, foreground, and burst agree.

This specific startup deviation was already acknowledged, but not resolved or owned, in `port/GAMEPLAY_HUD_FILM_OVERLAY_SOURCE_QA_2026-10-23.md` and `port/GAMEPLAY_HUD_FILM_GPU_REVIEW_2026-10-23.md`; the former film implementation explicitly chose frame 0 at first draw. It remains a narrower actionable residual after the overlay itself was integrated. This audit does not re-nominate held-pull shake, X prompt, or blood-burst fade/flip and does not claim a novel discovery.

## Deterministic CPU validation and bounded later fix

Use a tiny clock-injected frame-selector/recording-renderer test, without GPU, display, shared build, or changes in this audit. Feed the Windows oracle `last=0,index=0,fps=11` and first active UI-update timestamps 90 ms and 91 ms: expect first draw indices 0 and 1 respectively. At 91 ms, expect exactly one advance even if the timestamp is much later; a next update at `last+90` stays at 1 and at `last+91` advances to 2. Feed Linux's current first-draw rule the same timestamps and assert it emits 0 at 91 ms, exposing the mismatch. Record the four concrete texture paths and assert selected frame 1 is `film_frame_2.png`, with unchanged full-viewport destination, byte alpha 51, postprocess-before-film and film-before-bars/meter order. Keep the `sea_2` and menu film selectors out of scope. A later owner can initialize the gameplay film selector from a common monotonic epoch/first active UI-update time rather than the first draw, but should first decide/document the desired Windows-system-uptime analogue and retain single-step strict-threshold semantics; avoid a fixed “always frame 1” hack for the theoretical <=90-ms case.

This CPU gate proves command/phase parity under controlled clock inputs, **not** original-Windows pixel parity. A same-state original Windows intro frame with observed film index/clock and a lossless Linux frame is still needed before claiming visual acceptance.
