# Player firing-arm prior-delta CPU gate — 2026-10-23

## Verdict

A discriminating, executable `LevelScene` command-spy fixture **cannot be added against the present API without a production seam**. `UpdatePlayerVisual(float dt, ...)` receives only one delta and adds that same value to the body clock (`LevelScene.cpp:1137`) and arm clock (`:1166`). `main.cpp:1107-1109` supplies current `dt`; the preceding-rendered modified delta is neither passed to this method nor publicly settable. A test that passes `.001` as `dt` would merely change the current delta and pass on the known-wrong implementation; a helper-only arithmetic test would not exercise the integrated command path. A test expecting a future extra argument would not compile now. Accordingly this lane wrote **only this fixture specification**, not a speculative `port/tests/player_arm_prior_delta_cpu_test.cpp`.

The shared tree is already dirty in `LevelScene.cpp/.h`, `main.cpp`, `integration.sh`, and other files, including right-stick aim-line edits to this exact method. I made no edits to production code, existing tests, or shared status; did not build, run, use GPU/Xorg, capture, commit, or push. This is a source/API feasibility finding, not an executed parity result.

## Source-backed contract

Original `Player.cpp:467-475` restarts and advances the arm on a successful shot; `Character.cpp:1098-1111` advances again if unfinished during that update, then may finish it on body-sequence change. `AnimationPart.cpp:201-237` adds `Timing::GetLastUpdateDelta()` separately on each call, subtracting one frame period at most per call. `Timing.cpp:8` initializes that slot to zero; `program.cpp:149-177` assigns modified delta after `Render`. Forest Player ID2's XML references `player_anim_default.xml`; its arm Still and Running sequences have ten frames at 30 fps (`player_anim_default.xml:1483-1514`). The current port preserves the two calls and arm-before-body draw but uses current `dt` for both (`LevelScene.cpp:1163-1185,1307-1312`).
