# Raft, right-hand shaft, and foreground parallax: bounded source audit (2026-10-22)

## Verdict

The forest-1 XML deliberately uses **different horizontal-flip flags** for its three raft sprites: ID11 and ID57 are flipped, ID58 is not. The right-hand pale shaft is **ID15, `sun_shaft_2.png`, unflipped**; the corresponding left-side ID14 is flipped. ID15 is an ordinary light-texture Sprite beside the right LevelTrigger ID13, not a special exit-beam implementation. Therefore an apparent flip in an unmatched Linux/Steam view does **not** justify changing those authored flags or textures. The original and port do have a more basic **source-semantic transform-order discrepancy** for flipped and/or rotated ordinary sprites: Windows builds `World = Translation * Scale * Rotation`, while SDL draws a centered destination with local flip/rotation about that center. Its visual consequence for these IDs needs a controlled original-Windows discriminator before a broad correction, because the literal Windows matrix composition moves object centers as well as local corners. This audit is source-only, with no new build, capture, or acceptance claim.

Foreground speeds are *not* a demonstrated defect: for ordinary depth-parallax sprites the current Linux formulas exactly reduce to Windows' camera-relative X/Y displacement. The two forest-1 `ParallaxLayer`s at foreground depth instead follow camera X and scroll texture UV at 0.000690 per camera-world-unit; the port represents that different mechanism. Their artwork can appear to move at a different speed than ordinary foreground trees by design.

## Narrow transform-order discrepancy and caution

Windows source uses centered quad vertices (`Game/src/GameObjects/Sprite.cpp:215-223`), applies horizontal reflection as `m_matScaleX *= -1` (`:89-96`), and on each update resets world to identity, then multiplies **translation, scale, rotation in that order** (`Game/src/GameObjects/GameObject.cpp:160-164,202-210`). The shader evaluates `mul(input.Pos, World)` then View/Projection (`Game/ShaderFiles/BasicLightTexture.fx:37-46`), and the light-texture draw uploads this world matrix (`Sprite.cpp:626-637`; `Game/src/Effects/EffectAbstract.h:39-42`). By contrast, Linux uses an unmodified authored center as the SDL destination center and passes `SDL_FLIP_HORIZONTAL` plus `rotationDegrees` to `SDL_RenderCopyExF` with a null pivot (destination center), `LevelScene.cpp:829-855`, `SDLRenderer.cpp:185-190,229-233`.

Under the source's row-vector shader expression, the Windows object center follows `T*S*R` (scale/reflection and rotation also act on the translated center), while SDL holds the center at T and applies local `S*R` around it. This is concrete **matrix-operation non-equivalence**, not merely a possible mistaken angle sign. It affects raft IDs 11/57/58 and rotated shaft ID15, but not the unrotated/unflipped ordinary foreground speed derivation above. The practical size/direction is unexpectedly large if taken literally (for example ID11's center X becomes negative after its X reflection), so do not present a predicted Windows screenshot position as verified: the available Steam JPEG has no recorded camera or original runtime matrix values, and existing Linux captures are unmatched. Check actual Windows shader/runtime behavior before altering the port globally; a matrix-layout/upload assumption or a reference-build/level distinction would change the observed conclusion. The prior raft audit explicitly left combined flip+rotation unresolved; this source comparison narrows that uncertainty to transform composition, without establishing image parity.

## Prioritized fix gate

1. **First, instrument or capture the original Windows build** at one forest-1 frame: log camera XY/zoom, viewport, and the final world matrices plus transformed centers/corners for IDs 11, 57, 58 and 15. An isolated lossless render of those IDs is ideal. Match the Linux camera and isolate the same IDs using the existing diagnostic ID filter (`port/game/LevelScene.cpp:61-83`). This directly distinguishes local flip/rotation from translation-inclusive composition. A static hand calculation alone should not override the contradictory qualitative Steam composition.
2. If Windows runtime confirms translation-inclusive `T*S*R`, make a **scoped transform helper** in `port/game/LevelScene.cpp` for ordinary sprites that projects the Windows-transformed center and corner orientation before calling SDL (or draws a four-corner geometry path if SDL's single pivot/flip cannot represent it exactly). Verify ID11 (flip only), ID57 (flip+rotation), ID58 (rotation only), ID15 (rotation only), and a nonrotated/unflipped ground control at identical camera. Preserve authored XML/texture/flip flags and depth painter order. Do not bundle this with parallax-speed tuning.
3. If runtime matrices instead demonstrate centered local transforms, close the flip/shaft issue as an unmatched-reference appearance question. Retain foreground speed constants; only investigate a specific parallax ID if paired Windows/Linux motion shows a measured drift. A two-camera-position match can measure `ΔscreenX/ΔcameraX` for ordinary far/middle/near FG (`-1.1/-1.3/-1.8`), while ID37/40 require tracking texture landmarks, not quad bounds.

No source, asset, build, GPU capture, shared checkpoint, or status file was changed by this audit.
