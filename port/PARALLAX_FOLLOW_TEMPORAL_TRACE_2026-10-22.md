# Parallax follow temporal trace — forest-1 IDs 37/40 (2026-10-22)

## Verdict

The source-code phase split is real for an ordinary, unpaused update/draw: Windows constructs each layer's world matrix from the **position entering** `ParallaxLayer::Update`, then assigns current camera X to `m_position.X`; its draw sets U from current camera X. The Linux port computes destination and U from the current draw camera X. Thus Windows geometry lags its follow assignment by one object update, while the texture UV does not. This is a deterministic code-path difference, not a measured Windows pixel mismatch. It cannot by itself explain a *static, broad horizontal black band*: there is no Y displacement for either layer, and after a held camera's next update the geometry converges. During continuous movement it can recur as a small X displacement proportional to the preceding camera step, affecting texture registration and possibly the left/right edge, not the band's vertical extent or authored opaque-black pixels.

## Evidence and assumptions

- Both forest-1 XML objects are `ParallaxLayer`, `always_update=true`, `followcamx=true`, `followcamy=false`, `cameraparallaxmultiplierx=0.000690`, unflipped, and `effectlighttexture`, alpha 0.95: `Game/XmlFiles/levels/forest_exploration_1.xml:612-635,666-689`. ID37 is 2048×512 at Y=2800 (`shrubbery.png`); ID40 is 2048×677 at Y=4100 (`trees_top.png`). No sine wave or auto-scroll is active. Their initial XML X=1316.985352 is overwritten only *after* the first world-matrix update; the first draw after loading can therefore have a larger special-case offset than the steady A/B/C trace below.
- `Game/src/Game.cpp:154-163,170-180` follows/clamps the camera before manager update in normal gameplay. `GameObjectManager.cpp:221-257` updates `always_update` objects; `:302-330` draws them in a separate pass. `ParallaxLayer.cpp:26-35` calls `Sprite::Update` before assigning camera X. `Sprite.cpp:358-366` calls `DrawableObject::Update`; `DrawableObject.cpp:41-43` calls `GameObject::Update`; `GameObject.cpp:160-164,202-212` resets and builds `m_world` from the then-current `m_position.X` (the parallax offset is disabled in `ParallaxLayer` constructor, `ParallaxLayer.cpp:4-19`). There is no later world rebuild in `ParallaxLayer::Update` or `Draw`.
- `ParallaxLayer.cpp:37-83` reads camera X at draw, forces one UV span, and for these unflipped layers sets `xShift=-0.000690*cameraX`, left U=`xShift+1`, right U=`xShift`. `Sprite.cpp:369-385,626-637` sends cached `m_world` and current UV buffer to the light-texture effect. Source culling in `GameObjectManager.cpp:320-329` uses the *post-follow object position*, not the cached matrix; the numeric trace assumes the layer passes culling.
- Linux `port/game/LevelScene.cpp:945-958,978-987` selects `worldX=cameraX` and `uvShiftX=+0.000690*cameraX` in the same draw; the positive SDL phase is its documented equivalent of the source's left/right reversed U convention. `UpdateVisuals` at `:732-749` stores no preceding followed X. The port scale is 2/3 at `:914-915`. This report reads current source only; no original Windows executable trace or matched capture was run.

B is a **66.667-pixel horizontal test-vector contrast**, not an observed per-frame discrepancy. At B, Windows already has C1's UV but C0's matrix; C matches Linux in geometry and equivalent UV phase. For a general moving sequence, source center minus port center is `-(cameraX[n]-cameraX[n-1])*2/3`, subject to initial load and any draw without an update. The XML layer Y is unchanged by follow (`followcamy=false`), so their vertical screen spans are identical under this effect. A pause or damage-effect update skip can retain the previous matrix longer (`Game.cpp:176-180`), which does not turn this X-only mechanism into a persistent Y-band cause.

## Visual significance and bounded next action

Existing controlled Linux hide-ID evidence in `port/COMPOSITION_DIAGNOSTIC_NOTES.md:66-70,83-95` attributes the near-black lower span to authored ID37 and the topmost dark edge to ID40; it does not establish a Windows mismatch. A horizontally shifted, 1365-pixel-wide quad still covers almost all of a 1280-pixel view in the +100 test, and source X shift cannot create/remove a broad horizontal stripe across its full width. The texture's black interior and alpha are independently source-authored. No art, alpha, UV-direction, or general band fix follows from this trace.

The bounded next action for the renderer owner, after its exclusive rotation work, is a CPU-only A/B/C regression of the update/draw state for a follow-X parallax layer, including world X and left/right U. If the team elects source-exact temporal parity, cache the pre-follow X during Linux visual update and use it only for draw destination on follow-X layers; keep UV from current camera and leave XML, Y, alpha, painter order and textures unchanged. Verify convergence at C and a continuous-motion case. A matched Windows capture with recorded camera history would still be needed to claim improved pixel parity or to prioritize this over larger visual gaps. Do not implement a broad rendering fix on the assumption that this explains the black band.
