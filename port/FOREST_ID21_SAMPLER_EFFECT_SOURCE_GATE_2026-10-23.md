# Forest-1 ID21 sampler/effect source gate — 2026-10-23

## Verdict

**No ID21 renderer or art change is justified.** The original D3D10 ordinary light-texture path declares wrap addressing and linear minification with linear mip interpolation, while the current Linux path sends this native-size sprite through an SDL full-texture copy with linear scale mode and no source-controlled mip chain. That is a real *sampling-contract uncertainty*, potentially affecting fine RGB/alpha edges, but no original bound mip descriptor or matched Windows pixels establish a dark-middle-band mismatch. At the measured Linux x320/y440–500 window, the mapped source is well inside a 7×7 fully opaque PNG neighborhood; sampler edge addressing cannot account for the observed ID21-over-ID19 coverage there. The established painter-order/occlusion result remains the actionable explanation for that Linux frame, not a demonstrated filtering defect.

## Original Windows contract and x320 relevance

- Forest XML ID21 is `kMiddleBackground`, center `(-678.915161,3736)`, native 1985×1238, repeat-X true, no flips, alpha 1, `effectlighttexture`, `tree_strip_dark.png`, and no occlusion fade (`Game/XmlFiles/levels/forest_exploration_1.xml:337-351`). `Sprite::RecalculateVertices` uses default U 0–1 and only extends U for **non-native** repeat-X (`Game/src/GameObjects/Sprite.cpp:19-22,194-235`); thus this sprite draws one ordinary source span, not an out-of-range repeat, at this location. The prior ordering and same-binary GPU gates already establish the ID19 → ID21 → ID22 order and ID21's current-Linux x320 occlusion (`port/FOREST_ID21_WINDOWS_ORDER_SOURCE_GATE_2026-10-23.md`; `port/FOREST_ID21_OVERDRAW_GPU_DISCRIMINATOR_2026-10-23.md`). This report does not reopen that result.
- `BasicLightTexture.fx` declares `MIN_LINEAR_MAG_POINT_MIP_LINEAR` and U/V `WRAP` (`Game/ShaderFiles/BasicLightTexture.fx:10-16`). The pixel shader samples diffuse at interpolated UV, multiplies sampled RGBA by `lightColor`, then sampled alpha by object alpha (`:53-59`). `EffectLightTexture::Load` initializes light color to `(1,1,1,1)` (`Game/src/Effects/EffectLightTexture.cpp:29-48`); `Sprite::Draw_effectLightTexture` binds ID21 texture/alpha and restores white after each draw (`Game/src/GameObjects/Sprite.cpp:626-672`). Its burst tint branch is time-limited by `kBurstTintMaxTime=0.25f` (`Sprite.cpp:17,639-648`); there is no authored ID21-specific darkening effect. Standard source-alpha blending is enabled in the original (`Game/src/Core/Graphics.cpp:392-407`). The darkness is in the sampled `tree_strip_dark.png` asset, subject to subsequent scene compositing/postprocess, not an explicit per-ID21 lighting parameter.
- `TextureManager::LoadTexture` calls `D3DX10CreateShaderResourceViewFromFile` with null load-info arguments and never queries/states the bound resource's mip count or view range (`Game/src/Core/TextureManager.cpp:50-79`). The FX mip filter is therefore **not proof of populated or selected Windows mips**. The `Sprite::GetTextureDimensions` resource query only reads width/height (`Game/src/GameObjects/Sprite.cpp:107-140`). An original draw-state capture is required to settle the mip question.

## Current Linux contract and bounded sensitivity

- The port decodes the PNG to RGBA and uploads via `SDL_CreateTextureFromSurface`, enabling alpha blend (`port/linux/SDLRenderer.cpp:153-185`). For ID21, the port's `repeatX` becomes false because `native=true` (`port/game/LevelScene.cpp:548-555`); its 1985×1238 source maps to roughly 1323×825 screen px at the measured camera, so the ordinary copy is minified and selects `SDL_ScaleModeLinear` (`port/linux/SDLRenderer.cpp:209-225,266-269`; projection `port/game/LevelScene.cpp:1269-1271`). The port passes the default white tint and alpha 1 (`port/render/Renderer.h:46-59`; `port/game/LevelScene.cpp:553-555,1283-1285`). The repeat-tile branch at `SDLRenderer.cpp:237-250` is **not** ID21's path, notwithstanding its XML repeat flag. SDL exposes one scale mode here; this ordinary copy contains no explicit D3D-style mip selection. Unlike ID46, no actual-draw GL state trace has been made for ID21, so this is a source-path comparison, not a driver-state claim.
- Using the already measured Linux camera `(1248.98621,3400)` and prior projected ID21 bounds `[-664.30,-269.95]..[659.03,555.39]` (`port/FOREST_MIDDLE_BAND_17_19_CURRENT_SOURCE_GATE_2026-10-23.md`), x320/y440,450,460,500 maps approximately to PNG x1476 and PNG y173,158,143,83 under the port's ordinary V inversion (`port/game/LevelScene.cpp:1289-1304`). A read-only Pillow probe of `Game/Media/objects/tree_strip_dark.png` found **alpha 255 throughout each 7×7 neighborhood** around these four mapped points; the corresponding x640 neighborhoods near source x1956 had alpha 0 throughout. These are approximate **source-image** probes, not bilinear/mip D3D samples. They place x320 hundreds of source pixels from the U edge and tens to hundreds from the nearest V edge, so WRAP versus edge clamping and a ~1.5-source-pixel base-level footprint cannot explain broad transparency or exposure of ID19 at x320. An actual Windows mip chain could still alter interior RGB texture detail or alpha around other transitions; no magnitude/direction is established here.
- The known Linux ladder changes all 61 x320 pixels at y440–500 when ID21 is removed after ID22, and then exposes ID19 at 60/61 pixels (`port/FOREST_ID21_OVERDRAW_GPU_DISCRIMINATOR_2026-10-23.md`). That is a current-frame causal compositing result; it is not a matched-Windows color verdict. The ID46 sampler gate and raft mip experiment (`port/ID46_WINDOWS_SAMPLER_SOURCE_GATE_2026-10-23.md`; `port/RAFT_MIP_RENDERER_EXPERIMENT_2026-10-23.md`) already identify the same generic D3DX10 null-load-info/mip uncertainty, so this report does not infer a new global defect from it.
