# Forest foreground parallax direction/phase audit — 2026-10-22

## Verdict

**One distinct, unaddressed phase-resolution discrepancy is source-provable:** the current SDL wrapped-UV path truncates forest foreground X phase to a whole **source texel**, whereas Windows supplies continuously varying float U coordinates to the D3D shader. This is a small, motion-dependent phase stair-step, **not a reversed direction** and not a demonstrated cause of the broad dark lower foreground or pale right shaft. The primary rightward-camera sign and speed are correct in current Linux source. The already documented one-update follow-X *destination* lag is a separate, larger transient contract difference; this report does not rediscover it as new or propose a flip/asset/XML change.

## Authored and Windows contract

- `Game/XmlFiles/levels/forest_exploration_1.xml:612-635,666-689`: IDs 37 (`shrubbery.png`, 2048×512) and 40 (`trees_top.png`, 2048×677) are unflipped `kMiddleForeground` `ParallaxLayer`s, 2048 world units wide, alpha .95, `followcamx=true`, `followcamy=false`, X multiplier `.000690`, no auto-scroll. They are the broad foreground layers visible through the raft/bridge and right/exit-shaft neighborhood. The raft pieces and ordinary ID15 shaft are different objects; their authored flips are outside this audit.
- `Game/src/GameObjects/ParallaxLayer.cpp:37-83`: for an unflipped layer at camera X=C, Windows sets `xShift=-0.000690*C`, then left U=`1+xShift`, right U=`xShift`. The interpolated U varies continuously with C; the shader passes it through and samples with WRAP (`Game/ShaderFiles/BasicLightTexture.fx:8-17,38-52`). For a rightward camera step, a fixed texture feature traverses **left** across the quad at `2048*.000690=1.41312` world units per camera unit, or `.94208` screen pixels per camera unit at the port's 2/3 projection. Background ID1 uses `.000059`, hence the intended slower rate. These are texture-motion rates, not the ordinary depth-sprite geometry factor.
- The source's follow-X update builds its world matrix before assigning current camera X; the resulting previous-update destination X versus current-camera U split was already established in `PARALLAX_FOLLOW_TEMPORAL_TRACE_2026-10-22.md` and GPU-quantified in `FOREST_FOLLOW_LAG_GPU_DISCRIMINATOR_2026-10-22.md`. It is not evidence for changing the phase sign.

## Current Linux contract and the narrow mismatch

- `port/game/LevelScene.cpp:1204-1245` follows current camera X for the quad, exempts `ParallaxLayer` from ordinary depth parallax, and passes `uvShiftX=+C*.000690` for these unflipped IDs. The positive SDL shift is the equivalent of Windows' negative phase because SDL's unflipped source intervals run left-to-right while D3D assigns left U one greater than right U. `port/PARALLAX_SPEED_CHECKPOINT_2026-10-22.md` records that sign correction; `port/tests/parallax_speed_test.cpp` checks the scene handoff but not the renderer's subtexel phase.
- `port/linux/SDLRenderer.cpp:246-261` passes the float shift to `ForEachUVWrapSegment`. That helper (`port/linux/UVWrap.h:15-29`) computes `cut = int(fract(shift)*pixels)` and builds **integer** `SDL_Rect` source intervals, with destination fractions from that integer cut. Consequently all C values whose product `fract(C*.000690)*2048` falls within the same integer bin draw the same source intervals and same destination fractions. The D3D vertex UVs change throughout that interval. The SDL path is monotonic in the correct direction but steps by one source texel at boundaries; the exact 2048-pixel texture dimensions are confirmed by the shipped PNG headers.
- Concrete held-camera pair (allow two updates at each camera to remove the known follow-X geometry lag): C=1000 and C=1000.5 yield Linux phase `.690000` and `.690345`; multiplied by 2048 these are `1413.12000` and `1413.82656`, so both have `cut=1413` and **identical** wrapped-X copy geometry/sampling. Windows left/right U each change by `-.000345` and its ideal texture-feature position changes left by `2048*.000345*(2/3)=.47104` screen pixel. The maximum port phase truncation is below one source texel (under 2/3 screen pixel at this scale); actual final RGB depends on filtering, texture detail, sepia, and rasterization. This is source-level phase evidence, not a measured Windows/Linux pixel delta.

## Discriminating physical-GPU experiment

On an exclusive physical-GPU lane, capture **ID37-only** forest-1 frames from the same identified current binary at held camera X=1000 and 1000.5 (or a pair in the same phase bin), with camera Y, viewport, level/effect time, weather, and all other state fixed; wait at least two updates after each camera change. Record draw destination and `uvShiftX`, and compare a high-contrast non-seam patch plus full-frame difference. The present port predicts identical ID37 X pixels for that pair; an experimental fractional-UV shader path, or a lossless original Windows capture with the same state, should show smooth fractional motion. Repeat across a cut boundary to distinguish the predicted discrete step from filtering noise. Do not infer a general forest-darkness correction from a subpixel result. For a Windows parity claim, pair a lossless original-Windows frame with actual camera history, viewport, level/effect phase, and player/pickup state; the Steam forest JPEG is not such a pair.
