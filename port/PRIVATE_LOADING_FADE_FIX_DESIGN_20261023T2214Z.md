# Forest→Waterfall loading fade: exact correction design

Read-only design handoff; no code, build, GPU, capture, index, or shared-checkpoint change. Basis: current `port/linux/main.cpp` loading branches (`675–711`), later visual gates (`1313–1339`) and draw (`1505–1513`), plus `PRIVATE_LOADING_FADE_INDEPENDENT_SOURCE_QA_20261023T2212Z.md` and Windows `UIGameLoading::Update/Load/FinishedLoading` (`Game/src/UI/UIGameLoading.cpp:60–129`). Scope remains this one trigger route.

## Minimal update/draw correction

1. At the start of each frame's play-level update decision, **latch whether loading paused gameplay on entry**: `loadingPausedThisFrame = (loadingPhase == FadeIn || loadingPhase == OpaqueHold)`. Use this latch for the exclusive loading branch and for the later weather/scene/player/combat visual gates; keep paper/upgrade modal gates independent. This preserves the Windows order in which game objects update **before** `UIManager::Update` changes loading flags: on the hold-exit frame gameplay stays paused; from the next frame (FadeOut on entry) gameplay runs. It also lets the trigger-start frame finish its already-started gameplay/visual update.
2. Keep FadeIn destination installation and `> 0.20f`, OpaqueHold `> 0.05f`, destination reset, and scoped trigger unchanged. Keep incrementing the loading clock once per loading frame. Move FadeOut clock advance and `> 0.20f` cleanup out of the exclusive loading branch into the ordinary gameplay branch (or a once-per-frame UI tick followed by branching on the **entry** latch). Otherwise FadeOut never ends after removing it from the pause branch. Do **not** reset `loadingPhaseTime` on OpaqueHold→FadeOut: Windows starts the fade-out clock in `Load()`, before the 0.05-s hold.
3. On OpaqueHold→FadeOut, set a frame-local `holdExitThisFrame` flag. At draw, use opaque alpha (`1`) when that flag is set, even though phase is now FadeOut. On the following frame, calculate `max(0, 1 - loadingPhaseTime / 0.20f)` using the already-running clock. This matches the Windows `if / else if` chain: `FinishedLoading()` unpauses but does **not** execute its FadeOut alpha calculation in that same UI update. Keep the splash composited after postprocess/HUD and keep strict `>` fade-out removal.

An implementation shape is: snapshot `loadingPausedThisFrame` and clear `holdExitThisFrame` before the existing `if/else if` chain; change the loading arm to `else if (loadingPausedThisFrame)` and remove its FadeOut case; set the flag at hold exit; in the ordinary gameplay arm, tick/retire FadeOut once **before** existing gameplay code; use `loadingPausedThisFrame` (rather than post-transition phase) in weather, `objectsPaused`, and `scene.UpdateVisuals` gating; use the flag first in the splash-alpha expression. Do not make gameplay dependent on whether the fade-out splash remains present. The first FadeOut gameplay frame and its visuals should run underneath that splash, including the frame on which it is retired.

## Minimal deterministic verification (CPU-only; separate implementer)

- Drive the actual state/update path with fixed `dt = 1/60` and a scripted Forest→Waterfall trigger. Record per-frame phase-on-entry, phase-after-update, gameplay/scene-visual update counts, and draw alpha. Assert FadeIn/hold entries pause; **hold-exit frame** (`holdTime > 0.05`, not `==`) remains paused and draws alpha 1; **next frame** has FadeOut on entry, advances gameplay/weather/scene/player/combat visuals once, and draws the first sub-opaque alpha from the unreset fade clock; FadeOut continues while gameplay advances; cleanup occurs only at `> 0.20`, with gameplay advancing on that frame too.
- Use a small step sequence that hits `==` and `>` boundaries (prefer controlled exact deltas around 0.05/0.20 rather than asserting a fragile floating-point frame ordinal). Verify destination installs only after fade-in exceeds 0.20 and exactly once, and unrelated routes remain immediate. Observe the computed tint alpha or renderer spy rather than infer it solely from phase. No screenshot/GPU requirement for this source correction; physical GPU gate is separately owned.

Timing note: Windows reads the total clock before `program.cpp` increments it after `Game::Update`; the port advances its capped `dt` locally. These checks target the source-backed pause/order and opaque boundary mismatch, not a new wall-clock or pixel-parity claim.
