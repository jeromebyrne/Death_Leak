# ID37 original-Windows mip and matched-trace feasibility — 2026-10-23

## Decision

**The original ID37 shader resource's actual mip level 1 is not runtime-proven here.** The original source plus Microsoft's D3DX10 contract make a full chain, including level 1, the **expected successful-load result**, not a measured `ID3D10Texture2D::GetDesc` or SRV range. The asset is an ordinary 2048×512 RGBA PNG containing only base-image data; any level 1 would be generated by D3DX, not embedded in the file. A matched original-Windows ID37 trace is **not executable from this checkout now**: no original game EXE/PDB or Wine/Windows build/run toolchain was found. Do not label a Linux capture or Steam JPEG as that trace.

## Concrete evidence and inference boundary

- Forest-1 XML ID37 specifies `Media\\levels\\forest_exploration_1\\shrubbery.png`, `effectlighttexture`, 2048×512 authored quad and alpha 0.95 (`Game/XmlFiles/levels/forest_exploration_1.xml:612-635`). Local PNG IHDR is 2048×512, 8-bit RGBA; its chunks are IHDR, gAMA, pHYs, tEXt, three IDATs and IEND—no DDS/container mip payload.
- Nonanimated `Sprite::LoadContent` calls `TextureManager::LoadTexture` (`Game/src/GameObjects/Sprite.cpp:162-170`), which caches the SRV by filename and calls `D3DX10CreateShaderResourceViewFromFile(device, path, nullptr, nullptr, &texture, nullptr)` (`Game/src/Core/TextureManager.cpp:50-79`). No call-site mip cap or separate ID37 texture route was found. Microsoft's [D3DX10 loader API](https://learn.microsoft.com/en-us/windows/win32/direct3d10/d3dx10createshaderresourceviewfromfile) defines null load-info as reading image characteristics and null pump as synchronous. Its [load-info contract](https://learn.microsoft.com/en-us/windows/win32/direct3d10/d3dx10-image-load-info) says `MipLevels=0` or `D3DX10_DEFAULT` creates a full chain. For 2048×512 that predicts 12 levels (0–11), with level 1 at 1024×256, **if that documented default is the effective path and creation succeeds**. Source does not record the effective load-info, descriptor, or view range. In particular the null call is not itself a `GetDesc` result.
- `BasicLightTexture.fx:10-16,53-59` requests `MIN_LINEAR_MAG_POINT_MIP_LINEAR`, WRAP U/V and an implicit-derivative `Sample`. At a 2/3 projected scale, ID37's one-span quad nominally minifies by 1.5, yielding LOD about 0.585; an accessible level 1 would enter the mip-linear blend. This is a shader/resource **expectation**, not a sampled-LOD measurement. Linux's fractional path uses only `GL_LINEAR` on the base image (`port/linux/SDLRenderer.cpp:418-427`), as the post-alpha gap report noted.
- Fresh local inventory under `/srv/openclaw/workspace/death_leak_analysis` found zero `.exe` and `.pdb` files; checks found no `wine`, `wine64`, `wineserver`, `msbuild`, `dotnet`, `clang-cl`, MinGW C++ compiler, `steam`, `steamcmd`, `powershell` or `pwsh`. `Game/D3DX10d_43.dll` is present but is a library, not a runnable game. The existing Steam forest screenshot is a lossy, unpaired frame. Thus neither an original bound-SRV descriptor nor synchronized ID37 draw/frame metadata can be collected locally today. This is a local prerequisite, not proof that the shipped game lacks mips.
