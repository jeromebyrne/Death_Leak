# Forest→Waterfall loading fade — independent source-contract QA

Scope: read-only inspection of Windows source and committed `50014a1` diff against `port/linux/main.cpp`; no GPU, build, capture, or shared-file edits. HEAD was `50014a1` at review start. Unrelated dirty files were preserved.

## Verdict

**Concrete source-backed gameplay-pause mismatch:** Windows `UIGameLoading::FinishedLoading()` calls `UnPauseGame(false)` after `currentTotalTime > loadStart + 0.05` (`Game/src/UI/UIGameLoading.cpp:76-82,96-103`). `Load()` starts the fade-out clock immediately (`:105-129`). Thus the next game update runs active Waterfall gameplay while the black splash continues fading for roughly another 0.15 s. In the port, `loadingPhase != None` selects the exclusive loading branch (`port/linux/main.cpp:675-711`) and suppresses scene/weather/player/combat visual updates (`:1313-1339`) all the way through `FadeOut`; gameplay resumes only when its elapsed time exceeds 0.20 s after load. This extends the pause beyond the Windows contract and delays Waterfall simulation/animation behind a partially transparent splash.

**Smallest fix recommendation:** Keep the fade state machine ticking every frame, but make gameplay pause conditional on `FadeIn` or `OpaqueHold`, not `FadeOut`. On the frame crossing the 0.05 s hold boundary, select the loading branch as before (Windows game objects were already updated earlier that frame); starting with the following frame, run gameplay, weather, `scene.UpdateVisuals`, player/combat visuals during `FadeOut` while continuing to draw the splash. Preserve the existing `> 0.20` fade-out removal and trigger-specific destination logic. Avoid putting the FadeOut timer only inside the exclusive pause branch once that branch no longer runs.

**Secondary one-frame alpha mismatch:** On the exact update where `OpaqueHold` exceeds 0.05 s, Windows only calls `FinishedLoading` and changes flags; its `else if` chain does not execute the FadeOut alpha update that frame (`UIGameLoading.cpp:76-93`). The port flips phase to `FadeOut` at `main.cpp:701-705`, and the same frame's draw computes `1 - loadingPhaseTime / 0.20` (`:1505-1512`), immediately revealing the destination. Keep the splash alpha at 1 for that boundary draw; perform the first FadeOut alpha update on the following frame. The fade-out *clock* should still retain elapsed time from `Load()`, as the current code does.

## Source-contract checks

- Timing constants and strict `>` boundaries match: Windows 0.20 s fade-in, 0.05 s loading branch, 0.20 s fade-out (`UIGameLoading.cpp:7-8,69,78,88`); port constants and tests at `main.cpp:428-429,679,701,706`. Windows `Timing::GetTotalTimeSeconds()` is incremented by the capped, modified delta after `Game::Update` (`Game/src/program.cpp:148-175`), while the port accumulates its similarly capped `dt` (`main.cpp:550-559,678`). Consequently a fixed `--fixed-dt` affects this port fade as it does other simulation-clock effects; the source does **not** establish wall-clock fade parity under slow frames. No GPU timing claim is made.
- Trigger semantics: Windows `LevelTrigger::Update` defers `SwitchToLevel` (`Game/src/GameObjects/LevelTrigger.cpp:21-39`), handled after object updates (`Game/src/GameObjects/GameObjectManager.cpp:260-287`); `SwitchToLevel` pushes loading UI, pauses, starts loading (`:532-561`). The port starts fade at the Forest→Waterfall trigger (`main.cpp:1249-1285`) and delays destination scene installation until fade-in exceeds 0.20 s (`:675-700`). Restricting this commit to that one route is an intentional scope limit, not general Windows transition parity.
- Draw order: Windows world → postprocess → `UIManager::Draw` (`Game/src/program.cpp:293-318`); the loading screen is pushed to the current-screen tail (`Game/src/UI/UIManager.cpp:237-267`). The port draws its splash after scene postprocess and HUD (`main.cpp:1443-1513`). `gameloading.xml:1-9` has one active `blank_dark.png` sprite. This establishes ordering, not pixel parity.
- Original paused-object behavior is corroborated by `Game/src/Game.cpp:154-255` and `Game/src/GameObjects/GameObjectManager.cpp:205-257`: UI still updates while gameplay objects are paused. The port matches that only through the loading hold; the fade-out discrepancy above is material.

No runtime or visual parity was asserted. Lane released; report is the sole file written in this QA task.
